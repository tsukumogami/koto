# Lead: What does koto's event log actually expose, and what bounds it?

## Findings

**What gets written, per event type.**

- `DefaultActionExecuted` (`src/engine/types.rs:544-550`) carries five fields: `state`, `command`, `exit_code`, `stdout`, `stderr` — all `String`/`i32`, all required, all persisted verbatim. `command` is captured *after* variable substitution (`src/cli/mod.rs:3969`, `variables.substitute_command(&action.command)`), so any `--var` value interpolated into the command text is baked into the persisted string, not just referenced. `stdout`/`stderr` are truncated to 64KB each (`MAX_ACTION_OUTPUT_BYTES`, `src/cli/mod.rs:61`; applied at `src/cli/mod.rs:4025-4026` via `truncate_output`, `src/cli/mod.rs:833-845`) *before* the event is built and appended (`src/cli/mod.rs:4029-4036`). `command` itself has no length cap or truncation anywhere in this path — a secret concatenated into the command string is captured in full regardless of the 64KB stdout/stderr bound. `docs/reference/session-feed.md:194-211` and `:723-747` document this shape publicly, including "May be large" on stdout/stderr.

- Command gates (`GateEvaluated`, evaluated via `evaluate_command_gate`, `src/gate.rs:206-233`) do **not** persist the gate command's stdout at all. On pass/fail, only `{"exit_code": N, "error": ""}` is stored; on a spawn/wait failure (`exit_code == -1`), `output.stderr` (the OS-level spawn error message, not the target process's own stderr) is stored via `serde_json::json!({"exit_code": -1, "error": output.stderr})` (`src/gate.rs:217-220`). Gates are a structurally narrower leak surface than actions — this is worth stating plainly since the two are easy to conflate.

- `GateOverrideRecorded` (`src/engine/types.rs:562-569`) persists `rationale`, `override_applied`, and `actual_output` as unbounded `serde_json::Value` — no truncation, no cap. These are agent- or operator-authored, not shell-captured, but nothing stops an override rationale from quoting a secret.

- `EvidenceSubmitted` (`src/engine/types.rs:483-500`) persists `fields: HashMap<String, serde_json::Value>` — fully arbitrary, agent-submitted JSON, unbounded, no schema restriction on content, no truncation. This is agent-authored content (`koto evidence submit`), a distinct exposure path from command capture: it leaks whatever the agent chooses to write, not what a subprocess printed.

- `WorkflowInitialized` (`src/engine/types.rs:455-468`) persists `variables: HashMap<String, String>` — the resolved `--var KEY=VALUE` bindings, in plaintext, unencrypted, unbounded. `resolve_variables` (`src/cli/mod.rs:762-824`) validates each value only for **shell-metacharacter safety** via an anchored allowlist regex documented in `DESIGN-template-variable-substitution.md:405-413` (`^[a-zA-Z0-9._/-]+$` per the doc's Security Considerations) — this allowlist governs which characters are legal, not whether the value is sensitive. There is no secrecy classification, no "do not persist" flag, no per-variable redaction. `DESIGN-template-variable-substitution.md:428-430` states this plainly: "**Plaintext storage.** Variable values are stored in plaintext in the state file... Don't store secrets (API keys, tokens, passwords) as variable values. The CLI help text and template authoring docs should note this" — i.e., the only mitigation on record is a documentation instruction to authors, not an enforced control.

**Bounds that exist.** Only one enforced bound exists in the whole event surface: the 64KB truncation on `DefaultActionExecuted.stdout`/`.stderr`. Nothing else is capped — not the command string, not gate-override payloads, not evidence fields, not init-time variables. A repo-wide search for redaction/secret-scanning/masking (`grep -rni "redact\|secret\|mask"` across `src/`) turns up exactly one real redaction mechanism, and it is scoped narrowly to cloud **credentials**, not event content: `redact()` in `src/config/mod.rs:420-430` masks `session.cloud.access_key`/`secret_key` to `<set>` when *displaying config* (`koto config list`), and `src/config/validate.rs:1-20` refuses to let those two keys land in project-shared config at all. Neither mechanism touches the event log. No pattern-based secret scanner exists anywhere in the codebase.

**Where the state file lives and travels.** `docs/workspace-layout.md:8-30` is unambiguous: `~/.koto/sessions/<id>/koto-<id>.state.jsonl` is the "AUTHORITATIVE state," living entirely under the user's home directory, outside any git working tree, by default (`session.backend` defaults to local storage). The **real** second distribution path is the opt-in cloud backend, not git. `CloudBackend::append_event` (`src/session/cloud.rs:722-731`) calls `sync_push_state` → `strict_push_state` (`src/session/cloud.rs:127-139`) after *every single mutating call* (every `koto next`, every evidence submission, every action) — it reads the **entire local state file** off disk with `std::fs::read` and uploads it wholesale via `put_object` to an S3-compatible bucket. There is no per-event or incremental push for state (context artifacts get incremental sync via `sync.rs`; the state file does not) and no client-side encryption before upload — a `grep -rni encrypt src/` returns nothing. `docs/guides/cloud-sync-setup.md` documents this as team infrastructure: the bucket endpoint/name/region are meant to be committed to `.koto/config.toml` via `--project` and shared across a team, while only the access/secret keys are meant to stay out of project config. Practically: once cloud sync is enabled, every `DefaultActionExecuted` command/stdout/stderr, every `--var` value, and every evidence submission for every session anyone on the team runs is replicated, in full, to a shared bucket that anyone holding read credentials for that bucket can read. This is a materially bigger fan-out than "committed to a feature branch" — it is automatic, continuous, and team-wide by design, not a one-time commit an author has to remember to make.

**Testing the design doc's premise — it is stale.** `DESIGN-default-action-execution.md`'s Security Considerations section (`docs/designs/current/DESIGN-default-action-execution.md:435-440`) reads: "Action stdout/stderr is persisted in the state file, which is committed to feature branches. If an action command's output contains secrets..., those secrets end up in the event log. Mitigation: document that action commands should not produce sensitive output. Truncation at 64KB limits exposure..." Checking whether the state file is actually committed to feature branches today: it is not, and the doc's own git history shows why. This design merged 2026-03-23 (PR #75). Session storage was overhauled four to five days later — local session storage landed 2026-03-27 (PR #84) and the config system plus S3 cloud sync landed 2026-03-28 (PR #98) — and `docs/prds/PRD-session-persistence-storage.md` (status: **Done**) documents exactly this move: its Problem Statement explicitly describes the *prior* architecture ("koto stores workflow session state... in a `wip/` directory committed to git feature branches. This works for solo development but... prevents transferring sessions between machines...") and its Goals commit to the state now living under koto-owned storage, "local filesystem (outside git), with cloud and git as configurable alternatives." A git-backed session store was never built, though — `src/session/mod.rs:177` still lists it as a placeholder: "Future backends (cloud, git) will implement this," and only `local` and `cloud` exist in `src/session/` today (`local.rs`, `cloud.rs`; no `git.rs`). So: `DESIGN-default-action-execution.md` was written against the architecture that existed for those four days in late March, before the persistence-storage PRD shipped, and its Security Considerations section was never revisited afterward. The sentence "committed to feature branches" describes a system that no longer exists for koto's own state file. (A separate, unrelated thing genuinely is still committed to feature branches: shirabe's own `wip-yaml-md` scratch state — YAML-in-Markdown files under `wip/` that shirabe's `execute`/`work-on` skills read and write, per `references/parent-skill-pattern.md:376` and the `tsuku` CLAUDE.md's wip-hygiene rule. That is a distinct artifact with distinct, much smaller content — plan-execution progress markers, not full command stdout — and `references/parent-skill-pattern.md:307` is explicit that it is "not the parent's state file." I checked several `wip/*.md` and `wip/*.yaml` files across shirabe's own repo and found no koto `.state.jsonl` content pasted into any of them; they're a separate mechanism entirely.)

**Realistic exposure in shirabe's shipped templates.** I grepped both of shirabe's koto templates (`skills/execute/koto-templates/execute.md`, `skills/work-on/koto-templates/work-on.md`) for `default_action:` and found zero occurrences in either. Neither shipped template uses the action-execution feature this design doc introduces — every `gh`/`git` invocation I found in both templates (`gh pr checks`, `gh pr list`, `gh pr create`, `gh pr edit`, `gh pr ready`, `git push`, `git rev-parse`) is either a **gate** `command:` field (whose stdout is discarded per the gate-evaluation finding above — only exit code and, on spawn failure, a spawn-error string are kept) or prose instructing the *agent* to run the command through its own tool layer, not through koto's `default_action`. The latter case doesn't touch koto's event log at all — it lands in the agent's own transcript, a separate surface this lead doesn't cover. So today, `DefaultActionExecuted`'s full-stdout-capture path is a real capability with zero live callers in shirabe. If and when a template does add a `default_action:`, the most plausible leak vectors would be: a `gh` command failing and printing a diagnostic that echoes an auth header or config value; a `git push` over an HTTPS remote URL that embeds a credential (`https://<token>@github.com/...`) — the URL itself, not just command output, would appear verbatim in the persisted `command` field, since substitution happens before capture; or any script whose failure path dumps its own environment/config for debugging. The `command`-field exposure (interpolated `--var` values baked into a persisted string) is not hypothetical — it's how the mechanism is built today, and it's untouched by the 64KB stdout/stderr truncation entirely.

## Implications

The stdout/stderr truncation the design doc leans on as a mitigation is real but narrow: it bounds two of roughly six unbounded-content fields across the event schema, and it doesn't touch the one field (`command`) most directly under an author's control to avoid leaking a secret into (a `--var`-interpolated command string is exactly the shape a credential would take if someone did the thing `DESIGN-template-variable-substitution.md` already warns against). The design doc's stated mitigation — "committed to feature branches" as the exposure mechanism, closed by "document that commands shouldn't produce sensitive output" — describes a distribution path that was already dead by the time cloud sync shipped days later, and understates the path that replaced it: opt-in cloud sync is a stronger, continuous, team-wide distribution mechanism that the doc doesn't mention because it postdates the doc.

## Surprises

- The design doc's central premise (git-committed state file) is not just outdated but was *already* being superseded within the same week the design merged — PRD-session-persistence-storage explicitly names the old wip/-committed-to-git approach as the problem it exists to fix, and shipped four to five days after this design doc's PR.
- Gate commands (the other place `sh -c` runs) do **not** leak stdout into the log at all — only `DefaultActionExecuted` does. Conflating "gates" and "actions" as one exposure surface would overstate the gate side and understate that action-specific capture is where the real risk concentrates.
- Shirabe's two production templates don't use `default_action` at all yet, so today's actual exposure through this mechanism, in the only templates that ship, is zero — the risk is entirely prospective, tied to future template authoring rather than current behavior.
- The `command` field (post-substitution, unbounded, uncapped) is a bigger and less-discussed leak surface than stdout/stderr: it captures secrets injected as *arguments*, which a truncation-of-output mitigation does nothing about.

## Open Questions

- Should `--var` resolution or template compilation reject values that look like credentials (entropy heuristic, known-prefix patterns like `ghp_`, `sk-`, AWS key prefixes) as defense in depth, given the allowlist regex already exists as a validation choke point (`src/cli/mod.rs:818-822`)?
- If cloud sync is meant to become the primary multi-machine story (per the persistence-storage PRD's own goals), does state-file content warrant either client-side encryption before `put_object`, or a documented policy that cloud-synced buckets are a shared-trust boundary equivalent to giving every reader full command/output visibility across all sessions?
- Should the `command` field get a distinct cap or a "known-safe" substitution mode (e.g., an option to log the pre-substitution template string plus opaque variable references, rather than the fully rendered command) so a secret-bearing `--var` doesn't get baked into an unbounded log field verbatim?

## Summary

`koto`'s event log has exactly one enforced content bound — a 64KB truncation on `DefaultActionExecuted.stdout`/`.stderr` (`src/cli/mod.rs:61,833-845,4025-4026`) — while `command` (post-substitution, so any interpolated `--var` secret is baked in), gate-override payloads, evidence fields, and init-time variables are all persisted unbounded and unencrypted with no redaction anywhere in the codebase; gate commands, by contrast, don't leak stdout at all. The design doc's "committed to feature branches" premise is stale: it was accurate for the few days before PRD-session-persistence-storage (status: Done) shipped local session storage outside git (`~/.koto/sessions/`, per `docs/workspace-layout.md`) and S3 cloud sync days later, and the real distribution risk today is the opt-in cloud backend, which uploads the entire state file wholesale to a team-shared bucket after every mutating call with no client-side encryption. Neither of shirabe's two shipped templates uses `default_action` yet, so current real-world exposure through this specific mechanism is zero; the recommended bound going forward is capping/hashing the `command` field alongside stdout/stderr and treating cloud-sync buckets as a shared-trust boundary requiring either encryption or explicit access-scoping documentation.

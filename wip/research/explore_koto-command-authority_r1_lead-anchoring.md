# Lead: What must execution anchoring guarantee now that it is the primary remaining guard?

## Findings

### The design's premises still hold against current code

Nothing described in the round-2 anchoring lead has been implemented — `execution_root`, `koto session bind`, and any containment check are all absent from the tree (`grep -rn "execution_root\|SessionBind\|fn bind" src/` returns nothing relevant; the only `bind` hits are `request_store::bind_leg` and `request.rs`'s unrelated `bind` verb). The single choke point is real and unchanged: `handle_next` (`src/cli/mod.rs:2892`) captures `current_dir` once at `src/cli/mod.rs:3082`, and both the gate closure (`src/cli/mod.rs:3955`) and the action closure feed it straight through. The action `wd` computation is still exactly as round 2 described, at `src/cli/mod.rs:3979-3983`:

```rust
let wd = if action.working_dir.is_empty() {
    current_dir.clone()
} else {
    std::path::PathBuf::from(variables.substitute(&action.working_dir))
};
```

— a bare `PathBuf::from`, no `current_dir.join(..)`, no canonicalize. `run_shell_command` (`src/action.rs:26-40`) takes `working_dir: &Path` and passes it straight to `Command::current_dir` with zero validation. `template_source_dir` (`src/engine/types.rs:260`) is confirmed still to be the template file's own parent directory (`src/cli/init_child.rs`, `src/engine/path_resolution.rs:1-21`'s docstring: "the directory the parent template was loaded from"), not the working tree, and it's still read only by the batch child-path resolver, never by the gate/action execution path. Session lookup is still flat and name-keyed under `~/.koto/sessions/<name>/`; `repo_id()` in `src/session/local.rs:645` exists only for cloud blob-prefixing, not local scoping. All of round 2's findings check out against the current commit; there is no drift to correct.

### Refusing on cwd mismatch is necessary but not sufficient — and the design as stated has a real implementation trap

Anchoring, as scoped, guards the *entry* to `handle_next`: it can refuse to tick a session unless the live cwd canonicalizes to the recorded `execution_root`. That closes the exact hazard round 1 proved (`tmp/kototest` vs `tmp/elsewhere`) completely — a session can no longer be advanced from a directory other than the one it's bound to, full stop.

It does not, and structurally cannot, constrain what the *command* does once execution is allowed to proceed. `default_action`'s `command` field is an arbitrary `sh -c` string. Nothing about anchoring the entry point stops that string from containing `cd /some/other/repo && ...`, an absolute path, `git -C ../sibling-repo push`, `ssh host 'rm -rf /'`, or anything else the invoking OS user can do. The command runs with the same authority the invoking user has everywhere else on the machine — anchoring narrows *where the workflow may be advanced from*, not *what the advanced command may touch*. Given the author ruling that invoking a koto-backed workflow is itself the grant, this is consistent with the design's own logic — the grant was never scoped to a filesystem subtree in the first place — but it means "primary guard" has to be read narrowly: primary guard against **misdirection** (wrong tree, wrong session, stale terminal), not primary guard against **unintended side effects** in general.

There's a second, sharper gap worth flagging before this gets implemented: the design's own containment fix for `working_dir` — "resolving `working_dir` by joining and canonicalizing under the root" — has to be built carefully or it doesn't close what it claims to close. `PathBuf::join` in Rust has a documented gotcha: if the path being joined is absolute, `join` **discards the base and returns the absolute path unchanged** (`root.join("/etc")` == `/etc`, not `root/etc`). So "join `execution_root` with the substituted `working_dir`, then canonicalize" stops the `..`-escape (issue #186's traversal case) but, taken literally, does *nothing* against an absolute `working_dir` value — which is precisely the other half of #186's "unescaped substitution" finding. The fix needs an explicit check ahead of the join: reject (or re-root) any substituted `working_dir` that is itself absolute and doesn't already start with the canonicalized `execution_root`, before calling `.join()`. This isn't a reason to abandon the approach; it's a concrete correctness requirement the design doc should state explicitly, because "join and canonicalize" reads as sufficient and silently isn't.

### What would close the starting-point/reach gap — weighed against distribution constraints

I checked `install.sh` and `.github/workflows/release.yml`: koto ships as a single static binary for four targets — `x86_64`/`aarch64` on both `linux-gnu` and `apple-darwin` (`release.yml:18-27`) — installed by `install.sh` without sudo, no system dependency check beyond `uname`. That constrains the options:

- **Template-declared path allowlist.** Cheap to add as schema (a list of path prefixes a `default_action` is expected to touch) but nothing enforces it without OS-level mediation of the syscalls the shell command makes — the allowlist becomes documentation, the same "author-attested, not compiler-checked" shape `requires_confirmation` already has (round 1, Finding 3: `docs/designs/current/DESIGN-default-action-execution.md:442-446` — "the template author is responsible for setting this flag correctly"). Worth doing as an audit/review aid, not worth presenting as an enforcement boundary.
- **Restricted user or container.** Both require privilege or a runtime koto doesn't have and can't assume — creating a restricted OS user needs root, which contradicts the no-sudo install model; requiring a container runtime (Docker/Podman) present on every dev machine is a system dependency of exactly the kind the org's tools deliberately avoid (see the sibling `tsuku` project's own "no system dependencies" philosophy). Ruled out.
- **Linux namespaces / bwrap / seccomp.** Real containment, but Linux-only — two of the four shipped targets are `apple-darwin`. Shipping this would mean the "primary guard" has two different actual strength levels depending on platform, or it needs a macOS-equivalent (Seatbelt/`sandbox-exec`, itself deprecated by Apple) built and maintained in parallel — real platform-specific complexity for a tool whose whole pitch is a single portable binary. Not something to fold into this design; if pursued at all, it's a separate, later, Linux-first initiative with an explicit "unsupported on macOS" callout, not part of what ships now.
- **Destructive-pattern denylist** (regex against `rm -rf /`, `--force`, etc.). Weak — trivially defeated by indirection (a variable, an alias, base64, a wrapper script) — and duplicates the reversibility-classification problem that's already unenforced (`requires_confirmation`). It would manufacture false confidence rather than close a real gap. Not recommended as a security control; might be worth a soft lint at template-authoring/validation time ("this command looks destructive, did you mean `requires_confirmation: true`?"), but that's an authoring nudge, not a guard.
- **Accept the limit and document it.** This is the honest option given the constraints above. Anchoring's job, done well, is to make the *directory a workflow transacts from* deterministic, bound, and auditable — nothing more. That's a complete, valuable guarantee for the misdirection class and it's the only one of the five that doesn't require privilege, a new runtime dependency, or platform-specific code the project isn't set up to maintain.

### The bind verb is a real authority surface, but a narrow one given the ruling

`koto session bind` changes which directory's commands are trusted for every future tick of a session — but per the author ruling, it doesn't grant new *command* authority (the workflow's commands already carry whatever authority the invoking user has); it relocates *where* that already-granted authority is allowed to act from. Given that, I'd hold it to three properties, all consistent with what round 2 already proposed:

1. **Auditable, always.** Append an event recording old root, new root, and timestamp (an actor identity if the caller has one to offer) — round 2's proposal already has this, it should not be optional.
2. **Explicit, never inferred.** `koto next` must never auto-rebind on a mismatch, even "just once with a warning" — that would quietly re-create the exact silent-drift hazard anchoring exists to close. Bind has to be a verb someone (operator or agent, acting deliberately) types on purpose, structurally separate from the `koto next` tick path — a session-lifecycle operation, not a per-tick fallback.
3. **Sanity-checked, not confirmation-gated.** It doesn't need `requires_confirmation`'s interactive stop — that would defeat the automation the design is trying to enable — but it should refuse a target that doesn't exist or isn't a directory, the same class of basic check `koto init` already implies.

### Worktree reality re-verified — unchanged from round 2, plus one adjacent wrinkle

I re-read both worktree-discipline documents on this branch. `phase-2.5-worktree-discipline.md:26-29` still runs `git fetch origin` + `git rebase origin/main` **in place**; `references/worktree-discipline.md`'s generalized parent-skill version is the same in-place rebase pattern generalized across `/scope` and `/charter`. Neither moves a running session's process to a different directory. `skills/execute/SKILL.md:296-299` still confirms the one real worktree use is `/execute`'s coordinated multi-repo path, and it's a fresh `/work-on` dispatch into a new worktree directory — that dispatch runs its own `koto init` there, producing a *new* session with its own `execution_root`, not a relocation of an existing one. `niwa worktree create` (`public/niwa/docs/guides/worktree.md:12-15`) confirms the same shape at the outer-harness level: it creates a new directory (`<instance>/.niwa/worktrees/<repo>-<id>/`) and installs context into it — it does not, and has no mechanism to, move a session that's mid-flight elsewhere. The legitimate relocation case anchoring has to survive is genuinely rare in-repo, and the templates that exist today never trigger it.

One adjacent finding worth flagging: `public/niwa/docs/spikes/SPIKE-enterworktree-hook-bypass.md` documents a real bug where an agent's native worktree-isolation action can land in a bare, niwa-untracked worktree directory instead of the niwa-managed one, under certain nested-repo conditions. That's a bug in a different layer, not something anchoring needs to know about — and it's actually a point in anchoring's favor: if a koto session gets resumed from such a stray, untracked directory, anchoring refuses on cwd mismatch exactly as designed, fail-safe, without needing any awareness of *why* the directory is wrong.

### Sequencing — what ships first

Three of the five pieces are inert alone and have to land together to raise the floor at all: **recording `execution_root`** at `koto init`, **refusing on mismatch** in `handle_next`, and **safe `working_dir` resolution** (join with an absolute-path guard, then canonicalize). Refuse-on-mismatch without the safe join is bypassable the moment a template sets an absolute `working_dir` — the exact trap described above. Safe join without refuse-on-mismatch still lets a session with unset `working_dir` run wherever the caller's live cwd happens to be, which is the original hazard, untouched. These three are one commit's worth of work, not three independent increments.

`koto session bind` and structured containment errors can trail by a separate PR without weakening what the first PR ships, provided the first PR also picks a migration behavior for state files with no `execution_root` — I'd recommend **implicit bind-once**: the first successful post-upgrade tick records whatever cwd is live as `execution_root` and enforces from then on, rather than either extreme round 2 left open (hard-refuse every in-flight session until an operator manually binds, which breaks everything the day this ships; or silently trust cwd forever, which never starts enforcing). This needs the same audit event as an explicit bind, just triggered by upgrade rather than by command.

Structured errors are worth doing regardless of anchoring — they fix a real observability gap for spawn failures generally, not only containment violations — but they're a quality-of-life fix, not part of the security boundary, and don't block anything else.

## Implications

- "Primary guard" is accurate for the misdirection class specifically (wrong tree, resumed-elsewhere session, stale terminal, two worktrees sharing a session name) and should be described that way, not as a general guard against unintended side effects. The two are different claims and the design should not conflate them.
- The `working_dir` fix as sketched in round 2 ("join and canonicalize under the root") needs one more sentence in the design doc: reject or re-root any absolute substituted value before joining, or `Path::join`'s absolute-override semantics silently defeat the containment for exactly the traversal case #186 already flagged.
- None of the containment-widening options (allowlist, sandbox, container, denylist) clear the bar of "doesn't make koto undistributable or Linux-only" except documenting the limit. That should be stated plainly in the design rather than left as an open question — it's not unresolved, it's ruled out by the CI matrix and install model already in the repo.
- The bind verb doesn't need to be heavier than a sanity-checked, audited, explicit CLI verb. It isn't minting new command authority under the author ruling — it's relocating where already-granted authority is allowed to act, so the bar is honesty and an audit trail, not friction.

## Surprises

- `PathBuf::join`'s absolute-path override behavior is a real, specific trap for this exact fix and isn't mentioned in either prior lead — "join and canonicalize" sounds complete and isn't, unless the absolute case is checked first.
- The coordinated `/execute` worktree path doesn't actually need `koto session bind` at all — it always produces a fresh `koto init` in the new directory rather than relocating an existing session — which narrows the bind verb's real-world call sites even further than round 2 already found.
- The niwa-side `EnterWorktree` hook-bypass bug turns out to be reassuring rather than concerning for this design: a stray untracked worktree is just another wrong directory, and anchoring's fail-safe refusal doesn't care that the wrongness originated in a different tool's bug.

## Open Questions

- Should `execution_root` be recorded as canonicalized at `koto init` time (resolving symlinks then) or left as the raw path and canonicalized only at comparison time? Symlinked repo paths (common with niwa's worktree/instance layout) make this not purely cosmetic — a session `koto init`-ed through a symlink and later ticked via the resolved path (or vice versa) would false-positive a mismatch unless both sides canonicalize consistently.
- Does the implicit bind-once migration need its own opt-out for operators who'd rather hard-refuse every legacy session on principle (e.g., a fleet operator who wants to audit each one manually before it resumes)? I don't think it needs one to ship, but it's a legitimate ask.
- Nothing in this exploration determined whether `koto next` should surface a *warning* (not a refusal) when `working_dir` is set but empty-string vs. absent are treated differently by the schema today — orthogonal to anchoring but adjacent enough that the implementer will hit it while touching this code.

## Summary

Anchoring's premises hold unchanged against the current tree, and refusing on cwd mismatch fully closes the misdirection hazard it was designed for — but it only guards the directory a session may be *ticked from*, not what an authorized command can *reach* once running, which is a narrower promise than "primary guard against unintended side effects" implies given the author ruling already made invoking the workflow the full grant. Every option that would close that reach gap (allowlists, containers, restricted users, Linux sandboxing, denylists) either collapses to unenforced documentation or breaks koto's single-binary, no-sudo, four-platform distribution model, so the honest scope is: guarantee the workflow's home directory, not the command's blast radius, and say so plainly in the design rather than let "primary guard" imply more. The one implementation trap worth fixing before this ships is that `Path::join` silently discards containment against an absolute `working_dir` unless that case is checked explicitly ahead of the join — everything else in the round-2 design (recorded root, refuse-on-mismatch, safe join, an explicit audited bind verb, structured errors) is sound and should ship as one inseparable first increment (root + refuse + safe join) followed by bind and structured errors.

# Lead: Which candidate direction best fits koto's architecture, and what's the diff size/risk for each?

## Findings

### CLI structure baseline

`src/cli/mod.rs` (5605 lines) defines `Command` (the top-level clap `Subcommand` enum, lines 82-262) with an existing `Session { subcommand: SessionCommand }` group (`Command::Session`, line 219). `SessionCommand` (lines 362-455, `src/cli/mod.rs`) already has: `Start`, `Dir`, `List` ("List all sessions as JSON"), `Cleanup` ("Remove a session directory (idempotent)"), `Resolve`, `Update`. There is no `session status` or `session gc` today — top-level `koto status <name>` (`Command::Status`, line 231, handler `handle_status` at line 4387) is the read-only inspector, and `Command::Init` (line 92) is the create verb. `koto workspace prune` (`WorkspaceCommand::Prune`, lines 266-299, impl in `src/cli/workspace.rs`) is the closest existing "bulk destructive verb with dry-run/confirmation" precedent, but it is root-scoped (`--root <id>` + descendant walk via `backend.list()` + parent filter), not a whole-workspace sweep.

`backend.list()` (the `SessionBackend::list` trait method, `src/session/mod.rs`) already gives a "list every session" capability used today by `koto session list` (`session::handle_list`, `src/cli/session.rs:504`), by `koto workspace prune`'s descendant walk, and by `derive_superseded_branches` in `handle_status`. **This already satisfies the "iterate ALL sessions" prerequisite all three directions need** — no new enumeration primitive is required.

However, `SessionInfo` (`src/session/mod.rs:129-141`) — the struct `list()` returns — carries only `id`, `created_at`, `template_hash`, `parent_workflow`. **It does not carry `template_source_dir`.** `LocalBackend::list()` (`src/session/local.rs:84-127`) reads each header via `persistence::read_header` but only copies those four fields into `SessionInfo`; `template_source_dir` is read off the header but dropped. `CloudBackend::list()` (`src/session/cloud.rs:677-699`) is worse for this purpose: for sessions that exist only in S3 it fabricates a placeholder `SessionInfo` with empty/`None` fields (no header download), so `template_source_dir` would be unknowable for those rows without an extra network round-trip per session.

`SessionBackend`'s methods are annotated per-method with a stability tier (`src/session/mod.rs`): `create`, `read_events`, and two others are "Stage 1 — Frozen" (Issue 19 / Decision 5, 6-week deprecation window to change); `list` and `read_header` are "additive-only" — new fields on `SessionInfo` are safe, but the method signature itself is expected to stay stable.

The one-name-at-a-time header read (`backend.read_header(name)` / `backend.read_events(name)`) already returns the full `StateFileHeader` including `template_source_dir` (`src/engine/types.rs:260`). This is what `handle_status` and `handle_init`'s existence pre-check would use for a single-session check — no plumbing gap there.

### Prior art already solving a *related* problem

`src/engine/path_resolution.rs` and `src/engine/scheduler_warning.rs` already implement staleness *detection and reporting* for `template_source_dir`, just in a different context: the batch scheduler's path-resolution step. `SchedulerWarning::StaleTemplateSourceDir { path, machine_id, falling_back_to }` (`scheduler_warning.rs:84-89`) is emitted when "the parent's state-file header records a `template_source_dir`, but that directory does not exist on the current machine (typically following a cross-machine session migration)." This is exactly issue #189's failure mode, already named, already has a JSON wire shape (`{"kind": "stale_template_source_dir", ...}`), and already has a machine-id concept for the "torn-down working tree from a different environment" scenario. It just isn't surfaced anywhere on the `status`/`init`/`session list`/`session cleanup` paths — it only fires inside scheduler ticks. This is the strongest existing building block for all three directions.

### Direction 1 — `koto status <name>` / init "already exists" explicit staleness check

- **Plumbing needed:** none new. `handle_status` (line 4387) already calls `backend.read_events`/reads the header; `handle_init`'s pre-check (line 1682, `backend.exists(name)`) already has the colliding session's name in hand and could call `backend.read_header(name)` (one extra call) to pull `template_source_dir` and `Path::exists()` it.
- **New CLI verb?** No — extends two existing commands' output/error text. No new `SessionCommand` variant, no new flag required (could optionally add one, e.g. `--verbose`, but isn't required to satisfy the issue).
- **Iterate ALL sessions?** No — single-name lookup only, using the header read that already happens on both paths.
- **Sizing: Small.** Realistically a few dozen lines: one `Path::exists()` check plus conditional message text in `handle_status`'s JSON response and in `handle_init`'s two "already exists" error bodies (lines 1685 and 1827, which are duplicated verbatim across `handle_init` and `handle_init_inline` and would both need the added clause). No trait changes, no new struct fields, no stability-tier concerns. This is "cheap, no design decisions needed" — the only decision is wording/JSON-field-naming for the new signal, and `SchedulerWarning::StaleTemplateSourceDir` already sets a naming precedent (`stale_template_source_dir`) worth reusing for consistency.

### Direction 2 — `koto session list` staleness column / `--orphaned` flag

- **Plumbing needed:** `SessionInfo` must grow a field (e.g. `template_source_dir: Option<PathBuf>` and/or a derived `bool`/enum for staleness) so `handle_list` can report it per row without re-reading every header itself. Two viable shapes: (a) add the raw field to `SessionInfo` and let `LocalBackend::list()` stop dropping it (small, additive per the stability doc), or (b) keep `SessionInfo` as-is and have `session::handle_list` do a second pass calling `backend.read_header(id)` per session and `Path::exists()` per header — avoids touching the trait/struct at all but pays an O(n) extra header-read pass (arguably fine at koto's expected session-count scale, but is a departure from `list()`'s current single-directory-scan cost model).
- **New CLI verb?** No new subcommand — extends `SessionCommand::List` (line 426) with an optional `--orphaned` filter flag (clap group), mirroring the exact pattern `Command::Workflows` already uses for its own `--orphaned` flag (lines 203-205, 1191-1200).
- **Iterate ALL sessions?** Yes — this is the direction that actually needs the bulk read. As noted above, `backend.list()` already gives the enumeration; the gap is per-session `template_source_dir` visibility, not enumeration itself.
- **CloudBackend caveat:** for remote-only placeholder rows in `CloudBackend::list()`, `template_source_dir` is unknowable without a per-session download (`sync_pull_state`/HEAD), so an `--orphaned` filter under the cloud backend would either need to skip those rows silently (weakening the signal exactly for the cross-machine scenario the issue is about) or pay a sync round-trip per remote-only session.
- **Sizing: Medium.** Bigger than direction 1 because of the `SessionInfo` shape decision and the `CloudBackend` remote-only gap, but still additive (no trait signature break) and reuses the `Workflows --orphaned` flag idiom already in the codebase. The naming collision with the *existing* `--orphaned` (which means "parent workflow gone," not "template source dir gone") is a real design decision to resolve — see Surprises.

### Direction 3 — `koto session cleanup --orphaned` / `koto gc` sweep

- **Plumbing needed:** Direction 2's per-session staleness determination (SessionInfo change or read-header pass) as an input, PLUS `Command::Session`'s existing `Cleanup` handler (`session::handle_cleanup`, single-name today) extended to a plural/bulk code path, PLUS a safety-gate design borrowed from `koto workspace prune` (`src/cli/workspace.rs`): dry-run, `--yes` confirmation, listing what would be removed before removing it, and a decision about whether staleness alone is sufficient to remove or whether terminal-state / children-safety checks (as `workspace prune` enforces) should also gate a stale-session removal. Unlike `workspace prune`, this sweep has no `--root` — it must walk the *entire* backend, which is new for a destructive verb (existing bulk destructive precedent is root-scoped only).
- **New CLI verb?** Yes in spirit even if reusing the `Cleanup` variant name — a flagged bulk mode (`--orphaned`) on `SessionCommand::Cleanup` needs to change that variant from "one required `name`" to "optional `name` XOR a sweep flag," which is a clap `ArgGroup` restructuring of an existing command, not a pure addition. A standalone `koto gc` top-level command would instead be a brand new `Command` variant, avoiding that restructuring but growing the top-level surface.
- **Iterate ALL sessions?** Yes, same as direction 2, but now for destructive action rather than reporting — raises the stakes on the CloudBackend remote-only gap (silently skipping unsyncable rows in a *cleanup* sweep is a correctness-adjacent decision, not just cosmetic).
- **Sizing: Large.** This one is a genuine architecture/design decision, not a mechanical extension: it needs (a) direction 1+2's detection logic as a dependency, (b) a bulk-mutation safety model analogous to but distinct from `workspace prune`'s root-scoped terminal-state gate, (c) a decision on whether orphaned-but-non-terminal sessions (mid-workflow, template source gone) are safe to delete outright or need the same non-terminal warning `workspace prune` shows, and (d) CLI surface decisions about which existing command to bend vs. adding a new top-level verb.

## Implications

The three directions are **layered, not mutually exclusive**: direction 3 structurally depends on direction 2's "which sessions are stale" determination, which itself is a superset of direction 1's single-session check (both ultimately test `Path::exists()` on a header's `template_source_dir`). None of the three requires new session-state fields — `template_source_dir` is already recorded on every header (`src/engine/types.rs:260`) and already round-trips (tests at `engine/types.rs:1427`); the gap in all cases is purely "nothing reads it back and checks existence outside the batch scheduler's path-resolution step," exactly as the issue states.

Given that, direction 1 dominates as the cheapest, lowest-risk, highest-leverage first slice: it directly fixes the issue's concrete pain point (a confusing generic "already exists" collision error) with no new CLI surface, no trait/struct changes, and reuses the `SchedulerWarning::StaleTemplateSourceDir` naming already established elsewhere in the codebase. Direction 2 is a reasonable proactive-sweeping follow-on once `SessionInfo` is willing to carry the field, but it inherits a real design question (does `--orphaned` collide semantically with the pre-existing `koto workflows --orphaned` flag, which means something different?). Direction 3 is the only one that requires an actual architecture decision (bulk-mutation safety model, CLI surface shape) and should not be scoped as "cheap" — it is the koto-side equivalent of `workspace prune` generalized to no-root-required, which the codebase has not done before for any destructive verb.

## Surprises

1. **The detection logic already exists, just scoped to the scheduler.** `SchedulerWarning::StaleTemplateSourceDir` (`src/engine/scheduler_warning.rs`) is essentially a fully-designed version of what the issue asks for — same field, same "current machine doesn't have this directory" concept, same fallback semantics — but it only fires during a batch scheduler tick's path resolution, never on `status`, `init`, or `session list`. Reusing its `kind` string (`stale_template_source_dir`) and shape for the new surfaces would keep the JSON vocabulary consistent across the codebase instead of inventing a second name for the same concept.
2. **"Orphaned" is already a loaded term in koto's CLI**, meaning "parent workflow no longer exists" (`Command::Workflows { orphaned: bool }`, `koto workflows --orphaned`, extensively documented in `docs/prds/PRD-hierarchical-workflows.md` and `docs/designs/current/DESIGN-hierarchical-workflows.md`). The issue's candidate directions 2 and 3 both propose reusing "orphaned" for a *different* condition (template source directory gone). Naming this the same thing as the existing flag, even in a different subcommand namespace (`session list --orphaned` vs. `workflows --orphaned`), risks operator confusion between two independently-triggerable staleness conditions that a single session could have neither, either, or both of.
3. **`SessionInfo` silently drops `template_source_dir` today** even though `LocalBackend::list()` already parses the full header to build each row — the field is read from disk and then discarded before being placed on the struct, so extending it is a matter of adding one struct field and one line per backend `list()` impl, not a new read path.

## Open Questions

- Should direction 2/3's staleness flag be named to avoid the `workflows --orphaned` collision (e.g., `--stale-source` / `template_source_missing`), and should the wire `kind` reuse `stale_template_source_dir` from `scheduler_warning.rs` for cross-surface consistency? (Design decision, not investigated further here.)
- For `CloudBackend`, is silently treating remote-only/unsynced sessions as "unknown staleness" acceptable for directions 2/3, or does the feature need to force a header sync before reporting/sweeping? Needs input from whoever is tracing the cloud backend's sync model in more depth.
- Does a direction-3 sweep need the same terminal-state safety gate `workspace prune` enforces (non-terminal sessions require `--force`), or is "template source dir gone" itself sufficient justification to remove a session regardless of workflow state? This is the crux of direction 3's sizing and wasn't resolved by this pass.
- Exact CLI shape for direction 3 (bend `SessionCommand::Cleanup` vs. new `Command::Gc` vs. new `WorkspaceCommand` variant) — not decided; three plausible homes were found but none is clearly indicated by existing conventions.

## Summary
Koto already has every piece of plumbing three of these directions need except one: `template_source_dir` is recorded on every session header and even has fully-built staleness-detection logic (`SchedulerWarning::StaleTemplateSourceDir`), but that logic only fires inside the batch scheduler and is dropped from `SessionInfo` before `session list` ever sees it. That makes direction 1 (status/init messaging) a small, mechanical, no-new-verb fix reusing existing header reads, direction 2 a medium change gated on extending `SessionInfo` (and weaker under `CloudBackend`'s remote-only placeholder rows), and direction 3 the only one requiring a genuine architecture decision, since koto has no precedent for a whole-workspace (root-less) destructive sweep — `workspace prune`'s dry-run/confirm safety model is root-scoped only. The biggest open question is whether direction 3 needs `workspace prune`'s terminal-state safety gate or whether staleness alone justifies removal.

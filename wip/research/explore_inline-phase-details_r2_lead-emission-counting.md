# Lead: Can emission counting be recorded without violating R9?

## Findings

### 1. R9 verbatim, and what it actually forbids

R9 (`docs/prds/PRD-koto-next-output-contract.md:128-135`) reads in full:

> **R9. Directive split: summary and details.** Responses include `directive` (short summary, always present on non-terminal shapes) and an optional `details` field (extended instructions). Response behavior:
> - **First visit** to a state: both `directive` and `details` are present...
> - **Subsequent visits** (retries, self-loops, polling): `directive` is present, `details` is absent...
> - **Force-full retrieval**: `koto next --full` forces `details`...
> - **No details defined**: States that don't define extended instructions produce no `details` key...
> - **Visit tracking**: Uses existing JSONL state events. A state's visit count is derived from the event log (counting `Transitioned`, `DirectedTransition`, and `Rewound` events targeting that state). **No new state files or schema changes needed.**

The design doc's rejection (`docs/designs/current/DESIGN-koto-next-output-contract.md:151-153`) is narrower still — it rejects one specific mechanism:

> **Persist visit count alongside events**: Add a running counter to derived state or a separate tracking file. Rejected because it violates PRD R9 ("no new state files or schema changes").

Read literally, R9's prohibition is two things, and *only* two things: (a) **new state files** — a separate tracking file, a counter file, anything beyond the existing per-workflow `.state.jsonl` — and (b) **schema changes** — meaning a bump to `CURRENT_SCHEMA_VERSION`, i.e. a change to the wire format that an older koto build cannot parse. It does not say "no new event types" and does not say "no new fields." The design doc's rejected alternative was specifically "a running counter" as a mutable derived value — the objection is to *persisting a counter*, not to recording an emission as an append-only fact. This distinction is what makes candidates 3–6 below live options rather than re-litigating a settled rejection.

### 2. Cost of a new `EventPayload` variant

`docs/STABILITY.md` (§`EventPayload` additive variants, lines 192-247) states the governing rule directly: **new `EventPayload` variants are additive-only and do not bump `CURRENT_SCHEMA_VERSION`.** The doc comment on the constant itself (`src/engine/types.rs:190-199`) says the same: bump only for "a new *required* event type," a removed required field, or a change to the envelope keys (`seq`, `timestamp`, `type`, `payload`). A new optional variant that older readers can ignore is explicitly not a bump trigger.

Forward compatibility is mechanical, not aspirational: `Event`'s custom `Deserialize` impl (`src/engine/types.rs:1082 ff.`) matches the `type` string against a table of known variants; anything unmatched falls into `EventPayload::Unknown { type_name, raw_payload }` (`src/engine/types.rs:794-799`, catch-all arm at ~1331). `Event`'s custom `Serialize` writes back the original `type_name`/`raw_payload` verbatim, so round-trip is byte-identical even for events an older build doesn't understand (`src/engine/types.rs:1060-1075`). This has already been exercised in production: the doc comment on `ContextRemoved` (`src/engine/types.rs:530-536`) says outright "Additive per `docs/STABILITY.md`, so it does not move `CURRENT_SCHEMA_VERSION` — an older build lands it in `Unknown` and reads the rest of the log unharmed," and STABILITY.md's worked example (lines 235-241) documents that **six** `request.`-prefixed variants shipped together as an additive change with the constant left at 1, backed by a test (`adding_the_request_family_does_not_move_the_schema_version`, `src/engine/types.rs:3373`, asserting `CURRENT_SCHEMA_VERSION == 1`). So: a new `EventPayload` variant costs a match arm in `Event::deserialize`, a `type_name()` string, a doc comment explaining the additive-safety reasoning (house style per the examples above), and a test pinning the schema version — no schema bump, no new file. `src/session/validate.rs` and `src/session/version.rs` are both red herrings for this question: the former validates session-ID string shape, the latter handles cloud-sync conflict resolution — neither touches schema versioning. The actual version gate lives in `parse_header` (`src/engine/persistence.rs:570-580`), which checks `schema_version` once, at the header line, before any event is read — confirming the STABILITY.md claim that the gate is per-file, not per-event, which is exactly why additive events don't need it moved.

### 3. Does an existing event already record "a tick happened here"? — Partial, with a real gap

`GateEvaluated` is appended unconditionally for every non-overridden gate on **every** tick that reaches gate evaluation, whether or not the tick advances — `append_event(&gate_evaluated_payload)` fires at `src/engine/advance.rs:389-390`, before the code even decides whether the state has an `accepts` block or whether gates passed. So for a state **with gates**, a blocked re-tick does leave a footprint: one or more `GateEvaluated` records with the blocked state's name, timestamped after the last entry event.

A predicate along the lines of "count entry events (`Transitioned`/`DirectedTransition`/`Rewound`) targeting X, plus treat any `GateEvaluated` for state X appended after the most recent entry into X as evidence of a prior emission" is thus computable from the existing log for gated states — the information is there.

**But there's a gap the lead's framing anticipated and the code confirms is real.** A state with **no gates at all** that is not yet resolvable — has no `accepts` block satisfied, isn't auto-advanceable, and doesn't match a `skip_if` — falls through gate evaluation entirely (`gates_to_evaluate` is empty, the `if !gates_to_evaluate.is_empty()` block at `src/engine/advance.rs:372` never runs, so no `GateEvaluated` is written) and lands on one of two return paths in `resolve_transition`'s `NeedsEvidence` arm (`src/engine/advance.rs:561-584`):
- If `template_state.accepts.is_some()`: returns `StopReason::EvidenceRequired { failed_gates: None }` — **no event appended at all** (line 562-569).
- If no `accepts` and no failed gates: returns `StopReason::UnresolvableTransition` — also **no event appended** (line 578-583).

This is not a hypothetical corner case — a gateless state that simply expects evidence via `--with-data` (the ordinary, ungated `accepts`-block shape) is exactly this path, and it's likely the *majority* shape for states that carry long `details` blocks (instructional states waiting on agent work, not gate-blocked states). For those states, a blocked re-tick writes **nothing** to the log today. So "count gate_evaluated events since last entry" is a correct predicate only for the gated subset of blocked states; it does not generalize, and any design that leans on it needs either (a) a separate mechanism for the gateless case, or (b) to make gateless blocked ticks start writing something too (which is mechanism 3 below, explicitly).

### 4. The reserved-kind convention (`EvidenceSubmitted` riding a synthetic state)

`src/engine/audit.rs:1-110` documents this pattern precisely, and it was adopted for exactly the reason under discussion here — avoiding new `EventPayload` variants. The module doc (lines 4-9) states: "Decision 6 (DESIGN-koto-request-store) commits to **reusing** `EventPayload::EvidenceSubmitted` rather than adding new `EventPayload` variants for the request-store audit family — **PRD D10 requires zero new variants**." (Note: that's a *different*, stricter constraint — D10, from the request-store PRD — not R9 from the output-contract PRD under discussion here. R9 as quoted in §1 does not itself say "zero new variants"; it says "no new state files or schema changes." Conflating the two would overstate what R9 forbids.)

The mechanics: a reserved `fields.kind` string (e.g. `"ChildDispatched"`, or the `request_store.`-prefixed family) discriminates audit records that ride ordinary `EvidenceSubmitted` events, and — critically for collision-avoidance — some of them are additionally written against a **synthetic state name** rather than a real template state, e.g. `ABANDON_NOTICE_STATE = "request_store.abandon_notice"` (`src/engine/audit.rs:64-74`). The doc comment there is explicit about why: "This is load-bearing, not tidiness. The result synthesizer lifts a summary and payload from the most recent evidence event whose state matches the child's final state, with no kind filter — so an audit record written against the delegate's *actual* state would, on a terminal tick, be promoted as the child's result. **Every reserved audit record uses a synthetic state for exactly this reason.**" The dot in the state name (`request_store.abandon_notice`) is itself part of the safety property — a test (`the_abandon_notice_kind_and_state_are_both_reserved`, `src/engine/audit.rs:367-381`) asserts the pseudo-state "contains a dot," reasoning that a real template state name can't collide with it because template state names presumably can't contain dots (this repo's `derive_visit_counts` machinery keys purely on state-name string equality, so any real state named with a dot would collide — the convention's safety rests on state-naming discipline elsewhere, not on a hard type-level guarantee I can point to in this codebase; worth flagging as an inference).

Applying this to details-emission: a marker `EvidenceSubmitted { state: <real-state-or-synthetic>, fields: { "kind": "koto.details_emitted" } }` (or similar) would add **zero** new `EventPayload` variants and **zero** schema changes — it's the same enum variant already in the schema. It would need its own reserved-kind entry (extending `RESERVED_KINDS` or the `request_store.`-style prefix scheme, or a new prefix scoped to this feature) so template authors can't collide with it via `--with-data`. Two design choices follow directly from the `ABANDON_NOTICE_STATE` precedent: (1) should the marker ride the *real* state name (simpler, but must be excluded from any "most recent evidence for this state" projection the way `ABANDON_NOTICE_STATE`'s synthetic-state trick sidesteps), or (2) a synthetic per-state name (e.g. `"<state>.details_emitted"`, mirroring `request_store.respawn`'s dotted-child-of-state pattern) — more code but structurally immune to the promotion hazard the doc comment warns about.

On issue #161 (machine-readable reserved-kind catalog): I found no reference to it anywhere in this repo's committed docs or code (`grep` across `docs/` and `src/` for "161" near "reserved"/"catalog" turned up nothing). I cannot confirm its content or status from within this repo; treating it as a live open item is an inference from the task brief, not something I verified.

### 5. Is a non-advancing `koto next` already a writer? — Yes, confirmed for the gated case

Not new. `src/engine/advance.rs:389-390` calls `append_event(&gate_evaluated_payload)` for every non-overridden gate on a tick that reaches gate evaluation — this fires *before* the code decides whether to return `GateBlocked` (line 429-438) or fall through. So any state with at least one gate already writes to the session log on a blocked, non-advancing tick, today, in production. The objection "recording an emission would make `koto next` a writer when it currently isn't" is empirically false for that subset of states — the precedent already exists and is exercised by tests (e.g. `src/engine/advance.rs:3538-3545` asserts `GateEvaluated` is emitted for a failing gate).

The caveat from §3 carries over directly: for **gateless** blocked states, `koto next` today performs *zero* writes on a blocked tick (`EvidenceRequired`/`UnresolvableTransition` returns at `src/engine/advance.rs:562-569` and `578-583` never call `append_event`). So a details-emission marker that must cover *all* blocked-tick shapes — not just gated ones — would make `koto next` a writer on ticks that are writers today (gated) and on ticks that currently aren't (gateless). That's a real, if modest, behavior change: every blocked `koto next` call would touch disk, where today only a fraction do. Whether that's acceptable is a design question, not a correctness one — the mechanism is sound either way.

### 6. Header rewritability — the header is NOT append-only; it's rewritten in place

This resolves the lead's open question definitively, and the answer is the opposite of "append-only." `append_header` / `append_header_line` (`src/engine/persistence.rs:80-116`) opens the file with `OpenOptions::new().create(true).write(true).truncate(false)` — **not** `.append(true)`. Without the append flag, the write cursor starts at offset 0 on every call, so a second invocation against an existing file **overwrites the header line in place, byte for byte**, rather than appending a second header line. This is confirmed by the file's own test, `append_header_subsequent_write_is_well_formed` (`src/engine/persistence.rs:2463-2480`), whose comment states it outright: "The second call rewrites at offset 0 (the file was opened with `.write(true).truncate(false)`, so the cursor starts at offset 0 and the second header overwrites the first byte for byte)."

This is exercised in production, not just theoretically possible: `respawn_generation` (`src/engine/types.rs:322-340`) is mutated on an in-memory `StateFileHeader` and written back via `append_header` at respawn time (`src/engine/respawn.rs` constructs/updates `header.respawn_generation` and the header-write call sites in `src/session/local.rs:175-177` / `src/session/cloud.rs:712-717` route through the same `append_header_line`). So header fields *are* a real, already-used-for-similar-purposes mechanism for storing small pieces of mutable per-workflow state, updated in place, with no new file and no schema bump (both `respawn_generation` and `dispatch_epoch` are additive `Option<T>`/default fields per the `StateFileHeader` additive-evolution rules in `docs/STABILITY.md:140-189`).

Two things worth flagging about this mechanism specifically for details-emission tracking: first, it stores *global* per-workflow scalars (a generation counter), not naturally a per-state map — tracking "which states have had details emitted" would need something like a `Vec<String>` or `BTreeSet<String>` of state names on the header, which is a new field but not a new file/schema-bump under the same additive rules. Second, and more subtly, the header is rewritten wholesale on each call — there's no compare-and-swap or partial-update primitive here, so a concurrent-write hazard exists if two `koto next` invocations against the same session raced to update the header (the design doc and PRD's concurrency requirements, if any — not read in this pass — would need to weigh in on whether that's already a concern for `respawn_generation`/`dispatch_epoch` and whether a details-set field inherits the same protection).

### 7. Would suppressing on `advanced == false` instead of visit count fix the blocked-re-tick case? — No; it breaks the *true* first-visit case

The engine already computes `advanced` (`src/cli/mod.rs:3978`, `let advanced = advance_result.advanced;`) per R2/R3: "true if at least one state transition occurred during this invocation of `koto next`." The idea: suppress `details` when `advanced == false` (nothing moved this tick, so this must be a retry) and show it when `advanced == true` (a transition landed us here, so it's fresh).

This cleanly explains the *bug case* — a blocked, non-advancing `koto next` has `advanced == false`, so it would correctly suppress `details` on the second and later blocked ticks. But it breaks the **canonical first-visit case** the whole R9 feature exists to serve: the very first `koto next` call against a state that was entered via a *previous* invocation (or via `koto init` landing directly on an accepting initial state, with no auto-advance) also has `advanced == false` for *that specific call* — the transition into the state happened on an earlier invocation (or none at all, for the initial state), not on the call that's now asking "should I show details." Concretely:
- `koto init` creates a workflow sitting in its initial state with no `Transitioned`/`DirectedTransition`/`Rewound` event at all (entry is via `WorkflowInitialized`, which `derive_visit_counts` doesn't count — confirmed by the `count <= 1` check at `src/cli/mod.rs:4010`, which exists specifically to treat count `0` the same as count `1`). The first `koto next` call against that state performs no transition (nothing to auto-advance through, evidence pending) — `advanced` is `false` — yet this is unambiguously the first visit and R9 requires `details` to ship.
- A state reached at the tail of a multi-hop auto-advance chain *within* the same `koto next` call has `advanced == true` for that first visit — correctly shows details under either scheme.
- A blocked retry on that same state has `advanced == false` — correctly suppressed under either scheme, and incorrectly conflated with the case above.

So `advanced == false` does not distinguish "first tick, nothing to do but report" from "Nth blocked retry" — both are `false`, and the feature's most basic case (init into an evidence-gathering initial state) falls on the wrong side. `advanced == true && count > 1` (loop-back re-entry after a real transition) vs. `advanced == false && count > 1` (blocked retry) is a real, valid split for states *already visited at least once*, but it says nothing about first-vs-not, which is what R9 actually needs discriminated. The existing `count <= 1` predicate already absorbs the "count is 0 because entry wasn't a counted event type" edge case that trips up the naive `advanced`-based scheme; replacing it with `advanced` alone would just relocate that same edge case into a harder-to-see bug rather than removing complexity. `advanced` is a legitimate secondary signal (e.g., to detect true loop-backs) but not a standalone replacement for tracking emission history.

## Mechanism comparison

| Mechanism | New `EventPayload` variant? | Schema bump? | New file? | Writes on gateless blocked tick? | Covers all blocked-tick shapes? | Notes |
|---|---|---|---|---|---|---|
| New dedicated `EventPayload` variant (e.g. `DetailsEmitted`) | Yes (additive) | No (per §2 / STABILITY.md) | No | Would need to (new write on every blocked tick) | Yes, by construction | Cleanest semantics; costs a match arm, `type_name()`, doc comment, schema-version-pin test — precedented 6x by the `request.` family and `ContextRemoved`/`ContextAdded` |
| Synthetic-state `EvidenceSubmitted` w/ reserved kind (audit.rs convention) | No | No | No | Would need to (new write on every blocked tick) | Yes, if adopted uniformly | Reuses existing variant + existing reserved-kind infrastructure; needs a promotion-hazard-safe synthetic state name per the `ABANDON_NOTICE_STATE` precedent, and a new reserved-kind entry |
| Count existing `GateEvaluated` since last entry | No | No | No | No — gateless blocked ticks write nothing today, so this predicate is blind to them | **No** — confirmed gap for gateless `accepts`-only states | Free (no new writes) for gated states, but silently wrong/incomplete for the (likely common) gateless-evidence-required shape |
| `StateFileHeader` field (e.g. `details_emitted: Option<BTreeSet<String>>`) | No | No | No | Would need to (header rewrite on every blocked tick) | Yes | Header confirmed rewritable in place (§6), precedented by `respawn_generation`; needs whole-header-rewrite concurrency consideration; awkward fit for a growing per-state set vs. today's scalar/counter fields |
| `advanced`-flag-based suppression (no new recording) | No | No | No | N/A — no new write at all | **No** — breaks the true first-visit-via-init case | Zero implementation cost but incorrect; conflates "nothing to do but report" with "blocked retry," both `advanced == false` |

## Implications

- R9's actual text is narrower than "no new event types" — it bans new *files* and *schema (version) changes*, not new enum variants or new header fields, provided they're additive per the rules STABILITY.md already codifies and the crate has already exercised repeatedly (six `request.` variants, `ContextAdded`/`ContextRemoved`, `respawn_generation`, `dispatch_epoch`). The design doc's rejection targeted a *specific* mechanism (a mutable persisted counter/tracking file), not the whole space of "record something new."
- Any fix that only counts `GateEvaluated` events understates coverage: gateless blocked states (an ordinary `accepts`-only state awaiting evidence) leave no trace on a blocked retick today, so that predicate alone reproduces the original bug for a different — and probably larger — subset of states.
- The header-mutation path is real and precedented, but it's a scalar-oriented mechanism (`respawn_generation`, `dispatch_epoch`) being asked to hold a growing per-state set; that's a bigger shape change to `StateFileHeader` than the single-`u32` fields it's held so far, even though it stays within the additive-field rules.
- `advanced` cannot substitute for visit tracking without reproducing the exact "count 0 needs special-casing" complexity the current design already carries via `count <= 1` — it just moves the special case somewhere less visible.

## Surprises

- The header is explicitly **not** append-only — `append_header_line` opens with `write(true).truncate(false)` (no `.append(true)`), so repeated calls overwrite the header line in place at offset 0. This contradicts a natural assumption about a "JSONL log" and is worth calling out because it changes what's mechanically possible for header-based approaches (they're not immutable-once-written; they're update-in-place, single-writer, whole-line-rewrite).
- The gateless-blocked-tick write gap (§3/§5) is a bigger deal than it first sounds: it means "does a non-advancing `koto next` already write to the log" doesn't have one answer — it's "yes, always, for gated states; no, never, for gateless `accepts`-only states." Any mechanism-comparison that doesn't split on this will overstate what's free.
- `docs/STABILITY.md` §`EventPayload` additive variants effectively pre-answers most of question 2 in prose, including a named worked example (`request.` family, six variants, one commit) and a regression test asserting the schema constant didn't move. This reads as intentional prior art specifically for "can we add an event without triggering R9-style objections," not something this exploration had to derive from first principles.
- `src/engine/audit.rs`'s module doc cites "PRD D10 requires zero new variants" as the reason the reserved-kind convention exists — that's a *different, stricter* constraint than R9. Conflating the two would make R9 look like it forbids new variants when its own text (§1) does not say that.

## Open Questions

- Does the downstream PRD/design intend the details-emission marker to be scoped per-workflow (a header field or a `set` accumulated in evidence) or per-tick (an event emitted once per blocked tick, dedupable by consumers)? The mechanisms above split along that line and it isn't settled by anything read in this pass.
- If a new `EvidenceSubmitted`-riding reserved kind is chosen, does it need a synthetic state name (à la `ABANDON_NOTICE_STATE`) to avoid being promoted as "the state's evidence" by whatever code (if any) in this feature's path does a most-recent-evidence-for-state lookup? I did not find such a lookup specific to `details`, but `derive_visit_counts` and any future emission-count derivation function should be checked for the same hazard the `audit.rs` doc comment warns about.
- Is issue #161 (machine-readable reserved-kind catalog) actually open/relevant, and if so does it define a registration mechanism a details-emission kind would need to plug into? Not found in this repo's committed state — needs an out-of-band check (GitHub) if it matters to the decision.
- Concurrency: does anything protect `StateFileHeader` rewrites from a lost-update race between two `koto next` invocations on the same session today (for `respawn_generation`/`dispatch_epoch`), and would a new header-based emission-tracking field inherit or need the same protection?

## Summary

R9 forbids new state files and schema-version bumps, not new event variants or new additive header fields — both of the latter are already precedented in this codebase (six `request.`-family `EventPayload` variants and header fields like `respawn_generation`, all added without moving `CURRENT_SCHEMA_VERSION`), and the header itself is confirmed rewritable in place (not append-only), giving at least three R9-compliant candidate mechanisms: a new `EventPayload` variant, a synthetic-state `EvidenceSubmitted` riding the existing `audit.rs` reserved-kind convention, or a new `StateFileHeader` field. Counting existing `GateEvaluated` events is free but incomplete: gateless blocked states (ordinary `accepts`-only states awaiting evidence) write nothing on a blocked retick today, so that predicate silently fails to cover what is likely the more common blocked shape. Suppressing on the `advanced` flag instead of any recording is the cheapest option but is incorrect on its own — it conflates the true first-visit-via-`koto init` case (`advanced == false`) with a blocked retry (also `advanced == false`), breaking the feature's core scenario.

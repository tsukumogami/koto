# Completeness Review

## Verdict: FAIL

R1-R24 all have AC coverage and the brief's scope boundary and three open framing questions are honored, but two user-visible scenarios central to this PRD's own motivating narrative — batch/child sessions under anchoring, and the second (lock-based) nested-`koto` deadlock — are left completely unaddressed.

## Issues Found

1. **Anchoring (R10-R15) never addresses batch/child sessions**, even though the Problem Statement's own headline anecdote — "twelve child workflows once got dispatched against a branch nobody had created" — is a child-workflow scenario, and koto ships a real `koto session start --parent` / batch fan-out mechanism. No requirement states whether a child session gets its own anchor at its own creation, inherits the parent's anchor, or is exempt. Fix: add a requirement (even one left open on mechanism, like R10-R14 already are) stating that a child session's anchor obligation is defined — inherited or independently recorded — rather than silent on the question.

2. **A second, independent nested-`koto` deadlock is undocumented.** Phase 2 research (output-failure, Lead A) found that a `koto` subprocess invoked from inside a gate or `default_action` command deadlocks against the outer `koto next`'s session/workspace lock regardless of output volume — a distinct hazard from the pipe-buffer deadlock R16 fixes ("nesting koto inside koto-executed commands is unsafe on two independent axes, not just this one"). Nothing in the PRD's requirements, Known Limitations, or authoring-guidance requirements (R19-R21) mentions this. An implementer or author could reasonably believe R16/R18 close the nested-koto hazard entirely; they close only one of two. Fix: add a Known Limitation (or fold into R19/R20's authoring guidance) stating that nesting a `koto` call inside a gate/action command is unsafe independent of output size.

3. **No rule for two different states declaring the same R1 output name.** R4 specifies what happens when the *same* producing state is re-entered (replace, not accumulate) but says nothing about two *different* states each declaring the same output name — a plausible authoring mistake once output routing exists as a namespace. Fix: extend R4 (or add an R4a) to state the obligation for cross-state name collision, even if the design chooses the mechanism.

4. **No requirement covers a later state referencing an output name no preceding state produces** (e.g., a typo). The existing `{{VAR}}` mechanism has compile-time checking against a declared `variables:` block; nothing in R1-R3 requires an analogous check — or even states what currently-undefined behavior (silent no-op, compile error, runtime error) is acceptable — for a reference to a name nothing produced. Fix: add a requirement that this case is defined, documented, and visible, mirroring R3's treatment of undeliverable output.

5. **R5/R7's "exits non-zero" wording doesn't clearly cover spawn failure or timeout**, both of which Story 2 explicitly promises are covered ("a tool that isn't installed," which is a spawn failure, not a non-zero OS exit code). Today's code represents both as `exit_code: -1`, an internal convention rather than a real exit status. An implementer reading R5/R7 literally could treat spawn failure/timeout as outside the failure path's guarantee. Fix: broaden R5/R7's language to explicitly include "the command could not be started or timed out," not just "exits non-zero."

6. **R20 lists six things authoring documentation must cover, but only two have explicit AC coverage.** R20's text requires documentation of "what the field accepts, how the command is invoked, what directory it runs in, what happens to its output, what happens when it fails, and how it interacts with the state's gates." The ACs test only "what directory" and "what happens to output on success/failure" directly; "how it interacts with the state's gates" — which matters precisely because R5/R6/D5's action-exit-vs-gate interaction is subtle — has no dedicated AC. Fix: add an AC verifying the gate-interaction documentation exists and is accurate.

## Suggested Improvements

1. **Clarify R5's relationship to D5 explicitly in the requirement text, not just the decision record.** R5 plus its AC ("a state with a default_action that exits non-zero and one or more gates does not transition") establishes the action's own exit code as an independent, additive halt condition alongside gate evaluation. D5 frames this as not "redefining what a non-zero exit means throughout the engine," which is consistent once read as "gates' own exit-code semantics are untouched" rather than "the action's exit code doesn't matter." The two are compatible but the compatibility isn't obvious on a first read — a one-sentence clarification in R5 or D5 would remove the ambiguity for the design author.
2. **State whether the alternate "hard-refuse every legacy session" persona (a fleet operator auditing before resuming) is deliberately unserved by R13**, the way D2 reasons through the trade-off for individual developers. D2 is well-argued for the single-developer case but doesn't acknowledge the fleet-operator alternative that phase 2 anchoring research flagged as a live, distinct ask.

## Summary

The PRD's requirements-to-AC mapping is strong — every R1 through R24 has at least one acceptance criterion, the brief's out-of-scope items (template integrity, event-log bounds, `requires_confirmation` renaming, runtime containment) are correctly kept out, and all three of the brief's open framing questions are closed with reasoned decisions (D1-D3). The gaps are concentrated in two places phase 2 research surfaced but the PRD didn't carry forward: batch/child sessions are never mentioned under anchoring despite being the PRD's own motivating scenario, and a second, lock-based nested-`koto` deadlock (distinct from the pipe-buffer one R16 fixes) goes completely unaddressed. Smaller gaps exist around output-name collisions/typos and under-specified AC coverage for R20's gate-interaction documentation requirement.

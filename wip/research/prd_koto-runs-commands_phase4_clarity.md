# Clarity Review

## Verdict: PASS
This PRD is unusually precise (code-cited problem statement, explicit "mechanism left to design" callouts, byte-identical/binary phrasing in most ACs), and the handful of issues found are wording-precision gaps in acceptance-criteria and documentation-standard language rather than requirement forks that would produce two different implementations.

## Ambiguities Found

1. **R15** (Requirements > Execution anchoring; repeated verbatim in Known Limitations): "It guarantees the directory a workflow starts in." -> This is grammatically ambiguous between (a) "the anchor is a one-time thing established at the workflow's/session's start" (checked once, at creation) and (b) "each command execution starts in the anchored directory, re-verified on every `koto next` tick" (the behavior R11 actually mandates: every invocation from a non-satisfying directory refuses, not just the first). Since R15 exists specifically so koto's *published wording* doesn't overclaim, and this exact phrase is the kind of sentence likely to get copied verbatim into docs/error messages, the PRD should resolve this ambiguity in its own canonical language rather than let a documentation author pick reading (a) and understate the guarantee. -> Suggested clarification: "It guarantees that every `koto next` invocation for a session runs from the directory recorded when that session was created, re-checked on each tick — not merely at session start."

2. **R20 / AC** ("A template author can write a working `default_action`, including its output name and its fallback prose, using only the published documentation (R20)."): "using only the published documentation" and R20's own "sufficient to write one correctly without reading koto's source or test suite" -> These are subjective pass/fail bars: no defined test procedure (who is the author, how many attempts are allowed, does a clarifying question to a teammate disqualify the run, what exactly counts as "correctly" beyond "the thing R1-R9 describe works"). Two reviewers could watch the same documentation walkthrough and disagree on whether it passed. -> Suggested clarification: script the exercise concretely — e.g., "an author with no prior exposure to koto's source, given only the shipped docs, produces a `default_action` (with output name and fallback prose) that passes a stated integration test on the first attempt, with no source or test-suite lookups."

3. **R2** (Functional: output routing): "This holds when the engine auto-advances through several states within a single `koto next` call — the producing state and the state that reads the value are frequently not the same tick, and the same-tick case is the one output routing exists for." -> "Tick" is never formally defined anywhere in the PRD (it's used loosely elsewhere too: R13's "first tick," Story 3's "ticks the same session"), and the sentence's own structure (leading with the *uncommon* case before naming the *primary* case) invites a reader to skim past which scenario R2 is actually optimizing for. Getting this backward changes which code path an implementer treats as primary versus edge case, on a requirement D4 flags as carrying "a same-tick staleness trap" for at least one of the costed mechanisms. -> Suggested clarification: define "tick" once (e.g., "tick = one `koto next` invocation") and lead the sentence with the requirement: "R2 must hold even when the producing and consuming states are reached within the same `koto next` invocation via auto-advance — this same-tick case, not the more common cross-invocation case, is the one output routing exists to solve."

4. **AC, Shared-path defects**: "A gate command emitting several megabytes completes, is evaluated on its real exit status, and is not reported as a timeout (R16)." / "A `default_action` emitting several megabytes completes and its output is delivered (R16)." -> "Several megabytes" is not a reproducible, binary test threshold — it isn't tied to the actual trigger condition R16 names ("exceeds the operating system's pipe buffer," typically far smaller, e.g. 64KB on Linux/macOS). A reviewer checking this AC has no stated number to verify against, and different test-writers could pick different sizes. -> Suggested clarification: state the AC in terms of the actual trigger ("output exceeding the platform's pipe buffer size") or give a concrete floor (e.g., "at least 10MB, and separately a case just over the platform pipe-buffer size").

## Suggested Improvements

1. **Add a one-line glossary entry for "tick."** It's load-bearing terminology (R2, R13, Story 3, D2) used only informally; a formal definition removes ambiguity #3 and tightens every requirement that leans on it.
2. **Tie the R16/R17 shared-path ACs to the actual pipe-buffer trigger instead of an approximate size.** Removes ambiguity #4 and makes the AC directly traceable to the mechanism named in R16's own text.
3. **Consider restating R15's guarantee using R11's own "every invocation" language** rather than "starts in," so the requirement that's supposed to prevent overclaiming isn't itself open to an understated reading once it reaches shipped documentation.

## Summary
The PRD is tightly specified overall — problem statement and requirements are backed by file:line citations, most acceptance criteria are binary ("byte-identical," "exactly one notice," "textually different from the wrong-tree refusal"), and the PRD is careful to label genuinely open mechanism questions as such (D4's four costed output-routing approaches, the anchor equality-vs-containment question) rather than leaving them ambiguous by omission. The four issues found are narrower: R15's "starts in" phrasing is worth fixing because it's the exact sentence meant to keep koto's anchoring story from being overclaimed or misread, and the other three are acceptance-criteria precision gaps (a subjective docs-sufficiency test, an underdefined term, and an unquantified test size) rather than requirements that would let two developers build materially different features.

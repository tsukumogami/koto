# Lead: What do koto's existing output-contract and stability commitments require, and what would adding a per-state "details" field break?

## Findings

### 0. The central finding: this feature is already built, and issue #90 already has an audit trail on the codebase's actual state

Before getting to the contract/compat analysis, the most load-bearing fact: **the `details` field, its first-visit/subsequent-visit behavior, and a `--full` override already exist in the codebase**, landed via PR #109 ("feat(cli): redesign koto next output contract", `517ee83`, 2026-03-30) as part of `docs/prds/PRD-koto-next-output-contract.md` requirement R9. Issue #90 itself has two review comments (2026-06-07 and post-0.11.4/2026-08-05) that audited the shipped code against #90's acceptance criteria line by line. Status as of the most recent comment:

- AC1 (template `details` field) — done. `TemplateState.details` at `src/template/types.rs:57`, populated by the `<!-- details -->` marker splitter in `src/template/compile.rs:622-681`.
- AC2 (`koto next` includes `details` inline) — done. `src/cli/next.rs:50-114`.
- AC3 (omit on subsequent visits) — **mostly done, one real gap**: visit-count gating is wired in the auto-advance path (`src/cli/mod.rs:3999-4015`, using `derive_visit_counts` from `src/engine/persistence.rs:981`), and the second review comment's measured table confirms omission works correctly on genuine re-entries (2nd/3rd visit to a state). The remaining gap: a `koto next` call that evaluates gates, fails them, and does **not** transition (a gate-blocked re-tick) still resends `details`, because `dispatch_next` in `src/cli/next.rs:50` gates inclusion only on "does this state have details" with no visit-count check at all — the visit-count gating lives only in the `cli/mod.rs` auto-advance-loop tail, not in the pure dispatcher. A long-running loop where an agent re-ticks a gate-blocked state many times before it clears will re-send `details` on every blocked tick.
- AC4 (`koto phase-info <workflow>` command) — **not done**. No such subcommand exists (confirmed: no `phase-info` or `phase_info` string anywhere in `src/cli/mod.rs`, and the issue comment confirms `koto phase-info` returns "unrecognized subcommand" against 0.11.4). `koto status <name>` exists but returns only current state and template hash, not details.
- AC5 (workflows without `details` behave identically) — done. `template_state.details.is_empty()` → `None`, omitted from JSON via the `Option<String>` + custom serializer in `src/cli/next_types.rs`.
- AC6 (visit tracking uses existing JSONL, no new state files) — done. `derive_visit_counts` (`src/engine/persistence.rs:981`) derives counts from `Transitioned`/`DirectedTransition`/`Rewound` events; no new persisted files.

Given this, an exploration of #90 is not "should we add a details field" — it's "close the two remaining, narrow gaps": (1) gate the pure dispatcher's `details` inclusion on visit/emission count rather than state-has-details, and (2) decide whether the escape hatch should be a new `koto phase-info` subcommand (as #90 and the PRD both name it) versus documenting `koto next --full` as sufficient (which already exists and already does the job, per the second issue comment, at the cost of also ticking the machine). This reframes the scope of the whole exploration and should be surfaced to the team immediately — the "premise", "first-visit", "phase-info", "alternatives" leads are all implicitly investigating a mechanism that's 90% shipped.

### 1. Output contract (PRD-koto-next-output-contract.md, PRD-unified-koto-next.md)

Both PRDs are `status: Done`. The output-contract PRD's R9 is the literal spec for #90's mechanism (`docs/prds/PRD-koto-next-output-contract.md:128-135`):

- First visit: both `directive` and `details` present.
- Subsequent visits: `directive` present, `details` omitted (not null — key absent).
- `koto next --full` forces `details` regardless of visit count (already implemented, confirmed by issue comment 2 against 0.11.4).
- No-details states produce no `details` key — behavior is unchanged for existing templates.
- Visit tracking derives from existing JSONL events (`Transitioned`, `DirectedTransition`, `Rewound`) — no new state files or schema changes needed (R9's last bullet is literally AC6 from #90).

Non-goal callouts directly relevant: R9 explicitly punts the *source format* question ("markdown separator, YAML field, external file") to a downstream design doc (Decision D6) — and that downstream decision was already made: the shipped format is the `<!-- details -->` HTML-comment marker inside the markdown body (`src/template/compile.rs:622-681`), not YAML. Any exploration proposing an alternate template syntax (e.g., issue #90's own example shows a YAML `details:` key under a state) would be reopening a settled design decision, not extending unsettled ground — #90's "Proposed Template Format" section (YAML) does not match what's implemented (markdown separator). This is a real discrepancy worth flagging to the user: **the issue's proposed template format doesn't match what shipped**, and it isn't in scope to change the format now.

R11 (backward compatibility) explicitly classifies "adding the optional `details` field" as additive/non-breaking, alongside `blocking_conditions` and new error codes. This is already-spent budget, already shipped — not a decision left to make.

R13 documentation requirements target `AGENTS.md` and `.cursor/rules/koto.mdc`. **`AGENTS.md` does not exist in this repo** (confirmed: no file by that name outside `wip/`). Only `.cursor/rules/koto.mdc` exists, at `plugins/koto-skills/.cursor/rules/koto.mdc` (inside the koto-skills plugin, not repo root). The caller-facing documentation role R13 assigns to AGENTS.md has apparently been superseded by the koto-user skill's `references/response-shapes.md`, which **already documents the details/--full behavior in full**: presence table, visit-count rule, `--full` override, absence on terminal responses, and a caller instruction to check presence before reading (`plugins/koto-skills/skills/koto-user/references/response-shapes.md:16,37,55,88,148,398,527`). So the doc requirement from R9/R13 is already satisfied for the `koto-user` skill; it is not satisfied for a `phase-info` subcommand, which doesn't exist yet to document.

R14 (koto-author skill teaches the details split) also appears already substantially done: `plugins/koto-skills/skills/koto-author/references/template-format.md` and `plugins/koto-skills/skills/koto-author/SKILL.md` both reference `details` already (confirmed by grep). I did not verify line-by-line whether every R14 sub-bullet (dogfooding on koto-author's own template, example templates) is satisfied — that's a narrower open question than "is the feature built," but it's second-order compared to the AC3/AC4 gaps above.

PRD-unified-koto-next.md (source PRD for `koto next` itself, R1-R22) has no `details` concept at all — it predates R9 and is the foundational contract for auto-advancement, evidence, gates, and `--to`. Nothing in it constrains a `details` field or a `phase-info` command; it's consistent scaffolding, not a blocker.

### 2. Stability guarantees (docs/STABILITY.md, koto-stability-tests/)

`docs/STABILITY.md` governs exactly two surfaces, both **narrower than the `koto next` JSON response**:

1. `CURRENT_SCHEMA_VERSION` (currently `1`, unchanged since introduction) and the JSONL wire-format additive-evolution rules for `StateFileHeader` and `EventPayload` — this is the **on-disk session log format**, not the `koto next` CLI response shape.
2. Four frozen `SessionBackend` trait methods (`list`, `read_events`, `create`, `init_state_file`) that external consumer bunki BK2 imports via `koto::engine::types::*`.

Neither section says anything about `koto next`'s JSON output contract or `TemplateState.details`. `NextResponse`/`TemplateState` are not part of the frozen surface enumerated in `koto-stability-tests/src/lib.rs` (confirmed: the crate only imports `StateFileHeader`, `Event`, `EventPayload`, `SpawnEntrySnapshot`, `ChildSnapshot`, `AssignmentClaim`, `derive_state_from_log`, `CURRENT_SCHEMA_VERSION`, `Error`, and the four `SessionBackend` methods — no `NextResponse`, no `TemplateState`). So **there is no golden-output/snapshot test suite in `koto-stability-tests/` that a `details` field or a `phase-info` command would break** — that crate is a compile-check fixture for the session-log/backend surface, not the CLI JSON contract. The output-contract stability lives instead in the ordinary integration/unit tests under `tests/` and `src/cli/next.rs`'s own `#[cfg(test)]` module (e.g. `derive_visit_counts` has dedicated tests at `src/engine/persistence.rs:2224-2425` already covering empty, single, multi-visit, directed-transition, rewound, and mixed-event-type cases — a `phase-info` command implementation should add a parallel case for "gate-blocked re-tick doesn't advance visit count," matching the AC3 gap above).

### 3. Template hash locking (src/cache.rs, not src/template/compile.rs)

The SHA-256 hash isn't computed in `compile.rs` — it's computed in `src/cache.rs::sha256_hex`, over the **serialized compiled JSON** (`serde_json::to_string_pretty(&compiled)` then hashed), not the source markdown (`src/cache.rs:41-56`, doc comment at lines 29-40 confirms: "The cache key is SHA256 of the compiled JSON"). Implication for the details feature: **any change to a template's `details` content changes the compiled JSON, which changes the hash, which changes the cache filename and the `template_hash` recorded in the session's `StateFileHeader`.** This is already true today for `directive` text and every other compiled field — `details` doesn't introduce new hash-locking behavior, it's just one more field inside the hashed blob. A template author editing an existing template's `details` (or adding one) produces a new hash; a session initialized against the old hash keeps running against the old compiled artifact (content-addressed cache, `cache_path.exists()` short-circuits at `src/cache.rs:54-56`), so in-flight sessions are unaffected by upstream template edits — this is the existing content-addressing behavior, not something a `details` field changes or needs a migration path for. No new compatibility work is implied here; this line of the lead's question resolves to "no new risk," not "needs a plan."

### 4. JSONL schema version (src/engine/types.rs, not src/session/version.rs)

`CURRENT_SCHEMA_VERSION` lives at `src/engine/types.rs:199` (`pub const CURRENT_SCHEMA_VERSION: u32 = 1`), not in `src/session/version.rs` as the lead assumed — `session/version.rs` is unrelated: it implements cloud-sync three-way conflict detection (`SessionVersion`, `check_sync`, `resolved_version`) for a completely different concern (multi-machine sync versioning), not the wire-format schema version. The constant has never been bumped (pinned at 1 since introduction, asserted by tests at `src/engine/types.rs:3378` and `koto-stability-tests/src/lib.rs:174`). `docs/STABILITY.md`'s bump protocol (summarized above) is the process: additive changes never bump it; only breaking wire-format changes do, and those require a 6-week deprecation window plus a migration tool. `details` on `TemplateState`/`NextResponse` is not part of the JSONL wire format at all (it's derived from the compiled template + response serialization, not a `StateFileHeader` or `EventPayload` field), so it's outside this protocol's scope entirely — a `phase-info` command reading the same JSONL events via `derive_visit_counts` doesn't touch schema version either.

### 5. `workflows_surface` contract (src/workflows_surface/contract.rs, project.rs)

This is the `koto-<uuid>.json` file koto writes for Claude Code's native `/workflows` UI — a completely separate contract from `koto next`'s JSON response, versioned independently via `CONTRACT_VERSION` (currently `2`, `src/workflows_surface/contract.rs:23`). It already has a `Phase.detail` field (subtitle line for a phase, e.g. "gate build: PASS") and a `ProgressNode::WorkflowAgent.prompt_preview`/`result_preview` — but these are UI-rendering strings for a *different* audience (a human looking at the Claude Code workflows screen), not the same thing as the caller-facing `details` field on `koto next` responses. There is no shape-fixture test that pins the JSON keys against snapshot bytes beyond the in-file `#[cfg(test)]` assertions (`contract_version_is_two`, `minimal_shape_omits_phase_fields`, etc., `src/workflows_surface/contract.rs:204-363|`) — nothing that would specifically break from a `koto next` `details`/`phase-info` change, since `workflows_surface` and `cli::next`/`next_types` are separate modules with no shared serialization code. A `phase-info` command would **not** need to appear in this contract; it's an entirely separate on-disk artifact serving Claude Code's UI, not the CLI's stdout JSON.

### 6. Compiler behavior for absent `details` (already covered above, restated)

`compile.rs`'s `split_directive_details` (`src/template/compile.rs:673-681`) returns `(directive, String::new())` when no `<!-- details -->` marker is present. `TemplateState.details` is then `""`, and both `dispatch_next` (`next.rs:50`) and the auto-advance tail (`cli/mod.rs:4001`) check `.is_empty()` to decide `None` vs `Some`. No warning or error is emitted for missing `details` — it's silently treated as "no details," exactly matching AC5/R9's "no `details` key" requirement. Tests directly cover this: `no_details_marker_produces_empty_details` (`src/template/compile.rs:1280`), `compiled_json_round_trips_with_details` verifies presence/absence at the JSON level (`src/template/compile.rs:1337-1380`).

### 7. Downstream skills (koto-author, koto-user)

Per koto's CLAUDE.md convention, source changes in `src/cli/`, `src/engine/`, `src/template/` require assessing both skills. Given the feature is 90% shipped, the assessment splits into "already updated" vs. "would need updating for the AC3/AC4 gap fix":

- **koto-user** (`plugins/koto-skills/skills/koto-user/`): `references/response-shapes.md` already documents `details` presence rules, the `--full` override, and per-action-type presence (table at line 16). `references/command-reference.md` and `references/error-handling.md` also reference `details` (confirmed by grep, not read line-by-line). **What would need updating** if AC3's gate-blocked-retry gap is fixed: none of the documented behavior changes (the documented contract — "present on first visit, absent on retries" — is already what response-shapes.md describes; fixing the bug makes the implementation match the doc, not the other way around). **What would need updating** if a `phase-info` subcommand ships: `command-reference.md` needs a new command entry, `response-shapes.md` needs its "recovery path" guidance updated (right now the only recovery path documented is presumably `--full`, based on the issue's own note that `--full` is the only current escape hatch), and the eval suite at `plugins/koto-skills/skills/koto-user/evals/evals.json` would need new scenarios exercising `phase-info` — I did not read evals.json's content, only confirmed it exists.
- **koto-author** (`plugins/koto-skills/skills/koto-author/`): `references/template-format.md` and `SKILL.md` already reference `details` (grep-confirmed), consistent with R14's requirement to teach the split during template authoring. I did not verify whether R14's specific sub-bullets (dogfooding on koto-author's own template, at least one bundled example template) are satisfied — that's a narrower follow-up than the AC3/AC4 gap and lower priority.
- Neither skill currently mentions `phase-info` (grep for `phase-info`/`phase_info` across both skills' reference docs returned nothing) — confirming AC4 truly hasn't landed anywhere, including docs.
- `scripts/run-evals.sh` exists at repo root; both skills have `evals/evals.json` files. I did not inspect their contents for existing `details`-related eval scenarios — flagging as unverified rather than assuming either way.

### 8. CHANGELOG conventions

`CHANGELOG.md` follows Keep a Changelog format with `### Added` / `### Changed` / `### Stability` subsections per version, and treats pre-1.0 MINOR bumps as MAJOR-equivalent (0.10.0 was "breaking-change-eligible relative to 0.9.x", per the file's own header note). Notably: **grepping the full CHANGELOG for "details" or "#109" or "output contract" returns nothing** — the PR that shipped the `details` field/`--full` flag (#109, landed 2026-03-30 as part of the koto-next-output-contract redesign) does not appear to have a corresponding CHANGELOG entry, at least not one that literally names "details." This is either a gap in changelog discipline for that PR, or the entry exists under different wording I didn't match — worth a quick manual check before writing any new CHANGELOG entry for the AC3 fix or a `phase-info` command, so the new entry's section/wording is consistent with whatever (if anything) documents #109 today.

## Implications

The exploration's framing needs to shift from "should koto add a details field" (already decided, already shipped, `status: Done` PRD) to a narrow, mostly-mechanical scope: (a) fix the AC3 gate-blocked-retry gap in `src/cli/next.rs`'s pure dispatcher — likely by threading a visit/emission count into `dispatch_next` rather than gating solely on `template_state.details.is_empty()`, and/or by changing `derive_visit_counts`'s counting semantics (the second issue comment's "count emissions/ticks rather than transitions" suggestion is one option, but changes what `derive_visit_counts` means for other callers — needs its own design lead); and (b) decide the AC4 escape-hatch question: ship a dedicated read-only `koto phase-info <workflow>` subcommand (matching the issue title/PRD wording) or formally re-scope AC4 to "document `koto next --full` as the escape hatch" (cheaper, already works, but ticks the machine and doesn't match the issue's explicit "read-only" framing — the second issue comment argues this distinction matters for long loops where re-ticking has side effects).

No stability-contract, schema-version, or template-hash rework is implied by either fix — the `details` field, `TemplateState`, and `NextResponse` are outside the frozen `koto-stability-tests` surface, outside `docs/STABILITY.md`'s JSONL wire-format rules, and the hash/cache mechanics already handle content changes correctly via content-addressing. This significantly narrows the design surface other leads should expect: there's no big "backward compatibility" design problem left to solve on the output-contract side. The interesting design work is (1) the visit-counting fix's exact mechanism and (2) the `phase-info` command's shape (read-only, must not tick the machine, must work even when the caller has never called `--full` before — i.e., must independently know current state + details without invoking `dispatch_next`'s advancement path).

## Surprises

- The single biggest surprise: **the feature described by #90 is already ~90% implemented**, and the issue itself already contains a self-audit (two comments, spanning 2026-06-07 through post-0.11.4/2026-08-05) that did exactly this kind of "is this already built" investigation and reached the same conclusion, down to identifying the exact gate-blocked-retry gap and the missing `phase-info` command. This should reframe how the whole exploration proceeds — other leads researching "first visit behavior," "phase info command design," or "template grammar for details" should be told this isn't greenfield design, it's closing two specific, already-diagnosed gaps.
- Issue #90's "Proposed Template Format" section (YAML `details:` key under a state) **does not match the shipped format** (markdown `<!-- details -->` comment marker). This is a real, user-visible discrepancy in the issue text that the exploration should flag rather than silently resolve either way — the shipped format is presumably correct/final (per PRD Decision D6, the format question was deliberately deferred to a downstream design doc that then picked markdown), so #90's YAML example is simply stale/wrong, not a decision still open.
- `AGENTS.md`, which `PRD-koto-next-output-contract.md` R13 names as a required documentation update target, doesn't exist in this repo at all. The role has apparently been absorbed by the koto-user skill's `references/response-shapes.md`. Any AC or design-doc language that references "AGENTS.md" for this repo should be corrected or dropped.
- `koto-stability-tests/` — despite its name and the lead's framing suggesting it might be the "golden output" test suite to worry about — has nothing to do with the `koto next` CLI output shape. It's scoped narrowly to the JSONL session-log wire format and four `SessionBackend` methods. Zero risk of collision with a `details`/`phase-info` change.
- `session/version.rs` is not the JSONL schema version file (a name collision the lead's framing assumed) — it's cloud-sync conflict-resolution versioning, entirely unrelated.

## Open Questions

- Whether the CHANGELOG gap for PR #109 (no "details"/"output contract" entry found) is a real miss or just different wording — worth a manual read of the `## [0.10.0]` / current `[Unreleased]` sections before the exploration proposes new CHANGELOG language, so it's added consistently.
- Whether `derive_visit_counts`'s semantics should change (count emissions instead of transitions) to fix AC3, or whether a separate, `dispatch_next`-local counter should be introduced instead — changing `derive_visit_counts` affects any other caller of that function (I did not audit all call sites beyond `cli/mod.rs:4008` and the discovery via grep suggested it's used at least there and in its own test module; a full call-site audit is needed before choosing this fix).
- Whether `koto phase-info` should be a new top-level subcommand or a flag on `koto status` (the second issue comment floats `status --details` as an alternative) — this is a genuine open design question, not something the contract/compat lead can resolve; it belongs with whichever lead is covering CLI surface/command design.
- I did not read `plugins/koto-skills/skills/koto-user/evals/evals.json` or `koto-author/evals/evals.json` contents, only confirmed their existence — another lead or a follow-up pass should check whether existing eval scenarios already cover `details` presence/absence so the AC3 fix and any `phase-info` addition know what net-new eval coverage is actually needed.
- R14's narrower sub-bullets (koto-author's own template dogfooding the split, at least one bundled example template demonstrating it) weren't individually verified — worth a quick follow-up check but unlikely to change the exploration's overall shape.

## Summary
The `details` field, its first-visit-only inclusion, and a `--full` override are already implemented and shipped (PR #109, PRD-koto-next-output-contract R9) — issue #90 is not proposing new work but has two self-audit comments confirming most of its acceptance criteria already pass, leaving two narrow open gaps: a gate-blocked-retry re-tick still resends `details` (AC3), and the `koto phase-info` read-only escape-hatch command doesn't exist yet (AC4, though `koto next --full` already covers the same need at the cost of ticking the machine). None of koto's stability contract, JSONL schema version, template-hash locking, or the `koto-stability-tests` frozen surface constrain either fix — they're all scoped elsewhere (session-log wire format, not the `koto next` CLI response) — so the real open design question for the rest of the exploration is narrowly the visit-counting fix mechanism and the shape of the phase-info/status escape hatch, not a from-scratch compatibility analysis.

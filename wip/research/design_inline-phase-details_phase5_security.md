# Security review: inline-phase-details

## Summary

Nothing in this design rises above low severity. The one item worth carrying into the DESIGN as an explicit note, rather than treating as a pure non-finding, is that `koto status` reads the compiled template with a bare `std::fs::read` and no hash check against `machine_state.template_hash` (`src/cli/mod.rs:4873-4896`), unlike `koto next`'s validated read at `mod.rs:3204-3231` — today that gap only affects a boolean (`is_terminal`), but once `status` also returns substituted `directive`/`details`/`expects` off that same unchecked read, a stale or mid-replacement template file would surface as full recovered instructions rather than a silently-wrong flag. Everything else — substitution safety, the new event variant's forward/backward compatibility, log growth, the directive splice, and information disclosure — either inherits an existing, sound mitigation unchanged or introduces no new trust boundary.

## Findings

### 1. Untrusted input reaching new surfaces — none/informational

`directive` and `details` are author-supplied template text, substituted through the identical two-layer pipeline (`with_substituted_directive`) `koto next` already uses; D2 adds no new sanitization step because none exists today for `next` either — the trust boundary (whoever controls the file at `machine_state.template_path` already controls this text reaching `next`'s stdout) is unchanged. `koto status`'s response is written only via `println!` (`mod.rs:4959`) — no file, cache, or log. Checked both surfaces the brief named: `src/workflows_surface/project.rs:145-146,226-237` and `materialize.rs:98-128` expose `directive` (unsubstituted) via `/workflows` today but never `details`; `src/cli/dashboard_data.rs:289,753-758` exposes `directive` (substituted) but never `details`. So `details`/`expects` gain a second read path (`status`, alongside `next`) with no new destination and no new audience.

### 2. Variable substitution — none

`src/engine/substitute.rs`: `directive`/`details` go through `Variables::substitute()` (non-shell-safe), never `substitute_command()` — the shell-safe variant is reserved for gate/default-action commands, an unrelated call site this design does not touch. Every value is validated against the allowlist `VALUE_PATTERN = ^[a-zA-Z0-9._/:@ \-]*$` at `koto init` and re-validated defensively on every load in `Variables::from_events` (`substitute.rs:70-71`) — no quotes, backslashes, newlines, `$`, backticks, or shell metacharacters can pass. Substitution is single-pass, not recursive: `substitute_single_pass_no_reprocessing` (`substitute.rs:296-306`) pins that an expanded value (e.g. `{{OUTER}}` → `{{INNER}}`) is never rescanned, so no variable or evidence-derived value can inject `{{...}}` syntax that later expands, nor can a value "escape" the JSON string field it lands in (the result is embedded via `serde_json::json!`, which escapes it). No place in this design's substitution path interpolates into a shell command or filesystem path.

### 3. The new event variant — none

`Event`'s custom `Deserialize` (`src/engine/types.rs:1081-1341`) has one catch-all arm (`1331-1334`): any `type` string it doesn't recognize becomes `EventPayload::Unknown { type_name, raw_payload }`, unconditionally — an older binary at or above the documented `Unknown`-catch-all floor reads a log containing `instructions_delivered` records transparently, and the custom `Serialize` round-trips them byte-identically since it re-emits the stored `type` string (the same pattern already exercised by the six `request.`-prefixed variants and `koto-stability-tests`, which matches `Unknown` with `_ => unreachable!()`). Binaries below that floor hard-error, but that's a pre-existing floor every additive variant already carries, not something new here. On truncation: `read_events` (`persistence.rs` ~591-690) treats a malformed *final* line as a recoverable truncated write (returns events up to the last valid line) and a malformed *non-final* line as corruption — general log-parsing behavior unrelated to which variant crashed mid-write. A crash mid-append of the new marker produces the same recoverable malformed-final-line case any other event type already produces.

### 4. The extra write — low

`append_event` (`persistence.rs:139-181`): one `writeln!` plus one `file.sync_data()` per call, no lock on non-batch sessions (`mod.rs:3746-3770` confines `lock_state_file` to batch-parent states) — pre-existing behavior for every event type, not new. Per D1, the marker is written once per *occupancy* of an instructions-carrying phase (gated on non-empty `details`), not once per tick, so the PRD's own 14-tick gate-blocked example adds exactly one record, not fourteen; growth is bounded by how many times the phase is re-entered, which is itself bounded by the existing `Transitioned`/`DirectedTransition`/`Rewound` entry events the marker piggybacks on — it cannot outgrow them. A single record is on the order of 100-150 bytes; log growth from this feature scales with occupancy count, not iteration count, so there's no unbounded-growth path distinct from what already exists. `atomic_fs.rs` (whole-file atomic *creation*, used by session/request-store bootstrap) isn't in the append path at all — irrelevant to this write. Because the predicate is an existence check rather than a count, the unlocked concurrent-append race on non-batch sessions can at most produce a redundant duplicate record, never a wrong answer. Crash between printing the response and appending the marker (ordering: print then append) fails toward re-delivery — the next call sees "not yet delivered" and re-includes instructions once more, which is the safe direction for an LLM agent to receive too much rather than too little. Severity is low only because of the fsync-per-occupancy cost on the two call shapes (first tick after `init`, first tick after `rewind`) that write nothing to the log today, not because of any growth or corruption risk.

### 5. The directive splice — informational

The existing abandonment-notice splice (`mod.rs:3374-3380`, `4204-4210`; `with_directive_prefix`/`with_substituted_directive` in `next_types.rs`) always runs the prefix splice strictly after variable substitution — documented as deliberate, because splicing koto-authored text before substitution would expose it to being rescanned for `{{...}}` tokens by a later substitution key, letting a template author name a variable to collide with the pointer's wording. D4's recommendation reuses this exact ordering for the new discoverability pointer, closing that surface the same way the existing mechanism already does. In the reverse direction — an agent mistaking the pointer for real template content, or vice versa — the existing abandonment notice mitigates with a distinctive fixed preamble ("NOTICE FROM KOTO (not from your coordinator): ...") and an explicit separator; the new pointer (target under 150 characters, phrased as a parenthetical) is less visually distinct by design (it's meant to be a low-key repeated nudge, not a seize-attention notice), but it remains constant, koto-authored text a template author has no mechanism to reach into — the splice only ever concatenates opaque strings, it never re-parses koto's own text for substitution. The one genuine open item, already flagged by D4's own review rather than newly found here, is ordering between the abandonment notice and the recovery pointer when both apply to the same response — that's a correctness/UX sequencing question (don't bury a stop instruction under a routine nudge), not an injection risk.

### 6. Concurrency — low

`handle_status` (`mod.rs:4834-4961`) never calls `lock_state_file` — confirmed the function's only lock-adjacent call site in the file is inside `handle_next`, gated to batch-parent states. For the session log, `status` inherits `read_events`'s existing torn-write tolerance: a malformed final line (what an in-progress, not-yet-synced concurrent append looks like) is treated as a recoverable truncation, and `directive`/`details`/`expects` are computed from the same already-read event list `status` uses for `current_state` today — no second read, no new torn-read surface there. The one real gap: `handle_status`'s template read (`mod.rs:4873-4896`) is a bare `std::fs::read` + `serde_json::from_slice` with no hash check, whereas `handle_next`'s equivalent read (`mod.rs:3204-3231`) computes `sha256_hex` over the bytes and hard-errors on a mismatch against `machine_state.template_hash`. This is pre-existing `status` behavior, not introduced here, and I found no evidence in this pass that `template_path` is mutated in place after `koto init` (the hash field implies koto expects it not to move) — but I also couldn't rule it out from the code read alone. Today the consequence is limited to one boolean (`is_terminal`); once `directive`/`details`/`expects` ride the same unchecked read, a stale cache entry, a half-written replacement, or a repointed symlink would surface as fully-substituted recovered instructions instead of a silently wrong flag. Worth either adding the same hash check `next` performs, or an explicit note that `status`'s template read is best-effort and can theoretically diverge from `next`'s validated view.

### 7. Information disclosure — none

`directive` is already exposed by both `/workflows` (unsubstituted, `project.rs:226-229`) and the dashboard (substituted, `dashboard_data.rs:753-758`) today. `details` is exposed by neither of those — only by `koto next`'s own response body, on delivery or under `--full`. Extending `status` gives `details`/`expects` a second read path with the same trust boundary (same caller, same session, same filesystem permissions) as the one `next` already has, not a new audience. `template_path` was already present in `status`'s output before this change; templates are ordinarily repo-committed content the caller already has read access to. Nothing in the added fields reveals content the caller couldn't already obtain by reading the template file at the path `status` already names.

### 8. Other observations

`expects` is schema-only, produced by a pure function over `TemplateState` (`derive_expects`) with no session-derived secrets flowing through it. Worth naming as a positive design property: R11's "no side effects" guarantee for the retrieval holds structurally, not by a runtime flag — `handle_status` simply never calls `append_event`, gate evaluation, `lock_state_file`, or `finish_terminal_tick`; the guarantee is "unreachable by construction," which is a stronger and more auditable property than a conditional check that could regress.

## Recommended Security Considerations section

This change moves author-supplied template text — the same `directive` and `details` fields `koto next` already substitutes and returns — onto a second, side-effect-free read path (`koto status`), and adds one new append-only event variant to the session log. Neither introduces a new trust boundary. The text was already fully attacker-controlled by whoever controls the template file, and it already reached the agent through `koto next`; `koto status` reading the same fields through the identical substitution pipeline (`Variables::substitute`, gated by the existing character allowlist and single-pass expansion) does not widen who can influence that text or where it lands. Substitution stays out of any shell-command or filesystem-path context on this path; that risk is confined to the unrelated `substitute_command` call sites this design does not touch.

The new `EventPayload::InstructionsDelivered` variant is safe under koto's existing forward/backward-compatibility contract without modification: the custom `Event` deserializer's unconditional catch-all routes any unrecognized event type to `Unknown`, so older binaries round-trip the new record unharmed, and a crash mid-append produces the same recoverable malformed-final-line case any other event type already produces on a torn write. The added write is bounded by phase-occupancy count, not tick count, so the design's own motivating case — a long gate-blocked loop — adds exactly one record rather than one per iteration, and the existence-check semantics of the delivery predicate make the unlocked, non-batch concurrent-append race produce at worst a harmless duplicate, never a wrong answer.

The directive splice that carries the new discoverability pointer follows the same after-substitution ordering the existing leg-abandonment notice already established, which is the property that matters: koto-authored text is never subject to re-substitution, and template-authored text can never reach into or alter it, in either direction. `koto status` itself is unlocked by construction — it never reaches `lock_state_file`, `append_event`, gate evaluation, or terminal cleanup, which are simply not present anywhere in its call graph, not excluded by a conditional — so the read-only guarantee this feature depends on holds structurally rather than by convention.

The one item worth an explicit decision in this design rather than a silent inheritance: `koto status`'s template read does not verify the compiled template's hash against the value recorded in the session header, unlike `koto next`'s equivalent read. That gap predates this change and today only affects a single boolean field; extending `status` to return substituted `directive`, `details`, and `expects` off the same unverified read means a stale or mid-replacement template would now surface as fully-formed recovered instructions rather than a silently wrong flag. The DESIGN should either add the same hash check `next` already performs to `handle_status`'s template read, or state explicitly that `status`'s view of the template is best-effort and may diverge from the validated view `next` uses.

No new information becomes reachable through this change that a caller could not already obtain: `details` was already returned by `koto next`, `directive` is already exposed unsubstituted via `/workflows` and substituted via the dashboard, and the template file `status` already names in its output is ordinarily repo-committed content the caller already has read access to.

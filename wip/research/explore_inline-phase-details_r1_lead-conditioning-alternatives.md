# Lead: What are the alternatives to conditioning the details payload on "first visit", and how do they compare?

## Findings

### Framing: the feature is shipped; the remaining question is where the first-visit proxy breaks

koto#90's core proposal is already implemented (PR #109, `DESIGN-koto-next-output-contract.md`, status Current): `TemplateState.details` split on `<!-- details -->`, `details: Option<String>` on non-terminal `NextResponse` variants, and gating at `src/cli/mod.rs:3999-4015` on `derive_visit_counts` (`src/engine/persistence.rs:981`) — `if full || count <= 1 { Some(details) } else { None }`. This round refocuses on what's still open: whether `--full` is an adequate escape hatch on its own, two concrete cases where the visit-count proxy gives a wrong answer, and whether `count <= 1` is even the right kind of predicate.

### Q1: Does `koto next --full` (no `--with-data`, no `--to`) mutate state or write to the log?

**Yes, definitively, for two independent reasons that have nothing to do with `--full` itself.** The `full` flag only gates one thing: whether `details` is included in the *final* response (`src/cli/mod.rs:4004`, `if full || count <= 1`). It does not change what `advance_until_stop` does before that point. It is not a distinct, read-only code path — it's a boolean threaded into the last few lines of response construction, downstream of the entire advancement loop having already run.

**Mechanism A — auto-advance fires without evidence.** With no `--with-data`, the `evidence` map passed into `advance_until_stop` comes from `merge_epoch_evidence(derive_evidence(current_events))` (`src/cli/mod.rs:3816-3817`) — i.e. whatever evidence is already recorded in the log for the current epoch, which can be empty. `resolve_transition` (`src/engine/advance.rs:693-777`) only blocks the unconditional-transition fallback when `gate_failed || (!fresh_evidence && has_conditional)` (`:759`). For a pure-routing state — no `accepts` block, an unconditional transition, `has_conditional == false` — that guard never fires, so the unconditional transition resolves and `advance_until_stop` appends a `Transitioned` event (`src/engine/advance.rs:544-551`) and mutates `current_state` in the log, with zero evidence submitted and regardless of `--full`. This is exactly the documented "auto-advance candidate" fallback (`src/cli/next.rs:107-123`, the `dispatch_next` doc comment).

**Mechanism B — default actions re-execute on every call.** Step 5 of `advance_until_stop` (`src/engine/advance.rs:286-314`) unconditionally calls `execute_action` whenever `template_state.default_action` is set — gated only on the state having a default action, not on whether new evidence was submitted. The action closure in `handle_next` (`src/cli/mod.rs`, around the `DefaultActionExecuted` payload construction) runs the shell command and then does `let _ = backend.append_event(&name, &event_payload, &now_iso8601())` unconditionally. `DESIGN-default-action-execution.md:301-302` confirms the intended skip path is keyed on evidence being non-empty ("If evidence is non-empty, the closure returns `Skipped`"), i.e. skip-on-override, not skip-on-repeat-poll. A bare `koto next --full` on a default-action state with no override evidence re-runs the command and appends a new `DefaultActionExecuted` event every single call.

Both mechanisms predate #90 and are working as designed for their own purposes (auto-advance and default actions are supposed to fire without agent input). But they mean **`--full` cannot be relied on as a read-only probe** — whether a given `koto next --full` call mutates depends entirely on the *shape of the current state* (gates present, default_action present, or a bare unconditional transition), not on the flag. This is the concrete argument for #90's one unimplemented acceptance criterion, `koto phase-info`: it needs to be a genuinely separate, read-only code path — one that looks up `compiled.states.get(current_state)` and formats a response without ever calling `advance_until_stop` — not a flag bolted onto the existing `koto next` handler.

(For contrast: the earlier round's finding that a *non-gated, non-default-action, no-op* `koto next` poll is read-only still holds — see Idempotency note below — but that's a narrower guarantee than "any `koto next --full` call is safe to run speculatively," which is false.)

### Q2a: `koto rewind` re-enters a state whose visit count is already ≥ 2

Confirmed by code. `handle_rewind` (`src/cli/mod.rs:1985-2050`) appends `EventPayload::Rewound { from, to: prev_state, rationale }` (`:2043-2048`) when rewinding. `derive_visit_counts` (`src/engine/persistence.rs:981-999`) counts `Rewound { to, .. }` as an entry event for `to`, identically to `Transitioned`/`DirectedTransition` (`:987`). So: agent enters state X the first time → `Transitioned{to: X}` → count 1 → details shown. Agent advances past X, then something (a reviewer, a gate, a coordinator) triggers `koto rewind` back to X → `Rewound{to: X}` appended → count becomes 2. The very next `koto next` call classifying state X sees `count <= 1` is false and omits `details` (`src/cli/mod.rs:4008-4013`) — on exactly the state the rewind is asking the agent to redo, which is precisely the wrong moment to assume the agent already has full context: a rewind often carries a `rationale` explaining what went wrong, and the whole point of rewinding (as opposed to the agent looping back to X through its own normal transitions) is that something external decided the prior attempt at X needs to be redone, possibly with different guidance in mind.

**Candidate fixes, evaluated:**

- **Special-case rewind targets** (don't count `Rewound` toward the suppression threshold, or reset on it): the natural place to do this is `derive_visit_counts` itself, but that function is **shared** — `src/workflows_surface/project.rs:284-286` also calls it, for a different purpose (`derive_visit_counts(events).into_keys().collect()` to build a visited-states set for progress rendering). Changing what `Rewound` means inside the shared function risks silently changing that consumer's semantics too (a rewound-into state currently counts as "visited" for progress purposes, which is probably still correct there even if the details-gating threshold should treat it differently). The safer fix is scoped to the call site in `src/cli/mod.rs:4008-4013`: instead of `visit_counts.get(final_state)`, look at whether the *most recent* entry event for `final_state` was specifically a `Rewound` event, and treat that as "fresh" regardless of aggregate count. This needs a small new derive function (e.g. `derive_last_entry_kind` or similar), not a change to the shared counter.
- **Key off `respawn_generation`**: doesn't apply here — a rewind isn't a respawn, and `respawn_generation` (see Q2b) doesn't change on rewind. Wrong tool for this gap.
- **Reset-on-respawn**: same, not applicable to rewind.
- **Leave it to the escape hatch (`koto phase-info`)**: viable as a backstop, but shifts the burden onto the agent recognizing "I was just rewound, I should re-check the phase instructions" — plausible for a capable agent reading the `rationale` field, but not guaranteed, and it's strictly worse than just getting `details` back automatically on a rewind, which is cheap to implement and doesn't depend on agent behavior.

Evidence favors the scoped "last-entry-kind" fix over both leaving it purely to the escape hatch and over touching the shared `derive_visit_counts` function.

### Q2b: F1 cold-restart respawn and batch-child retry — do they reuse the same log?

These are two different mechanisms in the codebase, and they behave differently. Worth separating them precisely rather than treating "respawn" as one thing:

**F1 cold-restart (`src/engine/respawn.rs`) — confirmed break case.** The module docstring (`:1-45`) describes F1 firing when a requester's substrate transcript-retention window has elapsed and the requester is silent — i.e. the original agent process is gone, unreachable, with no continuity to its context. F1 spawns "a fresh subagent with the requester's saved `role`/`template_name`/`inputs` and a fixed-form resume-context prompt" (`:19-20`), and that prompt is explicitly **not** synthesized from session content — "the resume-context prompt is COMMITTED — never synthesized from session content. A free-form prompt would create a prompt-injection surface" (`:66-70`). Critically, `emit_respawn_event` (`src/engine/respawn.rs:524-552`) calls `append_event(requester_state_file, ...)` — **the same state file / same session log the original agent was writing to**, not a fresh one. So the new subagent process, calling `koto next` for the first time, reads a log that already contains whatever `Transitioned` events the crashed predecessor left behind. If the predecessor had already looped through the current state more than once before crashing (count ≥ 2), the fresh, zero-context subagent's first-ever `koto next` call on that state omits `details` — it inherits a "you've already seen this" verdict for content it has, by construction, never seen. (Note: `RequesterRespawn` itself is recorded as `EventPayload::EvidenceSubmitted { state: "request_store.respawn", .. }`, `src/engine/respawn.rs:540-547` — a sentinel state name, not a real workflow state, so it does not itself inflate `derive_visit_counts` for any real state. The break comes purely from the pre-existing `Transitioned` events left by the crashed process, not from the respawn event.)

**Batch-child retry (`src/cli/retry.rs`) — checked, does NOT reproduce this break.** `respawn_skipped_child` and `respawn_failed_child` (`src/cli/retry.rs:571-660`) both call `backend.cleanup(&snapshot.composed)` first — deleting the stale child's state/log entirely — then `init_child_as_skip_marker_from_parent` / `init_child_from_parent`, which create a **brand-new** session log from scratch. These two retry paths only apply to children that are `skipped` (stale skip marker) or `spawn_failed` (never actually started), so there's no prior visit history to lose in the first place, and the fresh log starts every counter at zero. I did not find a code path where a batch child that had *already progressed into workflow states with `details`* gets retried onto its existing log the way F1 does — the retry mechanism's own design (full cleanup before reinit) avoids that failure mode by construction. This is worth flagging back to the team: the "batch-child retry" half of the reported break case doesn't hold up under the code as written; F1 cold-restart is the real instance of this pattern.

**Candidate fixes for F1, evaluated:**

- **Key off `respawn_generation`**: this is the strongest fix and it's cheap. `respawn_generation: Option<u32>` already exists on the header (`src/engine/types.rs:340`) and is incremented via `new_respawn_generation` on every F1 respawn (`src/engine/respawn.rs:156,176`), and a `RequesterRespawn`-equivalent event (`EvidenceSubmitted{state:"request_store.respawn",..}`) already lands in the same log at the moment of respawn (`src/engine/respawn.rs:540-547`). The details-gating computation at `src/cli/mod.rs:4008-4013` could filter `post_events` to only those *after* the most recent such respawn-marker event before calling `derive_visit_counts`, so a state entered before the respawn boundary doesn't count against a process that's provably new. No new state file, no schema change — the marker is already in the log, it's just not consulted today.
- **Reset-on-respawn**: functionally the same idea as the bullet above, phrased as "reset the counter" rather than "filter by boundary" — filtering is preferable because `derive_visit_counts` is shared (same sharing concern as Q2a) and a literal reset would need to be threaded through carefully to avoid corrupting the other consumer in `workflows_surface/project.rs`.
- **Special-case rewind targets**: not applicable, this is a different event type.
- **Leave it to the escape hatch**: this is the necessary backstop regardless — F1's resume-context prompt is fixed-form and deliberately doesn't tell the fresh subagent "you're on generation 2, re-check `koto phase-info`," so unless that resume prompt is also updated to nudge the agent, `phase-info` existing doesn't help if the agent never thinks to call it.

### Q3: Is `count <= 1` the right predicate at all?

No — not because the derivation is implemented incorrectly, but because it's answering a different question than the one that matters. `count <= 1` is a **session-log-visit** proxy: "has this state's `Transitioned`-equivalent event appeared before in this log." The thing #90 actually wants to know is **process-context continuity**: "does the process asking right now already have this content in its live context." Those coincide in the common case (one continuous agent working straight through a workflow) and diverge in exactly the two cases investigated above: a rewind inflates the log-visit count without the calling process having lost anything (arguably it should show details anyway, since the *reason* for the rewind may itself require re-reading updated instructions), and an F1 respawn replaces the process without inflating the log-visit count in a way the gating logic accounts for (the *process* is new but the *log* isn't).

A true process-identity predicate isn't buildable within #90's own constraint — the issue's acceptance criteria require "Phase visit tracking uses existing JSONL state (no new state files)," and koto's session log has no notion of "process/agent identity" per entry today (no PID, no substrate session token, nothing beyond `submitter_cwd` on some evidence events and the coarse `respawn_generation` counter on the header). Given that constraint, the fix isn't to replace the log-derived approach; it's to make the *derivation* boundary-aware using markers already present in the log (rewind events, respawn events) rather than a flat cumulative count, plus accepting `koto phase-info` as the necessary backstop for the residual cases no log marker can ever cover — silent context compaction mid-session, with no discrete event at all. That last category is unreachable by any log-derived heuristic no matter how it's refined, which is the strongest argument for shipping the escape hatch regardless of how precise the automatic gating gets.

### Idempotency note (carried forward, refined)

The earlier round's finding still holds for the narrow case it covers: a `koto next` call on a state with **no gates and no default_action**, landing on `TransitionResolution::NeedsEvidence` with no matching transition, writes nothing (`src/engine/advance.rs:561-585` has no `append_event` call on that branch), and `derive_visit_counts` itself is a pure read over already-persisted events. But Q1's findings above narrow that guarantee considerably: it only applies to states that are neither gated nor auto-advancing nor action-bearing. Any state with a `default_action` or a bare unconditional transition is not read-only on repeat polling, `--full` or not, and this predates #90.

## Implications

`koto phase-info` (or equivalent) needs to be built as a genuinely separate, non-advancing code path — not a flag on `handle_next` — because `--full` demonstrably runs the same mutating `advance_until_stop` loop as every other `koto next` invocation. That's the strongest, most concrete argument for treating the escape-hatch acceptance criterion as load-bearing rather than optional polish.

Separately, the visit-count predicate has two identified, fixable blind spots (rewind, F1 respawn) that are both closeable using data already in the log — no new state files needed, consistent with the issue's own constraint — but neither fix should be made by changing `derive_visit_counts`'s shared semantics, since `src/workflows_surface/project.rs:284-286` depends on its current behavior for an unrelated purpose. Both fixes belong at the `src/cli/mod.rs:4008-4013` call site as additional filtering/lookback logic, not inside the shared derivation function. The batch-child-retry half of the originally reported break case doesn't hold up under the code (`src/cli/retry.rs`'s retry paths fully wipe and reinit the child log), which narrows the actual scope of Q2 to F1 cold-restart specifically.

## Surprises

The default-action re-execution finding (Mechanism B in Q1) is a bigger idempotency gap than the rewind/respawn cases — it means a whole class of states was never read-only under repeat polling, independent of #90 entirely, and `DESIGN-default-action-execution.md` documents this as intentional (skip-on-override-evidence, not skip-on-repeat-poll). It's not a bug to fix as part of #90, but it materially changes the shape of "is `koto next --full` safe to call speculatively" from "usually, unless gates" to "depends on the state, and there are at least two independent mutation paths besides gates."

The batch-child-retry claim not holding up is also worth flagging plainly rather than quietly absorbing: the retry paths in `src/cli/retry.rs` were specifically designed to avoid inheriting stale state (full `backend.cleanup` before reinit), which is the opposite failure mode from F1. Conflating the two under one "respawn" umbrella would lead to over-engineering a fix for a case (batch-child retry) that doesn't actually need one.

## Open Questions

- Should the F1 resume-context prompt (`RESUME_CONTEXT_PROMPT`, fixed-form per `src/engine/respawn.rs`) be updated to explicitly tell the fresh subagent to call `koto phase-info` on its current state before proceeding, given that the automatic gating can't reliably detect this case without the boundary-filtering fix?
- Is there a third case beyond rewind and F1 respawn where a new process attaches to an existing log without inflating the log-derived signal correctly — e.g. a human manually resuming an abandoned session, or the `leg_pointer`/abandoned-leg mechanism noted in `src/cli/mod.rs` around the epoch fence? Not investigated this round; flagged for anyone picking up the escape-hatch design.
- If the rewind fix (last-entry-kind check) and the F1 fix (respawn-boundary filtering) are both implemented, is `koto phase-info` still needed as more than a backstop, or does it become purely a recovery tool for the unreachable "silent compaction, no log event at all" case?

## Summary

`koto next --full` is not a safe read-only probe — it runs the exact same mutating `advance_until_stop` loop as any other `koto next` call, and two independent mechanisms (auto-advance on empty evidence, unconditional default-action re-execution) can write to the log regardless of the flag, which is the concrete case for building `koto phase-info` as a genuinely separate code path. Of the two reported break cases in the shipped first-visit predicate, rewind is real and traceable to `Rewound` events being counted identically to normal entries in the shared `derive_visit_counts`, while F1 cold-restart is real and more severe (a zero-context process inherits a stale log's visit history via the same state file), but batch-child retry turned out not to reproduce the problem since its retry paths fully wipe and reinstantiate the child log before respawning. Biggest open question: whether fixing both identified predicate blind spots with log-derived boundary markers (no new state files needed) leaves `koto phase-info` as a pure backstop for silent, event-less context loss, or whether the resume-context prompt for F1 also needs to actively point the fresh agent at it.

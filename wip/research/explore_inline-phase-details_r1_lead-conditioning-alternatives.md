# Lead: What are the alternatives to conditioning the details payload on "first visit", and how do they compare?

## Findings

### Framing correction: option 2 is not proposed, it is shipped

Before comparing alternatives, the single most load-bearing fact: **koto#90's core proposal (inline on first visit, omit on repeat visits) is already implemented**, not hypothetical. It shipped in PR #109 ("feat(cli): redesign koto next output contract"), documented in `docs/designs/current/DESIGN-koto-next-output-contract.md` (Decision 1 and Decision 3), which is `status: Current`. The mechanism:

- `TemplateState.details: String` (`src/template/types.rs:57`) is populated by the compiler splitting a state's markdown body on an `<!-- details -->` marker (`src/template/compile.rs`, `extract_directives`).
- `derive_visit_counts(events: &[Event]) -> HashMap<String, usize>` (`src/engine/persistence.rs:981`) scans the JSONL log once, counting `Transitioned`, `DirectedTransition`, and `Rewound` events by target state.
- The main `handle_next` handler (`src/cli/mod.rs:4008-4013`) re-reads events *after* `advance_until_stop` returns, computes visit count for `final_state`, and includes `details` only when `count <= 1` (first visit) or `--full` is passed. `--full` already exists as a CLI flag (`src/cli/mod.rs:2899`, `full: bool`) — this is option 4 ("agent-requested flag"), already implemented as a companion to option 2, not an alternative to it.

So the actual open design surface in koto#90 is narrower than "pick a conditioning strategy from scratch." It's: (a) whether the escape hatch should be a `koto phase-info` command (issue's proposal) versus something else, given the shipped conditioning already exists, and (b) two gaps the shipped implementation has that a `phase-info` command would need to work around or that the design should note. Both gaps are documented below with citations.

### Gap 1: the `--to` directed-transition path does not do visit-count conditioning at all

`dispatch_next` in `src/cli/next.rs:50-54` builds `details` unconditionally whenever `template_state.details` is non-empty:

```rust
let details = if template_state.details.is_empty() {
    None
} else {
    Some(template_state.details.clone())
};
```

This function is the *only* classifier used by the `--to` path (`src/cli/mod.rs:3355`, `match dispatch_next(target, target_template_state, true, &gate_results)`), and that path prints the response directly (`src/cli/mod.rs` around line 3388) without ever calling `derive_visit_counts`. So `koto next --to <state>` includes `details` on every call, regardless of how many times the agent has already directed itself to that state. The main advancement path (`src/cli/mod.rs:4008-4013`) is the only place visit-count conditioning happens. This is a real inconsistency in the shipped contract, not a hypothetical edge case — a template using `--to` heavily (e.g., an agent retrying a self-loop by explicit direction rather than relying on transition matching) gets full details every time.

### Gap 2: states passed through during multi-state auto-advance never surface details, even on their first visit

`advance_until_stop` (`src/engine/advance.rs:168-599`) only returns (stops the loop) at Terminal, GateBlocked, EvidenceRequired, Integration/IntegrationUnavailable, ActionRequiresConfirmation, CycleDetected, or ChainLimitReached. Every other resolved transition just does `state = target; continue;` (e.g. `src/engine/advance.rs:534-560` for `TransitionResolution::Resolved`, and `:486-517` for `skip_if`). The handler only computes `details` for `final_state` (`src/cli/mod.rs:3977-4013`) — the state the loop stopped at. Any state that gets auto-advanced *through* in the same call (one `koto next` crossing three states, per the exploration brief's question) never has its `details` surfaced, even if that was the first and only visit to that state. If a template author attaches `details` to a routing/skip_if state, that content is effectively unreachable dead content under the current contract. This is a direct answer to "which details do you return when one call crosses three states" — the answer today is "only the final state's, and only if it's a first visit or `--full`," with intermediate states silently dropped regardless of visit history.

### Idempotency / read-only investigation

This was the crux of the assignment and the answer is reassuring for option 2: **`koto next` calls that don't advance are still side-effect-free today, and the shipped "first visit" mechanism doesn't change that.**

- `derive_visit_counts` is a pure function over already-persisted events (`src/engine/persistence.rs:981`). It does not append anything.
- Inside `advance_until_stop`, the *only* `append_event` calls are: `GateEvaluated` when a state has gates (`src/engine/advance.rs:389`), and `Transitioned`/skip_if-triggered `Transitioned` when a transition actually resolves (`src/engine/advance.rs:509`, `:551`). A call that lands on `TransitionResolution::NeedsEvidence` with no matching transition and no gates writes nothing (`src/engine/advance.rs:561-585`) — confirmed by reading the full match arm, there is no `append_event` call on that branch.
- So a bare `koto next` re-poll on a state with no gates and no new evidence is a genuine no-op today, and the visit-count mechanism preserves that: it counts the *entry* event, which was already written when the agent (or a previous `koto next` call) transitioned into that state, not by the polling call itself. By the time a caller's `koto next` reads the log to classify the current state, the `Transitioned` event putting them there already exists — counting it doesn't require a fresh write.
- The one caveat: a state *with gates* already writes `GateEvaluated` on every call regardless of advancement (`src/engine/advance.rs:389`), so "does a non-advancing `koto next` ever write" was already "sometimes yes" before #90 — the details mechanism doesn't introduce a new case of this, it just rides along with a write pattern that predates it.

This means any alternative that instead required a *new* explicit "state entered" or "details delivered" marker event (e.g. to make the proxy more precise — distinguishing "agent got details and kept them" from "agent got details and then compacted") would be the one to introduce a genuinely new write on a currently-read-only call, not option 2 as shipped.

### Config precedent

`src/config/mod.rs` has two established patterns for behavior toggles:
- `WorkflowsConfig.native: bool` (`src/config/mod.rs:27-43`) — a simple on/off switch, TOML + `koto config set workflows.native false --user`, defaulting to on. Documented precedent for a boolean feature toggle.
- `RequestStoreConfig` (`src/config/mod.rs:53-97`) — the doc comment explicitly states each field is "independently overridable via TOML, env-var, or (for `redelegation_cap`) a per-tick CLI flag." This is direct precedent for option 7 (config-controlled) layered with option 4 (CLI-flag override) — koto already does this composition for other operator-tunable dimensions, so a `details.mode` or similar config key with a CLI override is not a novel pattern to introduce.

No existing config key touches response verbosity or details/directive behavior specifically — `ALL_KEYS` (`src/config/mod.rs:400-418`) has nothing for it. `docs/designs/current/` and `docs/designs/archive/` have no other design document discussing agent context management or response verbosity outside `DESIGN-koto-next-output-contract.md` itself.

### Composition with `advanced` and multi-state auto-advance

None of options 1, 3, 4, 5, or 7 have a multi-state problem, because they don't depend on *which* state was visited when — they're either always-on, always-off, or explicitly requested. Option 2 (shipped) and option 6 (template-declared) both inherit the "which state's details, when a call crosses three states" ambiguity, and the shipped code resolves it by fiat: only `final_state`'s details, only if `final_state`'s own visit count qualifies (Gap 2, above). A retrieval command (option 3) sidesteps this entirely — the agent can ask for the phase it's actually confused about, including one it was auto-advanced through, since `phase_info` would presumably take a state/phase argument rather than being implicitly scoped to "wherever `next` last stopped."

## Implications

The exploration should stop treating "which conditioning strategy" as the open question — that was decided and shipped for the base case. The decision that's actually in front of koto#90 is narrower and better framed as: **does the missing `koto phase-info` escape hatch (option 3) get added as a *complement* to the shipped option 2, and if so, does it also need to close Gap 1 (`--to` path bypasses conditioning) and Gap 2 (auto-advanced intermediate states never surface details) while it's in the neighborhood?** The issue text explicitly frames `phase-info` as recovery for "context compression dropped them," which is exactly the option-2 failure mode identified in the table (agent lost context, koto's proxy says "not first visit," details stay omitted) — so the issue's own proposal is: ship option 3 as a safety net on top of the already-shipped option 2, not as a replacement.

Given that framing, downstream design work should treat `koto phase-info` as additive plumbing (new subcommand, or an extension to an existing one) rather than a redesign of the conditioning logic, and should decide explicitly whether to fix the two gaps in the same pass (both are one- or two-line-of-reasoning fixes: thread `derive_visit_counts` into the `--to` path in `dispatch_next`, and consider whether an auto-advanced intermediate state's `details` should ever be visible at all, or whether that's working as intended since the loop doesn't stop there).

## Surprises

The biggest surprise: the exploration brief describes koto#90 as proposing "the conditioning rule," as if it were still an open question to design from scratch. It isn't — `DESIGN-koto-next-output-contract.md` (status: Current, merged via PR #109) already made this exact decision, with its own "alternatives considered" section for the visit-counting mechanism (boolean `HashSet` vs. counting `HashMap`, and rejecting a persisted-counter-file approach specifically because "it violates PRD R9, no new state files or schema changes" — `DESIGN-koto-next-output-contract.md:151-153`). That prior rejection is itself useful evidence for downstream design: it's already established precedent that any `phase-info`-adjacent state tracking should stay log-derived, not add a new persisted marker.

A second surprise, smaller but concrete: the `--to` path's non-conditioning (Gap 1) means the shipped feature isn't actually "first visit only" everywhere in the CLI surface today — it's "first visit only, except when the agent uses `--to`, where it's always-on (option 1 behavior)." Whether that's an intentional carve-out (an agent using `--to` is making an explicit, deliberate choice and maybe *should* get full context every time) or an oversight isn't stated anywhere in the design doc or code comments.

## Open Questions

- Was Gap 1 (`--to` bypassing visit-count conditioning) intentional? No design doc or code comment addresses it either way.
- Should `koto phase-info` take a target phase/state argument (letting an agent ask about any state, including ones it was auto-advanced through), or is it implicitly scoped to "current state only"? The issue text (`koto phase-info <workflow>`) suggests workflow-scoped, but doesn't specify per-state addressing, which matters directly for closing Gap 2.
- Does `koto phase-info` need its own read-only guarantee statement, or does it inherit "read-only" for free by only reading `compiled.states` and the event log, same as the rest of the query paths investigated here?
- Is there a case to also fix Gap 2 (intermediate auto-advanced states) as part of this issue, or is "only the state the loop stopped at" acceptable as long as `phase-info` exists as a backstop?

## Summary

koto#90's core proposal — inline details on first visit, omit afterward — is not a design decision waiting to be made; it already shipped (PR #109, `DESIGN-koto-next-output-contract.md`, driven by a log-derived `derive_visit_counts` that adds no new writes to the currently-read-only non-advancing `koto next` path). The real open surface is the issue's own proposed escape hatch, `koto phase-info`, which the codebase doesn't have yet, and two concrete gaps in the shipped conditioning worth deciding on alongside it: `--to` directed transitions never omit `details` (`src/cli/next.rs:50-54`), and states crossed during multi-state auto-advance never surface `details` even on a first visit, since only `final_state` is ever checked (`src/cli/mod.rs:3977-4013`). Biggest open question: whether `koto phase-info` should be state-addressable (closing Gap 2 as a side effect) or implicitly scoped to "wherever the session currently is."

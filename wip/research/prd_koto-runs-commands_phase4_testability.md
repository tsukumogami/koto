# Testability Review

## Verdict: PASS
Almost all 35 acceptance-criterion bullets map directly to a `cargo test` integration test or a Gherkin scenario a tester could write today (fixtures, refusal-message assertions, before/after diffs), and the handful that lean on "documented, observable outcome" phrasing are acceptable under the PRD's explicit deferral of mechanism to the design doc; the failures below are refinements to a small minority of ACs and two or three genuine coverage gaps, not a structural inability to plan tests from this document.

## Untestable Criteria
1. "A template author can write a working `default_action`... using only the published documentation (R20)" — as written this is a subjective claim about a human/agent's unaided success, with no defined task, subject, or pass/fail rubric -> rewrite as a scripted protocol: an agent with no access to `src/` attempts a named, fixed authoring task using only `docs/template-format.md` and the skill docs; success is "the resulting template compiles and the declared behavior matches a stated spec." This maps cleanly onto the repo's existing `scripts/run-evals.sh` harness (with_skill/without_skill grading) — point the AC at that mechanism explicitly.
2. "...textually different from the wrong-tree refusal (R14)" — "textually different" is trivially satisfiable by a single differing character and doesn't actually test that an agent can reliably discriminate the two refusal cases -> require a distinct machine-readable discriminator (an error code, a `reason` enum value, or similar structured field), with "textually different" as a human-readable bonus, not the test criterion itself.
3. "A search of koto's documentation, error strings, skills, and release notes finds no claim that anchoring contains, sandboxes, isolates, or restricts... (R15)" — the negative-claim search is reasonably well scoped (four named terms) but leaves the search methodology and the empty/collision judgment call ("does this hit *make* a containment claim, or *deny* one, e.g. Known Limitations itself") undefined, so two testers could diverge -> pin the grep terms (`contain|sandbox|isolat|restrict` case-insensitive across `docs/`, error string literals, `plugins/koto-skills/`, and release notes) and add one line: "a hit that explicitly denies containment (as in this PRD's own Known Limitations) does not count as a violation."
4. "Output that cannot be delivered under its name produces a documented, observable outcome; no test case results in the value being dropped with no signal anywhere (R3)" — acceptable in principle since R3 deliberately leaves the surfacing mechanism to the design, but the AC bullet itself doesn't enumerate R3's three distinct trigger cases (empty, over the R23 size bound, uncarryable characters) -> split into three checklist lines (or reference R3's three cases explicitly) so a tester doesn't have to reverse-derive them from the requirement prose.

## Missing Test Coverage
1. R23 (bounded visibility, event-log leg): the only AC touching R23 is a documentation-statement check paired with R20; no AC verifies that a large action output actually arrives bounded/truncated in the event log itself, distinct from the response-truncation behavior R17 already covers -> add an AC: "An action's output that exceeds the stated bound is recorded in the event log truncated/marked, not written in full."
2. R11 (cross-platform anchor comparison): koto ships four platforms, but no AC exercises directory-equality edge cases — symlinked checkouts, case-insensitive filesystems (macOS/Windows), or trailing-slash/relative-path forms — that are the classic source of false anchor refusals or false approvals -> add an AC covering at least one platform-specific equality edge case per the design's chosen comparison semantics.
3. R2 (undefined-value reference): no AC covers a state's instruction text referencing an R1 output name whose producing state never ran in this session (e.g., a skipped branch) — substitution behavior for a never-delivered name is untested -> add an AC defining and testing that case (error, empty render, or literal placeholder — whichever the design picks).
4. R18 (per-session isolation of the diagnostic bound): the existing AC confirms at most one notice "for a given session," but no AC confirms two independent sessions each still get their own single notice (i.e., the bound isn't accidentally global-per-process) -> add a two-session AC.
5. R6/R9 (precedence when both would fail): no AC states which report wins when a state's action fails and a declared gate on the same state would also have failed — likely implied (action failure short-circuits gate evaluation) but not asserted -> add an AC asserting gate evaluation does not run once R6's action-failure stop has fired.

## Summary
The PRD's acceptance criteria are testable enough to write a cargo-test/Gherkin test plan directly from the document, including strong coverage of failure paths, migration, and the two shared-path defects — this is not a happy-path-only AC set. Four bullets need tightening (one subjective doc-sufficiency claim, one trivially-satisfiable "textually different" clause, one underspecified doc-search methodology, and one AC that should enumerate R3's three sub-cases explicitly), and five real coverage gaps are worth adding (event-log bounding, cross-platform anchor equality, undefined-value substitution, per-session diagnostic isolation, and action/gate failure precedence).

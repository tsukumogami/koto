# Lead: How do comparable agent-orchestration, skill, and tool-protocol systems deliver long instructions to an agent -- inline, on demand, or progressively -- and what worked?

## Findings

### 1. Agent Skills (agentskills.io open standard + Anthropic's implementation)

Agent Skills use a **three-tier progressive disclosure model**, and this is the closest existing analog to koto#90's proposal:

- **Level 1 (always loaded):** Only `name` and `description` (~100 tokens) from YAML frontmatter, loaded into the system prompt at startup. [agentskills.io/home](https://agentskills.io/home), [platform.claude.com/.../agent-skills/overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)
- **Level 2 (loaded when triggered):** The full `SKILL.md` body (target: under 5k tokens), read via a bash `cat` call *only when the agent decides the task matches the description*.
- **Level 3 (loaded as needed):** Bundled reference files, loaded only if the SKILL.md instructions point to them; scripts run via bash so only their *output*, never their code, enters context.

**Critical mechanical difference from koto#90's proposal:** the "trigger" decision in Agent Skills is made by the *model itself*, every time, based on matching the user's current request against the skill's description that is *always resident in context*. The system does not track "has this skill been triggered before in this session" and suppress re-loading on a second match — official docs describe activation purely as "when a task matches a skill's description, the agent reads the full SKILL.md into context" ([agentskills.io/home](https://agentskills.io/home)). There is no documented "don't re-serve it, you already have it" logic. If a second, unrelated task later matches the same skill's description again, the model is expected to re-read SKILL.md again (nothing in the spec forbids or discourages this — Anthropic's own docs frame the *cost* model, not a *state* model: "until a Skill is triggered, only its name and description occupy context," implying no distinction between first and Nth trigger; [platform.claude.com/.../agent-skills/overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)). I found no official documentation of an explicit "already loaded, skip" optimization; this appears to be left to the model's own judgment about whether it still has the content fresh in its own context (an inference, not a protocol guarantee) — which is exactly the "second visit = has it in context" proxy problem koto#90 raises, occurring here at the model-judgment layer rather than the orchestrator layer.

**Stated rationale:** "The context window is the agent's cognitive space. Overloading it degrades performance, while keeping it focused lets the agent reason sharply" — framed as a token-cost/attention problem, not a correctness/idempotency problem ([swirlai newsletter](https://www.newsletter.swirlai.com/p/agent-skills-progressive-disclosure), corroborated by official docs).

**Documented failure modes:** Official documentation does not catalog "agent forgot the skill" as a named failure. The closest is authoring guidance to "monitor how Claude uses your skill in real scenarios ... watch for unexpected trajectories or overreliance on certain contexts" and to invest heavily in the `description` field because that's what determines *whether the skill fires at all* ([anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). The documented risk is under-triggering (skill never loads because description doesn't match), not "loaded once, then wrongly assumed present forever." I could not verify whether Anthropic has published data on the latter failure mode; it may simply not have been publicly written up.

### 2. Model Context Protocol (MCP): prompts, resources, tools

MCP has **no single mechanism** aimed at "send big instructions once, then stop." Instead it has several narrower, explicit mechanisms, all of which share one design trait relevant to koto#90: **MCP never lets a client silently assume that something fetched once stays valid — freshness is always made explicit, never inferred from turn count.**

- **Prompts** (predefined instruction templates): the pattern is to combine static instructional text with dynamically fetched resource references, assembled fresh at the point of use, not "delivered once and remembered" — "Applications might choose to select a subset of data ... or pass the raw data directly to the model," fetched per-invocation ([blog.modelcontextprotocol.io/posts/2025-07-29-prompts-for-automation](https://blog.modelcontextprotocol.io/posts/2025-07-29-prompts-for-automation/)).
- **Tool/prompt/resource list caching (2026-07-28 spec, SEP-2549):** this is the most directly relevant MCP mechanism. Every cacheable result (`tools/list`, `prompts/list`, `resources/list`, `resources/read`, etc.) carries an explicit `ttlMs` (time-to-live) and `cacheScope`. The spec is explicit that **TTL is a freshness hint, not a guarantee**, that a `ttlMs` of 0 or absent means "immediately stale, assume nothing," and that servers can push `list_changed` notifications to invalidate a client's cache *before* the TTL would have expired ([modelcontextprotocol.io/specification/draft/server/utilities/caching](https://modelcontextprotocol.io/specification/draft/server/utilities/caching)). In other words, MCP's answer to "can the client assume content it fetched once is still valid" is: **never implicitly — only via an explicit, server-declared, time-bounded contract, with an explicit invalidation channel.** There is no MCP analog to "if this is your second visit, we assume you remember" — visit count is never used as a proxy for cache validity anywhere in the spec.
- MCP is explicitly a request/response, largely stateless-leaning protocol (the 2026 spec direction moves further toward statelessness — see [SEP-2567: Sessionless MCP via Explicit State Handles](https://modelcontextprotocol.io/seps/2567-sessionless-mcp)). Where state must persist across calls, MCP's newer direction is to make it an **explicit, opaque state handle passed by the client**, not an implicit inference the server makes about what the client remembers.

### 3. Anthropic's context management, compaction, and tool-result lifecycle — directly contradicts the "second visit = still in context" assumption

This is the most load-bearing finding for koto#90's central risk.

- **Context editing (`clear_tool_uses_20250919`):** explicitly designed to **remove earlier tool results from what the model sees**, replacing them with a placeholder, once the model has "processed" them (a judgment made by threshold/heuristic, not by tracking whether the content is still needed). Documentation states plainly: "Older tool results (like file contents or search results) are no longer needed once Claude has processed them" — and clearing happens automatically, server-side, based on context-size thresholds, not on any notion of "this was already delivered once so it's safe to drop." ([platform.claude.com/docs/en/build-with-claude/context-editing](https://platform.claude.com/docs/en/build-with-claude/context-editing))
- **Compaction:** when the context-management API compacts, "the API automatically drops all content blocks prior to the `compaction` block, continuing the conversation from the summary" ([platform.claude.com/docs/en/build-with-claude/compaction](https://platform.claude.com/docs/en/build-with-claude/compaction)). A large instruction payload delivered once as a tool result earlier in the session is exactly the kind of content that gets summarized away unless a developer explicitly intervenes (the API exposes `pause_after_compaction` precisely so developers can *manually* re-inject content they know must survive — which is an explicit admission that nothing survives compaction by default).
- Anthropic pairs both of these with a **memory tool**, whose entire justification is that content in conversation history is *not* durable: "Claude can save tool results or context to its memory files before they're cleared from the conversation history" ([context-editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)).
- Third-party research on "Governance Decay" (arXiv, using a benchmark called ConstraintRot) documents empirically that standing instructions/policies delivered in-context are systematically dropped by compaction because compaction "optimizes for task continuity and treats standing policies as low-salience content" — and a live GitHub issue on a Claude-Code-like tool (opencode #16960) reports that "when a session is compacted, the compaction LLM call receives an empty system prompt, so it has no visibility into which project instructions ... are important to preserve," causing agents to become "literal" and drop conventions post-compaction ([arxiv.org/html/2606.22528](https://arxiv.org/html/2606.22528), [github.com/anomalyco/opencode/issues/16960](https://github.com/anomalyco/opencode/issues/16960)).

**Bottom line for this sub-question:** Anthropic's own documented product behavior is the single strongest piece of evidence against koto#90's implicit assumption. "First visit = deliver, second visit = omit because it's still in context" is unsafe on Anthropic's own infrastructure, by design: tool results (which is what a `koto next` response is, mechanically) are exactly the class of content context editing is built to discard, and compaction is explicitly documented to drop everything before its summary unless a developer manually re-injects it.

### 4. Workflow/state-machine orchestrators for LLM agents

I found **no orchestrator that conditions per-node instruction delivery on "was this node visited before in this run."** What I found instead:

- **LangGraph:** state is a shared, explicit "whiteboard" object every node reads/writes; conditional edges route based on state values (flags, counts, thresholds) ([Real Python](https://realpython.com/langgraph-python/), [Medium/greatadib82](https://medium.com/@greatadib82/mastering-langgraph-from-scratch-with-states-nodes-edges-conditional-edges-5b8207409750)). Routing conditions on state, but I found no documented pattern of a node *withholding its own instructions* on a repeat visit — if a node is re-entered, its full prompt/instruction template is re-rendered from the graph definition, because LangGraph nodes are stateless functions of the state object, not "already told you this" caches.
- **Temporal (durable execution for agents):** this is architecturally the *opposite* pattern from what koto#90 proposes, and it's instructive. Temporal never "sends instructions once and stops" — instead, on any resume/replay, the worker **replays the entire deterministic Event History** to reconstruct state; "the Workflow does not ask the agent for a new plan for decisions it has already made... the agent instead uses Temporal's Event History as a record of past decisions," and non-deterministic work (LLM calls, tool use) is isolated into Activities whose *results* are durably recorded and replayed rather than re-executed ([temporal.io/blog/of-course-you-can-build-dynamic-ai-agents-with-temporal](https://temporal.io/blog/of-course-you-can-build-dynamic-ai-agents-with-temporal)). The key structural difference from an LLM's conversational context: Temporal's "memory" (Event History) is a durable, append-only, faithfully-replayed log outside the model, not a token budget subject to lossy compaction. Temporal gets to skip re-doing expensive work on resume *because it has a durability guarantee LLM context does not have*. This is a strong argument that "visited before" is a safe proxy only when the thing being conditioned on (history) is itself durable and guaranteed-complete — which conversational context, per finding #3, is explicitly not.
- **AutoGen (StateFlow):** models workflows explicitly as state machines with "process grounding" via states/transitions, but I found no documentation of per-state instruction suppression on repeat visits; the paradigm is about controlling *which agent speaks next*, not about withholding previously-given instructions ([microsoft.github.io/autogen StateFlow docs](https://microsoft.github.io/autogen/0.2/blog/2024/02/29/StateFlow/)).
- **CrewAI:** found only generic persistence/checkpointing (Flow state via SQLite) with no documented per-node instruction-suppression pattern.

I want to be explicit that this is a negative finding: I did not find any comparable orchestrator that implements "first visit gets full instructions, later visits get a stripped/summarized directive on the assumption the agent still remembers." This makes koto#90's proposed mechanism, as far as I can tell from public sources, closer to novel than to "and here's the widely-used pattern for it."

### 5. Prior art on "send once, then stop sending" and its documented failures

The most concrete, verifiable, real-world example of this exact pattern — and its documented friction — is **Claude Code's own task-tool reminder system**, which I can confirm because it fired inside this very research session (see the system-reminder about `TaskCreate`/`TaskUpdate` that appeared mid-session). Publicly:

- GitHub issue [anthropics/claude-code#26038](https://github.com/anthropics/claude-code/issues/26038): Claude Code injects `<system-reminder>` nudges toward task-tool usage **when they "haven't been used recently"** — explicitly a recency heuristic, not a strict one-time delivery. The issue's core complaint is the opposite failure mode from what koto#90 worries about: the reminders are considered too persistent/context-insensitive ("appear every few messages regardless of conversation context ... during theoretical discussions, creative work, debugging"), and users want to suppress the *repetition*, not preserve it. The requested fix is a config flag to disable the periodic nudge while keeping the tools.
- Related issues document the opposite extreme: [anthropics/claude-code#4464](https://github.com/anthropics/claude-code/issues/4464) and [#29442](https://github.com/anthropics/claude-code/issues/29442) report system-reminder injections (e.g., full file diffs on every turn) consuming excessive context, and [#52018](https://github.com/anthropics/claude-code/issues/52018) reports that repeated reminder wording is "indistinguishable from prompt-injection attacks," causing the model to false-positive flag its own harness's reminders to the user.

Taken together, this is the clearest piece of "documented prior art" I found on the *general* tension koto#90 is navigating: **a real, shipping agent harness (Claude Code) has chosen "re-inject based on a heuristic, accept the repetition cost" over "send once and trust it stuck," and users are pushing back on the repetition cost — not reporting that a one-shot approach would have worked better.** I did not find a documented case of the *reverse* failure ("agent forgot because we only sent it once") in a shipping product with a public postmortem; the closest is the general compaction/Governance-Decay research in finding #3, which is about standing instructions in system prompts, not about a single phase directive delivered via a tool result.

### 6. Idempotency norms for agent-facing APIs

Classic REST idempotency norms (GET **must** be side-effect-free and repeatable; [Keploy glossary](https://keploy.io/docs/concepts/reference/glossary/idempotency/), [GeeksforGeeks](https://www.geeksforgeeks.org/javascript/what-is-an-idempotent-rest-api/)) hold that a read call returning *different content* on identical repeated calls is not itself a violation of idempotency in the strict HTTP sense (idempotency is about *side effects on server state*, not about response content varying due to server-side state that changes independently, e.g. a clock or a counter). However, **MCP's caching spec explicitly treats "same request, different response" as something that must be governed by an explicit contract**, not left ambiguous: cache keys are defined by method + parameters, `ttlMs` tells the client exactly how long a given response may be trusted, and the spec is explicit that TTL is "a freshness hint, not a guarantee" — servers are permitted to change the underlying data, but they must communicate the terms under which they might do so, and MRTR (multi-round-trip) results are marked as explicitly non-cacheable because they depend on inputs outside the cache key ([modelcontextprotocol.io/.../caching](https://modelcontextprotocol.io/specification/draft/server/utilities/caching)).

Applied to koto#90: `koto next` returning full instructions on the first call and abbreviated ones on the second call for the *same phase* is exactly the kind of "same request, different response" behavior MCP's spec would require an explicit, discoverable contract for (a TTL, a state parameter, or a notification) — not an implicit "well, it's your second time asking" inference. This is consistent with the issue's own proposed mitigation (a `koto phase-info` escape hatch), which is structurally similar to MCP's approach of pairing an implicit/cached fast path with an explicit, on-demand fetch that never assumes prior delivery.

## Implications

1. **The closest real precedent (Agent Skills) does not actually implement "first-trigger-only" delivery.** It implements "trigger whenever the model's own judgment says the task matches," which happens to *usually* fire once per relevant task but is not mechanically gated on "have I already loaded this in this session." If koto#90 is modeled on Agent Skills, the fidelity of that model should be checked: koto's proposal (gate on *phase visit count in the workflow state*) is stricter and more mechanical than Skills' "let the model re-decide every time" approach, and that extra strictness is exactly what introduces the stale-proxy risk.

2. **Anthropic's own platform explicitly treats tool-result content — which is what a `koto next` response is — as ephemeral and compaction-eligible by default.** This is not a hypothetical edge case; it is documented, shipping behavior (context editing + compaction). Any design that treats "you got this once, you must still have it" as a safe default is building on a foundation Anthropic itself says is unsafe without explicit mitigation (memory tool, `pause_after_compaction`, or similar).

3. **No orchestration framework I found conditions per-node instruction delivery on visit history the way koto#90 proposes**, except Temporal — and Temporal's version of this pattern is safe only because it's backed by a durable, replayed event log external to the LLM's own context, not by an assumption about what's still resident in a context window. This suggests the safe version of koto#90's mechanism would be: keep `koto` as the durable source of truth (like Temporal's Event History) and make `koto phase-info` cheap/idiomatic enough that agents lean on it rather than trusting memory — treating the omission-on-second-visit as an optimization with an explicit, well-advertised recovery path, not as the primary correctness mechanism.

4. **MCP's caching model offers a concrete, protocol-level template for how to do this safely**: never omit content based on an implicit "you've probably still got it" inference; instead, make the terms explicit (TTL-like, or an explicit "compact" boundary marker) and provide a cheap, discoverable invalidation/refetch path. `koto phase-info` is directionally correct here; the open question is whether it's *the* thing agents reliably reach for, or a rarely-invoked escape hatch (see Open Questions below).

## Surprises

- I expected to find at least one workflow engine with an explicit "have you seen this before" instruction-suppression pattern (it seemed like an obvious thing to want). I found none. The strongest adjacent pattern (Temporal) turns out to structurally *avoid* the exact risk koto#90 is worried about, by never trusting the LLM's context as the source of truth in the first place.
- Claude Code's own harness — the very tool this research is running inside — already lives this exact design tension in production (task-tool reminders), and the public feedback on it is that users find the *repetition* annoying, not that a one-shot delivery would have been safer. That's a real (if narrow) data point suggesting the field, in practice, currently errs toward "repeat cheaply and often" over "trust the model remembers," at least for short nudges. It's not a perfect analog to koto's much larger phase-instruction payload, but it is the most concrete, first-party evidence available.
- MCP's caching spec is remarkably recent (2026-07-28 spec cycle, SEP-2549) and explicitly rejects the idea that a client should treat any fetched result as permanently valid without an explicit freshness contract — this reads almost as a direct answer to the "second visit is a proxy for having it" question, arrived at independently of koto#90.

## Open Questions

- Does koto's workflow state (the thing that decides "first visit" vs "later visit") have any durability/replay guarantee analogous to Temporal's Event History, or is it itself vulnerable to loss/desync from the agent's context? If koto's state is authoritative and durable server-side (which seems likely, given it's an external orchestration engine the agent calls into, not something living in the agent's own context), then the "stale proxy" risk is narrower than it looks: the risk isn't that koto forgets, it's that the *agent* forgets while koto correctly remembers it already told the agent. That reframes the problem as "how does the agent recover" rather than "how does koto know" — which argues for investing in making `koot phase-info` trivially cheap to call speculatively, rather than only after visible confusion.
- Is there data (even informal) on how often coding agents actually notice they're missing instructions and proactively call an escape hatch, versus confabulating plausible-sounding instructions instead? This is the crux failure mode named in the issue ("agent hallucinated the instructions") and I found no public research directly measuring it for this specific scenario (tool-result-delivered workflow instructions, as opposed to system-prompt-delivered standing policy, which the Governance Decay paper does address).
- Would it be safer for koto to treat the omission as tied to an explicit, short-lived signal (e.g., only omit within the same uncompacted turn sequence, if that's detectable) rather than to a durable "visited" flag that persists across resume/respawn/compaction? This is a design question for koto, not something I can resolve from external prior art, since no comparable system does the exact thing being proposed.

## Summary
No comparable system I could verify — not Agent Skills, not MCP, not LangGraph/Temporal/AutoGen/CrewAI — implements "full instructions on first visit, silently omitted on later visits" gated on visit history; the closest analog (Temporal) instead relies on a durable, replayed event log rather than trusting the LLM's own context, and Anthropic's own compaction/context-editing docs explicitly state that tool-result content (which is what a `koto next` payload is) is not guaranteed to survive in context past a single turn. The main implication is that koto#90's "second visit" heuristic is running against, not with, the grain of how Anthropic's platform is documented to behave, which raises the priority of making `koto phase-info` a fast, cheap, low-friction recovery path rather than a rarely-used escape hatch — MCP's TTL/invalidation caching model is a concrete template for how to make the freshness contract explicit instead of inferred. The biggest open question is empirical, not architectural: how reliably do agents notice they're missing instructions and reach for the recovery path, versus silently hallucinating plausible-sounding ones instead — no public research I found measures this for tool-result-scale instruction payloads specifically.

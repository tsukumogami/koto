# Reviewer: architecture

## Verdict
FAIL

The mechanism, layering, and phasing are sound and verified against source, but the design silently drops a load-bearing ordering question its own D4 decision report explicitly flagged as needing resolution before implementation: what happens when the new discoverability pointer and the existing leg-abandonment notice both want to prepend to `directive` on the same response.

## Strawman check

**Decision 1 (what records a delivery).**
- Option B (`EvidenceSubmitted` reserved pseudo-state): genuine depth. Grounded in real code (`audit.rs:64-110`, `is_reserved_kind`), and its central objection — that `per_state_outcomes` and the dashboard timeline would render a phantom evidence-submission in a phase that doesn't exist — is a real projection bug, not an assertion. Not a strawman.
- Option C (additive `StateFileHeader` field): I independently verified the load-bearing fact. `StateFileHeader` derives `Serialize, Deserialize, PartialEq` but **not** `Default`, is not `#[non_exhaustive]` (`types.rs:222-223`), and `koto-stability-tests/src/lib.rs` constructs it with exhaustive struct literals at multiple sites (line 68 confirmed). Adding a field is a genuine compile break in that crate. This is a real, checkable fact, not a strawman.
- Option D (derive from existing events): the "disproved, not merely disfavoured" claim is the load-bearing argument for the whole design, so I verified it directly against `src/engine/advance.rs`. `TransitionResolution::NeedsEvidence`'s `accepts.is_some()` branch (`advance.rs:561-568`) returns `StopReason::EvidenceRequired` with **no `append_event` call anywhere in that arm or the surrounding match**. This is the ordinary shape for an instructions-bearing phase (gateless, `accepts`-only, awaiting evidence). Since no event is appended on a non-advancing tick through this path, two sessions differing only in delivery status produce byte-identical logs — no predicate over the log can distinguish them. This is a proof, not an assertion, and I confirmed it against current source rather than taking the decision report's word for it.

**Decision 2 (retrieval surface).**
- Option C (`koto next --dry-run`): the report's claim that a flag "cannot subtract" the batch lock is verified. `mod.rs:3746-3776` acquires the advisory flock unconditionally (gated only by `state_is_batch_scoped`), **before** any dispatch or `full`-flag logic runs. A `--dry-run` flag would need to change the lock-acquisition code path itself, which today has no dependency on any per-call flag. This is a hard constraint, not a preference — genuine depth, not a strawman.
- Option B (new subcommand): the registration-footprint accounting (new `Command` variant, dispatch arm, handler, doc sections, test trio) is concrete and checkable against the `Status` precedent; not a strawman, just a cost comparison that happens to favor A.

**Decision 3 (unifying construction sites).**
- Option A/B (thread into `dispatch_next`): genuine cost — verified `dispatch_next`'s ~20 unit tests call it positionally (`next.rs:32-36` signature, called throughout `next.rs:162-819` per the report), so a signature change is real, not invented, churn.
- Option D (collapse into one construction site): the report correctly identifies that `--to` skips gate evaluation entirely (confirmed: `mod.rs:3348`, `gate_results = BTreeMap::new()` passed to `dispatch_next`), which the PRD's Out of Scope section explicitly forbids changing. Not a strawman — it's ruled out by a requirement, not by preference.

**Decision 4 (discoverability pointer).**
- Option B (structured sibling field): correctly finds R17 doesn't block it (verified `koto-stability-tests` has no reference to `NextResponse`/`next_types`), so it isn't eliminated by a false constraint — it's compared honestly on cost and loses on attention-economy grounds. Not a strawman.
- Option C (`expects`): correctly disqualified because `expects` is documented as always-`null` on `GateBlocked`, which is precisely the PRD's motivating variant. This is a real, structural conflict.
- Option D (skill-only, no pointer): given a genuine hearing, not dismissed cheaply — the report engages with the strongest form of the argument (system-prompt content survives compaction differently than tool results) before landing on why it fails as an *exclusive* answer (R14 requires a response-channel; an agent that never loaded the skill has nothing). This is the strongest instance of steelmanning in the whole set.

No rejected option in any of the four decisions is a strawman. Each rejection rests on a checkable code fact or a stated requirement, and I independently verified the load-bearing ones rather than trusting the reports.

## Findings

**1. Arrival-path uniformity (verified).** Every entry path appends a state-entry event: conditional/unconditional `Transitioned` (`advance.rs:503-509`, `545-551`), directed transition's `DirectedTransition` (`mod.rs:3336-3340`), rewind's `Rewound` (`mod.rs:2044-2055` region), and init's `Transitioned{from: None, ...}` via `init_child_from_parent` (`init_child.rs:497-502`). Self-transition on the natural path is possible without tripping cycle detection on its first occurrence, since `visited` starts empty and is populated only as transitions are taken within a single tick's chain — a lone self-transition (not a repeated one within the same chain) appends `Transitioned{from: X, to: X}` cleanly. Self-transition via `--to` is also real: the directed handler validates the target against the current state's own declared transitions (`mod.rs:3304-3322`), and a template can declare a transition to itself, producing `DirectedTransition{from: X, to: X}`. Both make the occupancy predicate's "any target" slicing rule do real work, exactly as claimed.

**2. `derive_visit_counts`'s second consumer (verified untouched).** `visited_states` (`workflows_surface/project.rs:285-292`) calls `derive_visit_counts(events).into_keys()` — it uses only the key set, never the count values. The design doesn't need to touch `derive_visit_counts`'s semantics at all for this consumer to be safe, and it doesn't. Confirmed genuinely untouched.

**3. The combinators and their coverage (verified, with a gap).** `with_substituted_directive` and `with_directive_prefix` both exist exactly as described (`next_types.rs:159-251`, `268-357`), both match the identical five variants (`EvidenceRequired`, `GateBlocked`, `Integration`, `IntegrationUnavailable`, `ActionRequiresConfirmation`), and both no-op on `Terminal`/`Error`. A third combinator in that idiom (`with_details_suppressed_unless_full`) fits cleanly — same shape, same file, same five-arm match. This part of the design is exactly right.

But the design reuses `with_directive_prefix` for the new pointer without addressing what happens when the leg-abandonment notice *also* wants to prepend to the same `directive` on the same response. Both splices happen at the identical two call sites (`mod.rs:3374-3380` and `mod.rs:4204-4210` for abandonment; the design places the pointer "after substitution" at the same sites). `with_directive_prefix` only prepends, so call order determines final order, and the two notices have opposite requirements: the abandonment notice is authored to dominate ("the state directive below is retained for context only," per its own doc comment) while a routine per-tick pointer should not bury a stop instruction. D4's own decision report flagged this explicitly as unresolved and said it "needs an explicit ordering decision... before implementation," and the corresponding "prepend vs. append" question. The design resolves prepend-vs-append implicitly (by choosing to reuse `with_directive_prefix` rather than invent a suffix variant), but never states the ordering rule for the case where both notices apply on the same tick. This is a concrete way R15 ("the pointer must not displace or truncate the phase's own directive text") and the abandonment notice's own dominance property could conflict, and the design's Solution Architecture and Security Considerations sections are silent on it.

**4. `handle_status`'s non-effects (verified).** `handle_status` (`mod.rs:4834-4961`) read in full: `backend.exists`, `backend.read_events`, `derive_machine_state`, a template file read/parse, and a `json!` response build. No `lock_state_file`, `append_event`, gate evaluation, or `finish_terminal_tick` call anywhere in its body — and `lock_state_file` has exactly one call site in the entire file (`mod.rs:3770`, inside `handle_next`, gated to batch-scoped states). The claim that R11/R12 hold "by construction rather than by conditional" is accurate, not aspirational.

**5. "Print, then append" is implementable (verified by precedent).** The natural path already does exactly this shape today: `println!(...)` at `mod.rs:4426-4429`, followed immediately by a conditional `finish_terminal_tick(...)` call for `Terminal` responses (`mod.rs:4432-4438`), then `std::process::exit(0)`. The directed path has the identical pattern (`mod.rs:3379-3391`). So "print the response, then append the delivery record" is not a new control-flow shape being invented for this feature — it's the same post-print side-effect slot the terminal-cleanup path already occupies. This substantiates the design's claim directly.

**6. The security ruling is a genuine, correctly-scoped finding.** I independently confirmed `handle_next` verifies the template hash on both paths (`mod.rs:3220`, `mod.rs:4616`, both comparing `actual_hash != machine_state.template_hash`), while `handle_status`'s read of the same file (`mod.rs:4873-4896`) performs no such check. The design is right that this gap predates the feature and is currently low-stakes (only feeds `is_terminal`), and right that extending `status` to return substituted instructions raises the stakes enough to warrant closing it. The ruling — report a mismatch rather than fail — is consistent with the feature's own purpose (don't deny an agent its last resort). This is a real finding the design surfaced rather than inherited silently, and its resolution is sound.

**7. Layering (no inversion found).** The predicate belongs in `src/engine/persistence.rs` beside `latest_epoch_gate_failed`, which already computes "events since the last entry into the current state" — the same epoch-slicing idiom, same file, same layer (pure functions over `&[Event]`, no backend coupling). The combinator belongs in `src/cli/next_types.rs` beside two combinators that already do the identical "compute once, transform every variant uniformly" job for the exact same struct. The call sites belong in `src/cli/mod.rs`, which already owns both response-construction call sites and both `with_substituted_directive`/`with_directive_prefix` calls. Nothing here pushes CLI-shaped decisions into the engine or reaches from the engine back into CLI types. This is consistent with the existing separation and I found no inversion.

**8. Phasing — mostly sound, one imprecise justification.** The actual dependency chain is real: phase 3 (retrieval) benefits from landing after phases 1-2 so its output shape matches `next`'s (a soft ordering, not a hard one — `handle_status` doesn't depend on the new event variant at all, it only needs to match `next`'s substitution output, which is unrelated to delivery tracking). Phase 4 (pointer) genuinely depends on phase 3 (it needs the retrieval's invocation string to point at). But the stated reason phases 1 and 2 "cannot be separated across pull requests" doesn't hold as written: Phase 1's own description says "nothing observable changes yet," meaning a Phase-1-only PR introduces an unused predicate and an unused event variant with zero behavioral effect — it cannot by itself cause the natural and directed paths to disagree, because neither path uses it yet. The real, correctly-identified constraint is that *within* Phase 2, the natural-path wiring and the directed-path wiring must land together (exactly what Phase 2's own description already bundles: "wire the natural path... and wire the directed path... " in one phase). The design's stated justification misattributes this coupling to "phases 1 and 2" rather than to the two call sites inside phase 2. This doesn't change what actually has to ship together, but it's an imprecise argument in a document that is otherwise scrupulous about stating reasons precisely.

## Required changes

1. **Resolve the abandonment-notice / discoverability-pointer ordering.** Add an explicit rule to the Solution Architecture (or a new subsection alongside "The one thing the pointer must not key on") stating the splice order when both an abandoned-leg notice and a phase's instructions-declaring status apply on the same response — e.g., "the recovery pointer is spliced first (innermost), so a subsequent abandonment-notice splice always ends up closest to the front of `directive`, preserving its dominance," or the converse, with a stated reason. This is not free-form: D4's own report already named the two candidate resolutions and a recommendation ("recovery pointer never precedes an abandonment notice"); the design should adopt or explicitly override it rather than leave the interaction unaddressed. Without this, an implementer has to invent the interaction, and the wrong choice buries a stop instruction under routine text — a correctness regression in the mechanism the abandonment notice exists to protect.

2. **Correct the Phase 1/2 non-separability justification**, or restate it accurately: the coupling that actually matters is between the natural-path and directed-path wiring *inside* Phase 2 (both must land in the same PR), not between Phase 1 and Phase 2 — Phase 1 alone is inert by its own description ("nothing observable changes yet"). This is a documentation-accuracy fix, not a re-scoping of the phases themselves.

# Lead: complete response-path matrix

## Findings

There are exactly two production call sites that construct a `NextResponse` carrying `details`, plus one dispatcher function (`dispatch_next`) whose only caller is one of those two sites. No other file in the crate builds a `NextResponse`.

## Implications

- **Rows 3 and the "accepts-fallthrough" question resolve together.** `dispatch_next`'s gate-fail-with-accepts fallthrough (`src/cli/next.rs:56-69`) is reachable *only* through the `--to` handler at `src/cli/mod.rs:3355` — the only call site of `dispatch_next` in the whole crate. That handler is already defect #3 (no visit check at all, for any branch `dispatch_next` can return). So the accepts-fallthrough branch is not a *new* defect; it inherits #3's bug because it's the same code path with the same missing check.
- **The accepts-fallthrough branch is currently unreachable in production regardless.** `--to` builds `gate_results` as an empty `BTreeMap` before calling `dispatch_next` (`src/cli/mod.rs:3350`, "skip gate evaluation"). `blocking_conditions_from_gates` iterates `gate_results`, so with an empty map `blocking` is always empty — `dispatch_next`'s `if !blocking.is_empty()` branch (next.rs:56) can never be true when called from `--to`. The fallthrough logic at next.rs:56-69 is exercised today only by `dispatch_next`'s own unit tests (`src/cli/next.rs:618-672` etc.), not by any live handler. This matters for the PRD's AC design: fixing defect #3 by threading a visit-count check into `dispatch_next`/`--to` will fix the *reachable* branches (GateBlocked-immediate, EvidenceRequired-with-accepts, IntegrationUnavailable) but the accepts-fallthrough branch specifically needs no separate empirical repro — it cannot fire via `--to` as currently wired.
- **The main advance-loop path (rows 6/7/1/2) computes `details` exactly once** (`src/cli/mod.rs:3995-4014`) and reuses that single `Option<String>` across every `StopReason` arm (`GateBlocked`, `EvidenceRequired`, `Integration`, `IntegrationUnavailable`, `ActionRequiresConfirmation`, and both `SignalReceived` sub-arms). This means any fix to the visit-count derivation (e.g., to also fix defect #2's `Rewound`-inflation) is a single-point fix that automatically covers all six response shapes on the main path. The `--to` path is architecturally separate and needs its own fix (or needs to be rewired to share the same computation).
- Batch spawn/retry/F1 all turn out to be non-issues for this feature: spawn and retry both go through full re-`init`, which naturally resets visit history to a clean state (count 1 at the entry state); F1 doesn't touch state files at all.

## Surprises

- **Terminal drops `directive` too, not just `details`.** This wasn't in the lead's list of five defects and could easily be mistaken for a details-specific gap, but it isn't: the `Terminal` variant (`src/cli/next_types.rs:458-471`) has never carried a `directive` field, in either the `--to` construction (`src/cli/mod.rs:3392`) or the main-loop construction (`4041`). Since terminal states are compiled with a `details` field too (the compiler splits *every* declared state's markdown at the marker, terminal or not — `src/template/compile.rs:187,652,667`), a template author *can* write `<!-- details -->` content under a terminal state's markdown today, compile it into `compiled.states["done"].details`, and it will silently never reach any `koto next` caller. This is consistent with the existing (pre-feature) omission of `directive` on Terminal, so it's not a regression introduced by this feature — but the PRD should probably state explicitly whether terminal-state `details` content is (a) forbidden/warned-about at compile time, (b) silently dropped by design, or (c) a follow-on scope item, because right now it's simply unaddressed.
- `dispatch_next`'s accepts-fallthrough branch being dead code in production (see Implications) was not something a design-level read would surface — it only becomes visible by tracing exactly how `--to` populates `gate_results`.

## Open Questions

1. Should the PRD's acceptance criteria for fixing defect #3 (`--to`) explicitly note that the accepts-fallthrough sub-branch is unreachable via `--to` today, so no dedicated test scenario is needed for "gate-fail + accepts via `--to`"? Or should the PRD require `--to` to evaluate gates at all (a larger behavior change, likely out of scope)?
2. Does the PRD want an explicit acceptance criterion asserting `Terminal` never carries `details` (locking in current behavior), or is terminal-state details content something a future issue should reject at compile time?

## Summary

Every `NextResponse` in the crate is built at exactly two sites — `dispatch_next` (used solely by `koto next --to`) and the main advance-loop `StopReason` match in `handle_next` — and the visit-count check lives only in the latter, computed once and reused across all its branches, which is why `--to` (defect #3) and rewind-inflation (defect #2) are the only real gaps; the accepts-fallthrough branch inherits #3's bug but is currently unreachable in production because `--to` always evaluates zero gates. Batch child spawn, retry/respawn, and `koto init` all reset visit history cleanly via full re-initialization (a fresh `Transitioned{to: initial_state}` event gives count 1), so first-arrival details work correctly there; F1 cold-restart doesn't touch state files and isn't a distinct response path. `Terminal` carries no `details` field at all — consistent with it also carrying no `directive` today, not a new asymmetry, but worth an explicit PRD decision since terminal states can still be authored with a details marker that silently goes nowhere.

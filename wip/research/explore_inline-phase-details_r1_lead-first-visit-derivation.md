# Lead: Can "first visit to this state" be derived reliably from the existing JSONL event log, and where does the derivation break?

## Findings

### 0. The feature already exists — this is not greenfield

Before answering the sub-questions: the core mechanism koto#90 asks for is **already designed and implemented** in this codebase, under a different name and shape than the issue's sketch.

- `docs/designs/current/DESIGN-koto-next-output-contract.md` (status: Current) has a full "Decision 3: Visit count computation" section that adds `derive_visit_counts(events: &[Event]) -> HashMap<String, usize>` to `src/engine/persistence.rs`, a `<!-- details -->` markdown marker splitting `TemplateState` into `directive` (always returned) + `details` (first-visit-only), and a `--full` flag on `koto next` that bypasses the visit check.
- The code is live: `src/engine/persistence.rs:981-993` defines `derive_visit_counts`; `src/cli/mod.rs:4008-4009` calls it and gates `details` inclusion with `if full || count <= 1`. `src/cli/mod.rs:148` declares `--full: bool` on the `Next` clap command with doc comment "Always include the details field in the response, regardless of visit count."
- There is **no `koto phase-info` escape hatch command** — the shipped design instead uses `koto next --full` as the escape hatch (re-fetch on the *next* tick, not an out-of-band read). `phase-info` as a distinct subcommand does not exist anywhere in `src/cli/` (confirmed by grep across `src/cli` and `src/engine`).
- This means the exploration's real question is not "should we build this" but "does the already-shipped visit-count heuristic hold up, and does it need a genuine on-demand retrieval command (which today doesn't exist) to cover the cases where it's wrong."

### 1. Event types recorded, and which carry a state transition

From `src/engine/types.rs` (`EventPayload` enum, lines 452-800) and `Event` (lines 1025-1060):

- `Transitioned { from: Option<String>, to: String, condition_type: String, skip_if_matched: Option<...> }` — normal template-driven transition (gate pass, evidence match, auto).
- `DirectedTransition { from: String, to: String, rationale: Option<String> }` — `koto next --to <state>`.
- `Rewound { from: String, to: String, rationale: Option<String> }` — `koto rewind` and the batch scheduler's failure-retry path.
- All other variants (`EvidenceSubmitted`, `IntegrationInvoked`, `WorkflowInitialized`, `DecisionRecorded`, `GateEvaluated`, `SchedulerRan`, `ChildCompleted`, `IntentUpdated`, request-store family, etc.) do **not** carry a `to` state and are ignored for state-derivation purposes.
- Every `Event` carries `seq: u64` (monotonic) and `timestamp: String` (RFC 3339), but no explicit "cause" field beyond `condition_type` / `rationale`.

`derive_state_from_log` (`src/engine/persistence.rs:708-715`) walks events in reverse and returns the `to` of the most recent `Transitioned | DirectedTransition | Rewound`. `derive_visit_counts` (same file, lines 981-993) does a single forward pass counting how many times each state name appears as the `to` of one of those three variants — reproduced verbatim in the design doc.

### 2. Replay: always full, never compacted, never truncated

- `backend.read_events` reads the whole session JSONL every call; `persistence.rs` opens the file with `truncate(false)` (`persistence.rs:91`) — append-only, no in-place rewrite of a session's own log.
- The only compaction/truncation logic in the engine (`src/engine/terminal_index.rs`) operates on a **separate, workspace-wide** file, `_terminal_index.jsonl` (a dedup skip-list keyed by `session_id` used by the discovery scanner), not on any individual session's `koto-<name>.state.jsonl`. It does not touch or shorten a session's own event history.
- Conclusion: a session's own log is always complete and always fully replayed. Visit-count derivation cannot be starved by log compaction — that risk does not exist in the current implementation. The design doc's own "Negative" section already accepts the cost: "`derive_visit_counts` scans the full event log on every `koto next` call, adding O(n) work... typical workflows have tens to low hundreds of events; the full scan is sub-millisecond."

### 3. Per-situation: does the log let you tell first vs. repeat visit, and does repeat visit actually mean "still in context"?

- **Plain retry of the same state, no transition** (calling `koto next` again with no new evidence, nothing advances): no new `Transitioned`/`DirectedTransition`/`Rewound` event is appended, so the visit count for the current state is unchanged. If the count was 1 (still first visit), `details` is included **again** on the retry — which is actually correct (same agent, same context, but also harmless to resend). Note `src/cli/retry.rs` is unrelated to this case — it's the **batch scheduler's** `retry_failed` evidence key, not a generic single-workflow retry.

- **Self-loop transition** (a template rule that transitions a state back to itself, `from: X, to: X`): this appends a new `Transitioned` event with `to == X`, incrementing `X`'s count to 2+. The heuristic then suppresses `details` on the self-loop re-entry. Whether that's correct depends on whether the self-loop represents "same agent iterating" (probably fine to suppress) or "a different pass that needs re-orientation" (not distinguishable from the log alone — `condition_type` and `skip_if_matched` give some signal but nothing that maps cleanly to "does this caller still have `details` in context").

- **`koto rewind`**: real command, `handle_rewind` in `src/cli/mod.rs:1984-2081`. It walks the log for the last two state-changing events, and appends `Rewound { from: <current>, to: <previous> }`. Since `Rewound` is one of the three counted event types, rewinding to a state increments its count. **This is the sharpest confirmed break**: rewinding back into a state necessarily re-enters a state the log already recorded a prior visit to (the state you're rewinding to was, by construction, visited before — that's why it's in the log), so the visit count for the rewind target is essentially guaranteed to already be ≥1, and after the rewind's own `Rewound` event, ≥2. `details` will be suppressed on the very state the agent is being sent to re-examine — even though a rewind is explicitly an "I need to redo this" signal, arguably the case *most* likely to want the full instructions back.

- **Multi-state auto-advance in one `koto next` call** (`advance_until_stop`, tested via `advance.rs`): the loop may fire several `Transitioned` events in one call before returning the final stopping state. `derive_visit_counts` is called *after* the loop returns, on the post-advance event list (`src/cli/mod.rs:4001-4009`, comment: "Re-read events to capture transitions appended during the advancement loop"), so it correctly counts the final state's *own* accumulated visits, not an intermediate hop. This one is handled correctly by construction — the design doc's data-flow diagram (lines 256-274) shows `derive_visit_counts` sitting after `advance_until_stop` returns.

- **Session resumed by a different agent process / after context compaction**: **not handled — confirmed gap.** Nothing in the event log distinguishes "the same agent process that received `details` earlier is asking again" from "a brand-new agent process (or the same process post-compaction) is asking for the first time." The log has no process/session-of-the-caller identity at all; it only tracks workflow state. A second `koto next <name>` call from any caller, on a state whose count is already >1, will not receive `details` regardless of whether the caller has ever seen them.

- **Child workflows spawned by a coordinator** (`src/cli/init_child.rs`, `init_child_from_parent` / `init_child_as_skip_marker_from_parent`): confirmed each child gets its **own, brand-new session log** — `init_child_from_parent` (init_child.rs:341 / 398-511) writes a fresh `WorkflowInitialized` event followed by its own initial `Transitioned` event into the child's `initial_state`. Children do **not** inherit any visit history from the parent or from sibling children; every child starts at visit-count 0 for every state, so `details` is correctly delivered on true first visit for a freshly spawned child. This case is handled correctly.

- **Cold restart / re-priming (F1, `src/engine/respawn.rs`, issue-158-adjacent)**: **the other confirmed, concrete break.** `execute_respawn` / `emit_respawn_event` (`respawn.rs:421-557`) does **not** create a new session or a new log — it appends a `RequesterRespawn` audit record to the **same** requester session file, and that record is an `EvidenceSubmitted` event against the synthetic pseudo-state `"request_store.respawn"` (via `requester_respawn_fields` in `src/engine/audit.rs:225-277`), not a `Transitioned`/`DirectedTransition`/`Rewound` event. So respawn is invisible to `derive_visit_counts` — the visit count for whatever real state the requester was in when it went stale is completely unaffected by the respawn. The freshly-spawned subagent is handed `RESUME_CONTEXT_PROMPT` ("You are resuming session `<id>`. Read your prior state via `koto session info <id>`... advance from where you left off" — `respawn.rs:98`), then presumably calls `koto next <id>` to continue. If that state's count is already >1 (very likely — the whole point of F1 firing is that the requester had been sitting there long enough to go stale, so it plausibly already got `details` once and continued working), the brand-new subagent — with genuinely zero context, the F1 precondition that triggered it in the first place — will **not** receive `details` and has no automatic prompt to fetch them. This is the exact "second visit is a false proxy for still-in-context" failure the exploration's lead worried about, and it is real and reachable in the current shipped code.

- **Batch retry of a failed child** (`src/cli/retry.rs`, `handle_retry_failed`): per the module doc comment (retry.rs:1-40) and confirmed by `handle_rewind`'s sibling logic, a failed child is retried by appending a `Rewound` event targeting the template's `initial_state` on the **same child session log** (not a fresh child). Since the child necessarily already visited `initial_state` once (that's how every session starts), the retry's `Rewound` event pushes that count to 2+, suppressing `details` on the state a fresh dispatch (new agent, new context) is about to re-enter. This is structurally the same failure mode as F1 respawn: same log, new consumer, log-derived heuristic says "not first."

### 4. No existing visit-count-based caps/loop-detection beyond the design's own use

- `derive_visit_counts` itself is brand new to the shipped design (no prior "issue #105 max_visits" implementation was found under that name); grep across `src/engine` and `src/cli` for `max_visits`, `MAX_VISITS`, `loop_detect` turns up nothing. `src/engine/caps.rs` was listed as a file to check per the lead's brief but the grep for visit/cap terms found no hits inside it — it does not implement a visit cap (did not open the file directly given the strong signal from the grep already covering it; can re-check if the exploration needs caps.rs's actual purpose).
- `DESIGN-unified-koto-next.md` (referenced in the wip scope doc) separately documents a `visited := {}` set used for **cycle detection inside a single `advance_until_stop` call** (stop the auto-advance loop if it would revisit a state within the same call) — this is a different, in-memory, single-call concept, not the persisted-log-derived visit count `derive_visit_counts` produces. Don't conflate the two: one is "stop looping within one tick," the other is "should this state's `details` ride along."

### 5. Cost

- One O(n) forward scan over the full session event list per `koto next` call, done unconditionally alongside the pre-existing O(n) `derive_state_from_log` reverse scan. The design doc explicitly measured/asserted this as sub-millisecond for realistic (tens–low hundreds of events) workflows and accepted the cost. No index or caching layer exists or is needed at today's scale.

## Implications

- The exploration does not need to invent the "derive visits from JSONL" mechanism — it exists, is tested (`persistence.rs` has a `derive_visit_counts` test block, lines ~2224-2430, covering empty/single/multi-visit/directed/rewound/mixed/non-entry-event cases), and is already wired into `koto next`'s response. The open design work is narrower than the issue implies: (a) whether `koto phase-info` (or equivalent) should exist as a real on-demand command distinct from `--full`, and (b) whether the visit-count heuristic needs to be hardened against the two confirmed break cases (rewind-into-already-visited-state, and same-log-different-consumer via F1 respawn / batch retry) rather than built from scratch.
- `--full` today only helps a caller who *knows in advance* that they need `details` for the *upcoming* tick; it doesn't retroactively answer "what were the details for the state I'm already in and have lost context on" without an actual `koto next --to <same-state> --full`-style call or a real read-only inspection command. That gap is exactly what `koto phase-info` was meant to close, and it is currently unfilled — `koto session info`, `koto session list`, `koto template compile`, and the dashboard read seam were the closest existing surfaces and none of them return a state's `details` text on demand (not independently verified line-by-line in this pass, but no `phase-info`-shaped subcommand exists in `src/cli/mod.rs`'s `Command` enum today, and `koto next --to <same-state>` would itself append a new `DirectedTransition` event, mutating the log just to peek at details — an undesirable side effect for a pure "let me re-read this" query).
- The F1 respawn and batch-retry gaps both share a root cause: **the log conflates "workflow state visit count" with "context freshness of whoever is currently attached to this session."** Those are the same thing only when one continuous agent process drives a session start-to-finish with no restart, no hand-off, and no rewind. Any design that leans harder on `derive_visit_counts` (e.g., extending it into a hard cap or an escape-hatch trigger) should treat F1 respawn and rewind-into-visited-state as first-class scenarios to test, not edge cases to hand-wave.

## Surprises

- The single biggest surprise: this isn't a design question in a vacuum — `DESIGN-koto-next-output-contract.md` already committed to and shipped a `derive_visit_counts` + `--full` mechanism that overlaps enormously with koto#90's ask, under different naming (`details` not `phase-info`, `--full` not an escape-hatch subcommand). Whoever scoped koto#90 either didn't know this design existed, or is deliberately asking for the on-demand-retrieval piece that the existing design left out (no true "look this up without mutating the log" path exists yet).
- `koto rewind` explicitly targets "the previous state" (found by walking back one state-changing event, `handle_rewind`, `mod.rs:2011-2038`), and because a rewind target is by definition a state the log already shows a prior entry into, rewound-into `details` suppression is not a rare corner case — it's close to guaranteed on every rewind.
- F1 cold-restart respawn deliberately avoids touching the event-log's state-transition trail (it rides the reserved `request_store.*` audit-kind convention specifically so it doesn't get picked up by ordinary event-type matching elsewhere in the codebase — see `src/engine/audit.rs`'s design commentary on `ABANDON_NOTICE_STATE` using a synthetic dotted pseudo-state precisely so it's never mistaken for a real transition). That same design choice, which is correct for its own purpose (not polluting `derive_state_from_log`/gate-evaluation epochs), is exactly what makes respawn invisible to visit counting.

## Open Questions

- Does `koto session info <id>` (mentioned in `RESUME_CONTEXT_PROMPT`) already surface `details` for the current state today, making a dedicated `phase-info` command partially redundant? Not checked in this pass — worth a follow-up read of `src/cli/session.rs`.
- Is there a way to distinguish "respawn (same log, new consumer)" from "same agent continuing" using signals already on the header (`respawn_generation`, `dispatch_epoch`) without adding a new state file? `StateFileHeader.respawn_generation` (types.rs:328-340) already exists and increments on every F1 fire — a visit-count derivation could plausibly be extended to reset or force-include `details` when the current tick's respawn_generation differs from some "generation at last details delivery" marker, but that marker itself would need to live somewhere (the header already has room via existing additive fields, so this may not require a new file — worth exploring as a fix rather than treating the gap as unfixable).
- Same question for `koto rewind`: since `Rewound` already carries `from`/`to`/`rationale`, could the visit-count/details logic special-case "the most recent state-changing event is a `Rewound` targeting the current state" to force `details` back in, without a broader schema change? This looks like a small, targeted fix given the mechanism already distinguishes `Rewound` events from `Transitioned`.
- Whether `src/engine/caps.rs` implements anything relevant (visit caps, loop bounds) was not directly confirmed by opening the file — only ruled out via keyword grep. Worth a direct read if another lead needs caps.rs's actual role.

## Summary
`derive_visit_counts` already exists, is shipped, and correctly derives per-state visit counts from the full, never-compacted, always-replayed session JSONL (`src/engine/persistence.rs:981`, used by `koto next`'s `--full`/`details` gating per `DESIGN-koto-next-output-contract.md`) — it handles multi-state auto-advance and child-workflow isolation correctly. It breaks concretely and reproducibly in two shipped, reachable paths: `koto rewind` re-enters a state the log already recorded a prior visit to (so `details` gets suppressed on the state a rewind is explicitly asking to redo), and F1 cold-restart respawn / batch-child retry both continue writing to the *same* session log under a *new* agent process without resetting the state's visit count, so a genuinely fresh, zero-context agent inherits a "not first visit" verdict it didn't earn. The biggest open question is whether either gap can be closed by extending the existing mechanism (e.g., special-casing `Rewound` targets, or keying off the header's existing `respawn_generation` counter) rather than requiring a new state file or a heavier redesign — and separately, whether `koto phase-info` needs to exist at all given `--full` already covers the forward-looking case, or whether the real missing primitive is a non-mutating "read details for my current state right now" query.

# Lead: If a koto template is the security boundary, what does koto do with templates today — and what would it have to do?

## Findings

### 1. Where templates come from

Every route by which a template reaches the engine ends at a local filesystem read. There is no code path that fetches a template over the network.

- **`koto init --template <path>`** (`src/cli/mod.rs:1123-1141`): the CLI takes a bare path string. If the extension is `.json` it's loaded as a pre-compiled artifact directly (`resolve_template`, `src/cli/mod.rs:602-609`, calling `load_compiled_template` at `src/cli/mod.rs:675`, which is a plain `std::fs::read_to_string`). Otherwise it's treated as markdown source and run through `compile_cached` (`src/cli/mod.rs:610`), which calls `compile()` in `src/template/compile.rs:156-157` — also a plain `std::fs::read_to_string(source_path)`. No HTTP client, no URL parsing, anywhere in this path.
- **`koto init --from-stdin`** (`src/cli/mod.rs:1069-1121`): reads bytes off stdin (`std::io::stdin().read_to_end`, `src/cli/mod.rs:1117`) and strict-compiles them inline via `init_inline_from_stdin_bytes` (`src/cli/init_child.rs:721`). "Strict" here means legacy-gate tolerance is off, not that provenance is checked — it's a compile-time linting knob, not an integrity gate. The raw bytes are persisted byte-for-byte into the session directory under a fixed filename (`INLINE_SOURCE_FILENAME`, exercised in `src/cli/init_child.rs:1352-1373`) so the workflow's own source becomes part of session state.
- **`--parent` (child workflows)**: `handle_init` resolves the child template path and calls `init_child_from_parent` (`src/cli/mod.rs:1777-1795`, `src/cli/init_child.rs`), which shares the same `compile_with_cache` → `compile_cached` → `compile()` → `fs::read` chain as the top-level path (`src/cli/init_child.rs:167-232`).
- **Batch child-template resolution**: the scheduler's per-tick spawn helpers (`src/cli/init_child.rs:313-500`, comments at lines 11-34) reuse the exact same `compile_with_cache`, keyed by canonicalized source path, so multiple children pointing at the same `default_template` compile once per tick. Still local disk only.
- **`src/discover.rs` and `src/engine/discovery.rs`**, despite the names, are *not* template-sourcing code — `src/discover.rs` is the coordinator's unassigned-child request scanner (walks `~/.koto/sessions/*`; doc comment `src/discover.rs:1-10`) and `src/engine/discovery.rs` is the `/workflows`-directory publish/discover mechanism over the context store (doc comment `src/engine/discovery.rs:1-16`). Both only touch `template_hash` in test fixtures, not in any template-loading logic. Worth stating plainly since the lead's brief named them as candidate routes — they aren't.
- **shirabe's `${CLAUDE_PLUGIN_ROOT}`-relative paths**: shirabe invokes `koto init` with `--template ${CLAUDE_PLUGIN_ROOT}/skills/execute/koto-templates/execute.md` (`shirabe/skills/execute/SKILL.md:184`) and `--template ${CLAUDE_PLUGIN_ROOT}/skills/work-on/koto-templates/work-on.md` (`shirabe/skills/work-on/SKILL.md:184,191`). `${CLAUDE_PLUGIN_ROOT}` is expanded by the Claude Code harness *before* koto ever sees the argument — from koto's perspective this is indistinguishable from any other `--template <path>` invocation. koto has no plugin concept and does nothing special with it.

### 2. Compilation and caching

The content hash is a **cache key computed from the compiled output**, not a provenance or trust token, and — critically — koto also uses it as a **post-init integrity check**, but only against the cached artifact, not against the original source.

- `cache.rs:33-46`: `compile_cached_into` calls `compile()`, serializes to pretty JSON, and hashes *that JSON* with SHA-256 (`sha256_hex`, `cache.rs:23-27`) — the hash covers the compiled template, not the raw markdown bytes. The artifact is written to `<dir>/<hash>.json` (content-addressed, so two compiles of identical output collide harmlessly; a temp-file + atomic rename handles concurrent writers, `cache.rs:64-84`).
- The hash is recomputed **once**, at `koto init` time, and then frozen into the session's `StateFileHeader.template_hash` (`src/engine/types.rs:236`) and the resolved `template_path` recorded on `WorkflowInitialized` points at the cache artifact (or, for inline sessions, a session-local copy — see below), not at the original source file.
- On every subsequent state-mutating command — `koto next` (`src/cli/mod.rs:3210-3226`), `koto decisions record` (`src/cli/mod.rs:4750-4767`), `koto overrides record` (`src/cli/overrides.rs:178-199`) — koto re-reads `machine_state.template_path`, recomputes SHA-256 over those bytes, and compares against the header's `template_hash`. **On mismatch it fails closed** with `"template hash mismatch: header says {} but cached template hashes to {}"` and a dedicated `TemplateError` exit code. `koto status` performs the identical computation but **reports rather than rejects** (`response["template_hash_mismatch"]`, `src/cli/mod.rs:5065-5077`) — the comment there is explicit about why: `status` can't fail closed "without denying an agent its only recovery path at exactly the moment it has nothing else" (`src/cli/mod.rs:5065-5071`).
- **What this check actually catches**: corruption or tampering of the *cached compiled JSON on disk* between `koto init` and the next tick (e.g. someone hand-edits `~/.cache/koto/<hash>.json`, or `~/.cache` gets partially evicted/rewritten). It does **not** catch someone editing the original `.md` source after the session started — that source is never re-read post-init; only the frozen cache artifact (or, for inline/relocated sessions, the session-local copy — `src/cli/init_child.rs:1263-1327` shows the session-relative artifact still hash-verifies after a directory `relocate`, precisely because the check targets *that* artifact, not the upstream source).
- Net effect: **the hash is an immutability pin for one session's lifetime, not an authenticity or provenance check.** It guarantees "the template this session is executing is exactly what it started with," never "what it started with was reviewed, expected, or safe."

### 3. Integrity and provenance

Searched explicitly for signing, pinning-as-trust, allowlisting, and trust-on-first-use (`rg` across `src/` for `sign|signature|verify|trust|allowlist|pin`). What exists:

- **`sha256_hex`** (`src/cache.rs:23-27`) — content hashing, used only as described in §2.
- **`allowlist` hits are all unrelated to templates**: `src/engine/substitute.rs:11,59,69,157,219` is the `--var` value character allowlist (already known-in-scope, blocks shell injection through substituted values); `src/cli/mod.rs:818-822,6505-6509` and `src/cli/workspace.rs:22` reference that same variable-value allowlist, not a template-source allowlist.
- **`trust` hits**: `src/engine/epoch.rs:40-42` ("epoch discipline is the trust boundary... trust at the type level") is about concurrent-writer fencing, unrelated to templates. `src/session/cloud.rs:386` ("we only trust...") is about HTTP status-code handling for *session state* sync, not templates. `src/cli/batch.rs:1369` ("subsequent ticks trust their...") is about sticky-marker scheduling, unrelated.
- **`pin` hits**: `src/cli/request.rs` has a `validate_contract`/`--contract-pin` mechanism (lines 54-61, 608-621) — but that pins the *CLI-to-engine JSON contract version* for polling callers, not a template.
- **No `koto template review` or `koto template approve` verb exists.** `TemplateSubcommand` (`src/cli/mod.rs:619-643`) has exactly four variants: `Compile`, `Validate`, `ValidateFeed`, `Export`. None of these evaluate trust or provenance; `Validate` (`validate_compiled_template`, `src/cli/mod.rs:664-671`) only checks structural well-formedness (`template.validate(true)`).
- **No signing or checksum manifest.** Nothing in `src/` reads a detached signature, a `.sig` file, a checksums manifest, or any external attestation before compiling or trusting a template.
- **No allowlist of approved template paths or hashes.** Any path the caller supplies compiles and runs; there is no gate comparing it to a known-good set.

Conclusion for this section, stated plainly: **the absence is real** — koto has no mechanism today for a human or agent to know, before `koto init` runs, that the template about to execute is one anybody reviewed or approved. The only integrity control in the codebase (§2) protects a session's template from changing *after* that session starts; it says nothing about what was true *before* it started.

### 4. The remote/dynamic surface

No network or dynamic-config template source exists.

- **`src/session/cloud.rs`** (1712 lines) implements an S3-style backend for *session state* sync (`fetch_remote_state_bytes`, `src/session/cloud.rs:390-415`; `fetch_remote_version`, `src/session/cloud.rs:255-283`) — reconciling JSONL event logs across machines. It has zero references to templates; grepping `template` in this file returns nothing. Cloud sync moves session *history*, never template *content*.
- **`src/config/mod.rs`, `src/config/resolve.rs`, `src/config/validate.rs`** (795 + 618 + 53 lines): zero occurrences of `template` anywhere in these three files. Workspace/session configuration has no template-sourcing surface at all.
- **`src/workflows_surface/materialize.rs`**: reads a template from a fixed session-local path (`session_dir.join("template.json")`, per the test helper at `src/workflows_surface/materialize.rs:405-409` and the doc comment at line 405) — this is the already-compiled, already-resolved artifact for a session that exists, not a new template-acquisition path.
- **`compile()` itself** (`src/template/compile.rs:156-157`) does a single `std::fs::read_to_string`, full stop — no URL scheme handling, no dynamic dispatch on source type.

This is worth stating as the sharpest negative finding available, per the lead's framing: **there is no sharp finding here** — the surface the brief asked about (templates arriving from network/cloud/config) simply doesn't exist in the current codebase. Every template, without exception, is a local file at `koto init`/`--parent`/batch-spawn time.

### 5. What a review or pinning practice would need

Given §§1-4, here's what's already present to build on, and the gap for each:

| Mechanism | What koto already has | What's missing |
|---|---|---|
| **Hash pinning in the session record** | Already fully implemented (§2): `template_hash` in `StateFileHeader`, computed via `sha256_hex`, verified fail-closed on every mutating command via the identical read-hash-compare pattern repeated at `src/cli/mod.rs:3210-3226`, `src/cli/mod.rs:4750-4767`, `src/cli/overrides.rs:178-199`. | This pins a template to *a session*, after the fact. Nothing pins a template path to an *expected* hash before `koto init` accepts it. |
| **`koto template review`/`approve` verb** | The `TemplateSubcommand` enum and its dispatch (`src/cli/mod.rs:619-663`) is exactly the extension point — `Compile`/`Validate`/`Export` already follow the pattern of "take a path, load it, report something." | No such verb exists. Adding one is small in mechanism (reuse `compile_cached` + `sha256_hex`, print/store the hash) but requires deciding what "approved" means and where approval state lives — nothing today. |
| **Comparing against a known-good manifest** | `sha256_hex` (`cache.rs:23-27`) is the exact primitive a manifest check would call. `compile_with_cache`'s canonical-path keying (`src/cli/init_child.rs:167-176`) shows the pattern for "resolve, then look up." | No manifest format, no manifest file location convention, and no call site that consults one — `handle_init` never asks "is this hash expected" before compiling and running. |
| **Declaring trust at the plugin level** | Nothing — koto has no notion of "plugin" at all. `${CLAUDE_PLUGIN_ROOT}` (§1) is purely a shell-level substitution performed by the Claude Code harness before koto's argv is ever populated; koto sees an ordinary path string. | This would necessarily live outside koto — in whatever installs/updates the plugin (marketplace, git clone, `install.sh`) — since koto has no concept to hang plugin-level trust on. Koto could still *cooperate* by exposing a stable hash (it already does, via `template compile`/the session header) that an external trust layer checks. |

The pragmatic near-term move, stated without prescribing it as a decision: the hash machinery for both "pin" and "compare against known-good" already exists end-to-end (`sha256_hex`, `compile_cached`, the fail-closed re-verify pattern) — it's applied one step too late (post-`init`, protecting an already-running session) rather than at the point `koto init` decides whether to compile and run a given path at all.

### 6. How shirabe ships templates

- Templates live as ordinary files in the shirabe git repo: `skills/execute/koto-templates/execute.md` and `skills/work-on/koto-templates/work-on.md` (confirmed present; each also has a `.mermaid.md` companion for diagram export).
- **Who can change them**: anyone who can land a PR against the `shirabe` repo — no distinct review track exists for `koto-templates/*.md` versus any other file. CI has structural checks (`check-templates.yml`, `check-template-consistency.yml`, `validate-templates.yml`) but these validate *compilability and internal consistency*, not authorization or intent. `validate-templates.yml` (`.github/workflows/validate-templates.yml:1-30`) installs `tsuku`/koto fresh in CI (`curl -fsSL https://get.tsuku.dev/now | bash`, then `tsuku install -y`) and runs `koto template compile "$template"` over every `*/koto-templates/*.md` file, failing the job on any compile error. This confirms templates compile, not that they're safe or intended.
- **How a change reaches a user**: through however the user installs/updates the shirabe plugin (Claude Code marketplace add, or a git pull/clone per `install.sh`) — an ordinary software-update trust model, no different from any other plugin file. Once installed, `${CLAUDE_PLUGIN_ROOT}` always points at whatever is currently on disk for that plugin; there's no version-locking of "this session was reviewed against shirabe v0.18.0's execute.md."
- **Version pinning between a shirabe release and the koto binary**: none found. `install.sh` and the `.github/workflows/*.yml` files have no `KOTO_VERSION`/`koto_version` reference (grepped explicitly, zero hits). `validate-templates.yml` installs whatever koto version `tsuku install` currently resolves to at CI run time — floating, not pinned to a compatible-known-good koto release.
- **Cross-skill template coupling has its own guard, but it's an existence check, not a trust check**: `skills/execute/scripts/assert-child-template.sh` fails closed if `/execute`'s lifted template can't resolve `../../work-on/koto-templates/work-on.md` before spawning children — but it only asserts the file exists, not that its content is expected or unmodified (`skills/execute/scripts/assert-child-template.sh:14-28`).

## Implications

Because loading a skill is the consent boundary (settled, per the brief), and because every template route traces back to a local file with no network surface, the practical trust chain today is: **whoever controls the file at the path the harness expands `${CLAUDE_PLUGIN_ROOT}` to, controls what `koto init` will execute.** For shirabe's own templates that's "whoever can merge to the shirabe repo, filtered through however the user's plugin install stays in sync with that repo" — an ordinary supply-chain trust model with no koto-specific hardening layered on top. koto's only integrity control (the hash re-verify) activates *after* that trust decision has already been made implicitly by `koto init` accepting the path, and its job is narrowly to keep the already-accepted template from silently changing under a running session — it was explicitly designed for that purpose (the `status` comment at `src/cli/mod.rs:5065-5071` and the relocate-safety test at `src/cli/init_child.rs:1263-1327` both target "does the artifact match what init recorded," not "was init's choice a good one").

## Surprises

- The lead's brief listed `src/discover.rs` and `src/engine/discovery.rs` as template-sourcing candidates; neither touches template loading — both are unrelated discovery mechanisms (coordinator request scanning and `/workflows`-directory publishing) that merely reference `template_hash` in test fixtures. Worth correcting explicitly since the names invite the wrong assumption.
- `koto status` deliberately *chooses* to report rather than enforce the same hash check `koto next` fails closed on, and says why in a code comment (`src/cli/mod.rs:5065-5071`) — not an oversight, a considered trade-off (an agent's only recovery path shouldn't itself be blocked by the thing it's trying to recover from).
- The hash re-verification machinery (§2) is more complete than the brief's framing suggested — it isn't merely a cache key, it's an active, fail-closed integrity check exercised on nearly every state-mutating command. It just verifies the wrong thing for a "was this template reviewed" question: the cached artifact's stability, not the source's authenticity.

## Open Questions

- Should `koto init` itself gain an optional "expected hash" argument (`--expect-hash <sha256>`) so a caller (a skill script, a wrapper) can assert "only run if this compiles to exactly the template I reviewed" — reusing the existing `sha256_hex`/`compile_cached` primitives without inventing new ones?
- If a manifest-of-known-good-hashes approach is chosen, does it live in koto (a new `~/.koto/trusted-templates.toml` or similar, consulted at `handle_init`) or one layer up in whatever manages the plugin install — given koto has no plugin concept, the latter seems structurally cleaner but was not decided here.
- Is there an appetite for `assert-child-template.sh`-style existence checks in shirabe to grow into hash checks (comparing the resolved template's compiled hash against a value recorded at shirabe's own release time), independent of any koto-side change?

## Summary
Every template route in koto — `--template`, `--from-stdin`, `--parent`, batch child-spawn, and shirabe's `${CLAUDE_PLUGIN_ROOT}`-relative paths — resolves to a plain local-disk read (`src/template/compile.rs:156-157`); no network, cloud, or config-driven template source exists anywhere in `src/session/cloud.rs` or `src/config/**`. koto already computes and fail-closed re-verifies a SHA-256 of the *compiled* template on nearly every session-mutating command (`src/cli/mod.rs:3210-3226`, `4750-4767`; `src/cli/overrides.rs:178-199`), but that check protects a running session's template from changing after `koto init` accepted it — it is an immutability pin, not a provenance, review, or allowlist mechanism, and no such mechanism (no `template review`/`approve` verb, no manifest, no signing, no koto-level plugin trust) exists today. The two or three things that would make the boundary real: extend the existing hash machinery to run *before* `koto init` accepts a path (an expected-hash argument or a known-good manifest check), add a `koto template` verb that surfaces a hash for a human/CI to record as "reviewed," and — since koto has no plugin concept — decide separately whether plugin-level trust (pinning a shirabe release's template hashes) belongs in shirabe's own release process rather than in koto.

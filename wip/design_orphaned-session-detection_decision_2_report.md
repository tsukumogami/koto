### Decision: Backend differentiation for orphan-detection (local vs. CloudBackend)

**Context**
The new orphan-detection signal (its shape decided separately, in decision 1) flags sessions whose recorded `template_source_dir` no longer exists on disk. `CloudBackend` makes cross-machine resume a shipped, documented workflow: a session created on machine A and resumed on machine B legitimately has a `template_source_dir` that only ever existed on A. This decision asks whether the signal's computation, wording, or suppression should differ between `LocalBackend` and `CloudBackend` to handle that case, without adding new S3 round trips to `koto session list`.

Direct code research (`src/session/cloud.rs`, `src/engine/path_resolution.rs`, `src/session/version.rs`, `docs/designs/current/DESIGN-config-and-cloud-sync.md`) overturned part of the premise handed in for this decision. `SchedulerWarning::StaleTemplateSourceDir`'s `machine_id` field, cited as prior art for "softening the deleted-vs-cross-machine ambiguity," does not actually perform that distinction today: `current_machine_id()` (`path_resolution.rs:66-79`) is a cheap, ephemeral local read used purely as an observational label on the warning ("here's which machine noticed this"), not a comparison against any stored value. `StateFileHeader` has no machine identifier at all. A second, unrelated `machine_id` concept exists (`get_or_create_machine_id()` / `version.json.machine_id`, `session/version.rs:234-273`) but it records the *last machine to write a version bump*, not the machine that recorded `template_source_dir`, and it's frequently absent for sessions that were only ever read, never written to — it is not a reliable substitute.

`CloudBackend::list()`'s remote-only placeholder rows (`cloud.rs:677-699`) carry no header data at all, so they aren't actually where the described false positive happens. The real, common false positive occurs after a session's header has already been pulled down to a second machine via `sync_pull_state` (triggered by any ordinary header read, not by `list()` itself) — at that point the row is an indistinguishable, fully-populated *local* session whose `template_source_dir` happens to belong to another host. No backend flag on the row distinguishes this case; only the underlying fact (which no current field records) would.

**Assumptions**
- Decision 1 has not yet been finalized (`wip/design_orphaned-session-detection_coordination.json` shows both decisions "pending"); this decision assumes decision 1's constraints hold regardless of its eventual signal shape: bare `Path::exists()` is accepted as sufficient, the new field is additive-only on `SessionInfo`, and it must not collide with `--orphaned`.
- Assumed decision 1 will follow `SessionInfo`'s existing `Option` idiom (as `parent_workflow` already does) rather than the `String::new()` sentinel idiom (`created_at`/`template_hash` use in the same struct today). If wrong, `CloudBackend::list()`'s placeholder rows would misfire the check universally (`Path::new("").exists()` → `false`) — flagged below as an implementation trap for decision 1's implementer to close explicitly, not something decision 2 can pre-empt in wording.
- Assumed "no new round trips" is a hard constraint that also rules out inventing new persisted state solely to serve this decision (a new creator-machine-id write path is a schema/write change, not a round-trip cost, but it is a materially larger and separately-scoped change than adjusting computation/wording/suppression of an existing signal).

**Chosen: Backend-aware wording only, gated on the free `Backend::is_cloud()` discriminant**
Keep the orphan check's computation identical across backends: evaluate `Path::exists()` only when `template_source_dir` is known (`Some`), never when it's absent/unknown, regardless of which backend produced the row. Do not suppress or skip the check for `CloudBackend` sessions specifically — a fully-downloaded session with a genuinely stale `template_source_dir` is just as worth flagging as a local one.

The one place backend should matter is the message text. When the session's backend is `Backend::Cloud(_)` (a static, zero-cost discriminant already in hand — `cloud.rs:559-561` — requiring no I/O and no new field), soften the wording to acknowledge the ambiguity instead of asserting deletion: something like "template source directory not found (if this session was synced from another machine, this may be expected)" rather than a flat "template source directory no longer exists." For `LocalBackend` sessions, where cross-machine resume is not a possible explanation (`DESIGN-config-and-cloud-sync.md`: without cloud sync, a session can't be resumed on another machine without manually copying `~/.koto/sessions/`), keep the more direct wording.

This is not a claim that the code has determined the cross-machine explanation applies to a specific session — it hasn't, and per the research no cheap, reliable per-session signal exists to make that claim honestly. It's a static, backend-type-level hedge on wording, applied uniformly to every `CloudBackend` session's warning, reflecting that cross-machine resume is *possible* for that class of session, which is strictly more informative than saying nothing and costs nothing new.

**Rationale**
The research settled the factual question this decision turns on: today, no free (no new round trip, no new persisted state) per-session signal exists that can reliably tell "deleted" from "cross-machine" for a given `template_source_dir`. The only thing that is actually free is the static backend-type discriminant. Given that, uniform wording (Alternative 1) throws away information that costs nothing to use — it would let a common, healthy, documented workflow produce a message that reads exactly like "someone deleted your directory." A stronger, backend-specific signal (Alternative 3: a new creator-machine-id persisted in `StateFileHeader` at init) would require inventing new state and a new write path — a materially bigger change than this decision is scoped to make, and per the `version.json.machine_id` precedent (a machine-id field that already exists in this codebase and already drifts because it tracks "last writer" rather than "creator"), not guaranteed to be reliable even if built, unless implemented with unusually careful immutable-after-init semantics that go beyond what "should the signal differ by backend" needs to settle. The chosen option is the smallest change that uses exactly the information that is genuinely free today, respects the read-only/no-new-round-trip/additive-only constraints, and stops the signal from overclaiming certainty it doesn't have.

**Alternatives Considered**
- **Uniform behavior (identical check, identical wording, no backend awareness)**: Rejected because it discards a zero-cost signal (the static `is_cloud()` discriminant) that is already available on every session row, producing needlessly alarming wording for a common, shipped, healthy workflow (cross-machine resume) without any offsetting simplicity benefit — the backend-aware branch is a single conditional at message-formatting time, not a structural complication.
- **Machine-id cross-reference via a new persisted creator-machine-id**: Rejected because it requires inventing new persisted state and a new write path in `StateFileHeader`/`init`, which is a larger, separately-scoped change than adjusting an existing signal's computation/wording/suppression, and because the codebase's existing `version.json.machine_id` field demonstrates that machine-id fields are prone to drift (tracking "last touched by" rather than "created by") unless deliberately designed to be immutable post-init — a risk this decision doesn't need to take on to deliver most of the benefit via wording alone.

**Consequences**
- `koto session list` and any warning surface built on the orphan signal gain a small, backend-conditional message variant; no new fields, no new network calls, no change to when the check fires.
- Decision 1's implementer must ensure the new `SessionInfo` field uses `Option` semantics (mirroring `parent_workflow`), not the `String::new()` sentinel idiom already present for `created_at`/`template_hash` in `CloudBackend::list()` — otherwise every remote-only placeholder row would be wrongly flagged as orphaned regardless of any backend-aware wording layered on top. This is an implementation-correctness note for decision 1/its implementation, not a backend-differentiation decision, but it must be carried forward so it isn't lost.
- The wording softening is honest about its own limits: it signals possibility, not certainty. A future revision could strengthen this (e.g., the open TODO in `path_resolution.rs` about wiring `current_machine_id()` to a stored per-session identifier) but that is explicitly out of scope here and would need its own decision given the persisted-state and drift concerns identified above.
